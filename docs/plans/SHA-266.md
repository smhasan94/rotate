# Implementation plan: SHA-266 provider and consumer matrix doc

## What the code does today

Read from `src/provider/{aws,github,npm,openai}.rs`,
`src/consumer/{github_actions,aws_secrets_manager}.rs`, `src/apply.rs`,
`src/rollback.rs` and the plans for SHA-251 to SHA-262. Where the code and a
ticket differ, the doc follows the code.

- AWS is automated end to end. Revoke deactivates the key and never deletes
  it, so `restore` reactivates it and `revoke_replacement` deactivates the
  replacement. It is the only provider with `verify_replacement`, so it is
  the only one that can resume at verify in a new process.
- GitHub and npm are always in manual replacement mode. `restore` is always
  `Unsupported`. `verify_replacement` and (for a pasted replacement)
  `revoke_replacement` are not available, so rollback tells the operator to
  revoke the pasted token by hand. GitHub `ghs_` tokens are identified,
  checked and described but not revocable. npm needs an `npm login` session
  token for the token list and delete, and a delete that asks for a one-time
  password fails and names the page.
- OpenAI depends on the admin key: with one, replacement, revoke and
  `revoke_replacement` are automated; without one, replacement is manual and
  revoke is manual (`manual_revoke`). A service-account key is removed only
  by deleting its service account, and only when it is that account's only
  key; otherwise revoke is manual. Admin keys are identified but not
  checked or rotated. `restore` is always `Unsupported`.

## Changes

1. `docs/providers.md`: legend (Automated, Manual, Unsupported); one table
   per provider with the seven ticket operations (`identify`, `check_valid`,
   `describe_scope`, `create_replacement`, `verify`, `revoke`, `restore`)
   plus `verify_replacement` and `revoke_replacement`, each with status,
   operator credential and a one-line note. `manual_instructions` and
   `manual_revoke` are covered in the notes of the rows they change. A
   status cell may read `Automated; Manual without admin key` for OpenAI.
   One table per consumer (`find` with ByValue or ByName, `update`,
   `restore`) with the token or IAM permissions. A "before an incident"
   checklist per provider. Known gaps section.
2. `rotate plan` (and the apply preview) prints one line naming
   `docs/providers.md` when any rotation has a manual replacement, a manual
   revoke or a consumer that cannot be updated. `--json` is unchanged.
3. README links the doc.

## Tests

- T1 (covers AC1), `tests/provider_matrix.rs`: parses the doc's tables and
  asserts 4 providers x 9 operations (the 7 required plus the 2 resume and
  rollback ones) and 2 consumers x 3 operations, each with a status of
  Automated, Manual or Unsupported and a non-empty note. It also reads the
  `Provider` and `Consumer` trait blocks from `src/` and asserts every trait
  method name appears in the doc, so a new trait method fails the test until
  it is documented.
- T2 (covers AC2), same file: builds each real provider with no credentials
  and derives cells from the code with no network call: `create_replacement`
  from `replacement_mode()` (OpenAI with and without an admin key), `revoke`
  from `manual_revoke()`, `verify_replacement` and `revoke_replacement` from
  whether they return the trait's default `Unsupported`, `identify` from a
  sample of each format, and `restore` from `restore()` itself (GitHub, npm
  and OpenAI answer `Unsupported` without a call; AWS answers `Restored`
  against a local wiremock IAM). Each must equal the doc's cell. The
  conformance suite's `restore_outcome` check accepts both `Restored` and
  `Unsupported`, so it records no outcome to compare against; the test calls
  `restore` directly instead.
- T3 (covers AC3), `tests/plan_cli.rs`: a plan with a manual npm mock prints
  `docs/providers.md`; a plan with only automatic steps does not.

## Out of scope

The minimum-permission policies (SHA-270), the usage guide (SHA-269), any
change to provider behaviour.
