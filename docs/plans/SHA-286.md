# Implementation plan: SHA-286 batch GitHub revocations in one apply

`POST /credentials/revoke` takes up to 1000 tokens, must be unauthenticated,
and allows 60 such requests an hour. `GithubProvider::revoke_many` already
chunks by `REVOKE_BATCH`, but `Provider::revoke` sends one token, and
`main.rs` runs `executor.run(rotation)` to completion, revoke included, one
rotation at a time. Dozens of leaked tokens cost one request each and can
hit the limit part way through. The fix has two halves: a batch hook on the
`Provider` trait, and an executor that runs every rotation to the revoke
gate first and revokes in a final phase.

## Decisions

- One executor entry point for many rotations: `Executor::run_all(&[&
  PlannedRotation]) -> Vec<Outcome>`, outcomes in input order. `run(rotation)`
  stays as `run_all(&[rotation])`, so the unit tests, the GitHub integration
  tests and `confirm_revoked_by_hand` do not change. `main.rs` calls
  `run_all` once.
- Two phases inside `run_all`. Phase 1 (`prepare`) runs each rotation in
  order through eligibility, the plan entry, resume, create, update, verify,
  `recheck_by_hand`, the revoke gate and `record_force`; everything that
  ends there (skipped, failed, needs rollback, held, pending without
  `--wait`, revoke by hand confirmed or still open) is final at once. A
  rotation whose gate said `Revoke`, or `Wait` with `--wait`, becomes a
  `Ready` and is not touched again until phase 2. Phase 2 (`revoke_ready`)
  groups the `Ready` rotations by provider, waits once per group, then
  makes one `revoke_batch` call per group and records each rotation's
  result as `finish` does today. Revoke is still the last step of every
  rotation, and still skipped after any earlier failure, because only a
  rotation that passed its gate is ever in a group.
- The executor never calls `Provider::revoke` directly any more; it always
  calls `revoke_batch`, also for a group of one. The default implementation
  loops over `revoke`, so AWS, npm, OpenAI, the mock and the scenario mocks
  make exactly the calls they make today and the call logs of existing tests
  still show `revoke` per credential. `GithubProvider::revoke` stays for the
  trait contract, the conformance suite and the provider tests; its body
  (`revoke_many(&[token])`) is unchanged.
- The held replacement keeps its SHA-293 contract. Today `steps` removes the
  verified credential from `held` and keeps it alive in a local until
  `finish` returns, so a revoke error that echoes it is redacted
  (`UpstreamText::Redacted`); a run that never held it gets
  `UpstreamText::Summary` (SHA-294). Now the credential moves into
  `Ready::verified: Option<Credential>` and lives until that rotation's
  revoke outcome is recorded in phase 2, then is dropped (zeroized, and
  unregistered from the redactor with the last copy). `Ready` derives no
  `Debug`, holds the value nowhere else, and never reaches state or audit.
  The lifetime grows by the time the other rotations take to reach their
  gate; with `--wait` it already spanned the window. `UpstreamText` is
  decided per rotation from `verified.is_some()`, exactly as before.
- Within a batch, every rotation is still its own record: its own `revoke`
  audit entry (ok, failed or skipped) and its own checkpoint
  (`Step::Revoked`, `restore_ref`), written in group order after the batch
  returns. `record_force` stays where it is, at the gate in phase 1, so
  every `force` entry of a batch precedes the request (AC7).
- Rate limits. `GithubProvider::revoke_batch` stops at the first chunk that
  answers `RateLimited` and returns that error for the chunk and for every
  later chunk, without sending them. Any other chunk error (5xx, 422 other
  than "already revoked") applies to that chunk only and the next chunk is
  still sent, as the rotations are independent today. The executor adds
  rotate's own text to a `RateLimited` revoke failure: "re-run rotate apply
  after <rfc3339> (in <remaining>) to revoke it" when the provider gave a
  hint, else "once the provider's rate limit resets". Nothing is retried.
- `--wait`: phase 1 records the pending revoke and the skipped `revoke`
  audit entry as today, then returns a `Ready` carrying `not_before`.
  Phase 2 orders the groups by their latest `not_before` (groups with
  nothing to wait for first, then by time; ties keep first appearance),
  sleeps once per group until that latest time, and sends the batch. No
  credential is revoked before its own time; one with an earlier time waits
  for the latest in its provider group, never for another provider. One
  notice per group replaces the per-rotation one.
- Crash safety. Before the request every rotation of a chunk is at
  `verified`, `pending_revoke` or `failed` at force/revoke; a crash between
  the request and the checkpoints leaves them there. A re-run resumes each
  at `Revoke`, passes the gate again and sends the same tokens: GitHub
  answers 202, or 422 "already revoked", both `Ok`, and the checkpoints are
  written. A crash between two checkpoints leaves some rotations `revoked`:
  `split_already_rotated` drops those before assessment with zero calls and
  the rest are re-sent. The window is the same as today's for a single
  rotation; nothing new is recorded.
- Installation and legacy tokens. The executor keeps `manual_revoke(scope)`
  per rotation after the wait, so a `ghs_` token whose scope names the
  installation type never enters the batch. One whose scope does not (a
  seeded record, or a legacy-format token) is refused by `revocable` inside
  `revoke_batch`, gets its own `Unsupported` result and is left out of the
  request; the executor turns that into revoke by hand with
  `INSTALLATION_UNSUPPORTED` (or the legacy text) as it does today.
- `revoke_batch` is added to `MUTATING`. State, audit, plan and status
  schemas do not change; no new exit code.

## Changes

`src/provider/mod.rs`

- `Provider::revoke_batch(&self, credentials: &[&Credential]) ->
  Vec<Result<Revoked, ProviderError>>`, default: `revoke` on each in order,
  one result per input, never stopping early. Doc on `revoke`: apply calls
  `revoke_batch`; implement `revoke` and override `revoke_batch` only when
  the provider has a bulk endpoint.
- `MUTATING` gains `"revoke_batch"`; `mutating_list_matches_contract`
  updated.

`src/provider/github.rs`

- `revoke_chunk(&self, tokens: &[&SecretValue]) -> Result<(), ProviderError>`:
  one `POST /credentials/revoke` with `revoke_body`, `Auth::Anonymous`;
  422 "already revoked" is `Ok`; otherwise `op_error(REVOKE, err)`. Factored
  out of `revoke_many`, which keeps its signature and all-or-nothing
  precheck and now loops `revoke_chunk`.
- `revoke_batch` override: `token` then `revocable` on each credential;
  refused ones get `Err` in place. Accepted `(index, &SecretValue)` pairs are
  chunked by `REVOKE_BATCH`; each chunk's `revoke_chunk` result is written to
  every index in it (`Ok(Revoked { restore_ref: None })` or a clone of the
  error). After a chunk returns `RateLimited`, the remaining chunks get a
  clone of it with no request. An empty accepted set sends nothing.

`src/apply.rs`

- `struct Ready<'r> { index: usize, rotation: &'r PlannedRotation,
  progress: Progress, verified: Option<Credential>, not_before:
  Option<OffsetDateTime> }`; `enum Prepared<'r> { Done(Progress, RunResult),
  Ready(Ready<'r>) }`. No `Debug` on either.
- `pub async fn run_all(&mut self, rotations: &[&PlannedRotation]) ->
  Vec<Outcome>`: eligibility (`Outcome::skipped`), `prepare` per rotation,
  then `revoke_ready` on the collected `Ready`s; results placed by `index`.
  `run` becomes a wrapper.
- `async fn prepare<'r>(&mut self, rotation: &'r PlannedRotation) ->
  Prepared<'r>`: today's `steps` up to and including the gate. The tail of
  `steps` that moved the verified credential out of `held` now puts it in
  the `Ready`. `finish` is split:
  - `async fn gate(&mut self, rotation, provider, progress) ->
    Result<Option<OffsetDateTime>, RunResult>`: `recheck_by_hand` for
    `RevokeManual`, `resume_gate`, `record_force`, `Hold` and `Wait`
    handling. `Ok(None)` is revoke now, `Ok(Some(t))` is ready after `t`
    (`--wait`), `Err` is final.
  - `fn record_revoke(&mut self, ready: &mut Ready, result: Result<Revoked,
    ProviderError>) -> RunResult`: the match on the revoke result with
    `UpstreamText` from `ready.verified`, the rate-limit hint
    (`retry_hint(now, retry_after)`), `revoke_by_hand`, the `Revoked`
    checkpoint. Then `ready.verified` is dropped.
- `async fn revoke_ready(&mut self, ready: Vec<Ready<'_>>) -> Vec<(usize,
  Progress, RunResult)>`: group by `rotation.provider`, order groups as
  decided, per group: wait (`notice` naming the rotation ids, then
  `tokio::time::sleep`), `manual_revoke` per rotation (by hand, out of the
  batch), one `revoke_batch` over the rest, then `record_revoke` for each in
  order. A result vector of the wrong length fails every rotation of the
  group at revoke with "the provider returned N results for M credentials;
  the old secret may still be valid". A provider missing from the registry
  (cannot happen after phase 1) fails the same way.
- `fn outcome(rotation, progress, result) -> Outcome`: the `unchanged`
  computation from `run`, shared by both phases.
- Module doc: the two phases, where the verified replacement lives and for
  how long, and the GitHub batch.

`src/main.rs`: `outcomes.extend(executor.run_all(&requested).await)`.

`src/provider/mock.rs`: no override; a test-local wrapper in `apply::tests`
(`BatchRecorder`, delegating every method to a `MockProvider` and recording
the size of each `revoke_batch` call in an `Arc<Mutex<Vec<usize>>>`) proves
the executor groups.

Docs: `docs/usage.md` "For each confirmed rotation, in this order" becomes:
every confirmed rotation is taken through create, update, verify and the
revoke gate first, then the old secrets are revoked, last; GitHub tokens go
to the revocation API in one request per 1000; a rate limit fails the
rotations still to revoke with the time to re-run; `--wait` waits once for
the latest window of each provider. One line in `docs/non-interactive.md`
under exit 1 for the rate-limit re-run.

Unchanged: `aws.rs`, `npm.rs`, `openai.rs`, `rollback.rs`
(`revoke_replacement` and `restore` are per rotation and out of scope),
`state.rs`, `audit.rs`, `status.rs`, `plan.rs`, `render_summary`,
`run_status`, the exit mapping.

## Tests

GitHub integration tests live in `tests/github_provider.rs` and reuse
`pipeline`, `mount_user`, `mount_revoke`, `revokes` and `trace_capture`. A
new `pipeline_many(rec, leaked: &[&str], extra: Vec<Arc<dyn Provider>>)`
plans several findings in one registry; `seed_verified(p, id)` moves a
record to `verified` with `MANUAL_REF` and one updated consumer, as the
SHA-289 installation test does. Tokens are built with `classic`/`token` and
unique tags.

- T1 (AC1) `sha286_t1_five_github_and_one_aws_revoke_in_one_post`: five
  classic tokens plus a `MockProvider::new("aws").identify_prefix("mock_aws_")`
  finding; `ReplacementSource::Prompt(ScriptedPrompt)` pastes five
  replacements whose `GET /user` answers `octocat`; `run_all`. Assert one
  POST whose `credentials` array holds exactly the five leaked tokens, no
  `Authorization` header, one mock `revoke` call with the AWS fingerprint,
  six `Revoked` outcomes in input order, `run_status` `Done`.
- T2 (AC2) `sha286_t2_revoke_batch_chunks_1001_tokens`: provider level,
  `revoke_batch` over 1001 credentials; assert request sizes `[1000, 1]` and
  1001 `Ok`. The executor side of AC2 is
  `apply::tests::ready_rotations_are_revoked_in_one_batch_per_provider`
  (`BatchRecorder`: three npm rotations seeded `verified` and two for a
  second mock provider give `revoke_batch` sizes `[3, 2]`, one call each).
  1001 rotations through the executor would mean 1001 fsynced state writes,
  so the chunking is proven where it lives.
- T3 (AC3) `sha286_t3_batch_writes_one_revoke_entry_and_record_each`: three
  seeded rotations; after `run_all`, `audit::read_all` has three `revoke`
  entries with outcome ok whose `rotation_id` and `fingerprint` sets match
  the plan; three records at `revoked`; the audit log and the state file
  contain none of the three tokens.
- T4 (AC4) two tests. `sha286_t4_rate_limited_chunk_stops_the_batch`:
  provider level, 1001 credentials, `POST` answers 429 with `retry-after:
  1800`; assert one request and 1001 `RateLimited { retry_after:
  Some(1800s) }`. `sha286_t4_rate_limited_revoke_fails_every_rotation`:
  three seeded rotations through `run_all` with the same mock; assert one
  request, every outcome `Failed { step: Revoke }` with text containing
  "re-run rotate apply after" and the rfc3339 time 30 minutes from the
  clock, no 202 ever answered (old secret still valid), records at `failed`
  with `failed_step` revoke, `run_status` `Failed` (exit 1), `render_summary`
  carries the time.
- T5 (AC5) `sha286_t5_only_gate_passed_rotations_enter_the_batch`: four
  GitHub rotations: one seeded `pending_revoke` with `revoke_not_before` an
  hour ahead; one whose consumer is `not_updatable` (held); one whose
  replacement `GET /user` is mounted `up_to_n_times(1)`, so the paste check
  passes and the verify step gets the catch-all empty 200 and fails to
  decode (failed at verify); one ready. Without `--wait`, assert the POST
  body has only the ready token and the other three outcomes are
  `PendingRevoke`, `Held`, `Failed { step: Verify }`.
- T6 (AC6) two tests. `sha286_t6_revoke_batch_leaves_out_installation_tokens`:
  provider level, `[ghs_, ghp_, ghp_]`; the body has the two `ghp_` tokens,
  result 0 is `Unsupported(INSTALLATION_UNSUPPORTED)`.
  `sha286_t6_installation_token_in_a_batch_is_by_hand`: executor level, the
  `ghs_` rotation seeded `verified` with a scope without a `type` line so
  `manual_revoke` is `None`; assert its outcome is `RevokeManual` with
  `INSTALLATION_UNSUPPORTED`, the two others `Revoked`, one POST with two
  tokens.
- T7 (AC7) `sha286_t7_force_is_recorded_before_the_batch_request`: a
  wiremock `Respond` that, when the POST arrives, reads the audit log and
  records whether a `force` entry exists for every forced rotation and
  whether any ok `revoke` entry exists yet; assert `(true, false)`, the
  records have `force: true`, and the audit order is every `force` before
  every `revoke`.
- T8 (AC8) `sha286_t8_wait_sends_one_batch_after_the_latest_window`: two
  rotations seeded `pending_revoke` at now+1s and now+2s, `with_wait(true)`;
  assert elapsed >= 2s before the single POST (two tokens), both `revoked`,
  one "waiting until" notice naming both ids. Unit half
  `apply::tests::wait_groups_by_latest_not_before` with `with_clock` past
  both times: no sleep, one `revoke_batch` of two; and with a third
  rotation of another provider at `Revoke`, that provider's call precedes
  the GitHub group's wait.
- T9 (AC9) `provider::tests::default_revoke_batch_calls_revoke_in_order`:
  `MockProvider` with `fail_next("revoke", Permanent)`, `revoke_batch` over
  three credentials; the log shows three `revoke` calls with the
  fingerprints in input order and the results are `[Err, Ok, Ok]` with the
  restore refs of inputs 1 and 2.
- T10 (AC1, AC4) `sha286_t10_batch_revoke_never_leaks`: the T1 and T4
  executor runs under `trace_capture`; for every leaked and replacement
  token assert absence from the summary, `term.out`, `term.err`, the audit
  log, the state file, the TRACE capture and `format!("{outcome:?}")`; on
  the wire the leaked tokens appear only in the revoke body and in
  `Authorization` of `GET /user` and `GET /user/orgs`, the replacements only
  in `Authorization` of `GET /user`. CLI half in `tests/leakage.rs`
  `sha286_t10_mock_batch_apply_sweep`: a `MockRun` with a gitleaks report of
  three `ghp_` canary tokens under `inputs/` (the scenario's github mock,
  prompt answers `["all"]`), `apply <report> --all` at `-vvv` with
  `RUST_LOG=trace`, exit 0, three `revoked`; the `Sweep` covers stdout,
  stderr, the state file, the audit log and the call log for every canary
  and the mock replacement.
- Existing tests that pin the old shape and change: `wait_revokes_after_the_window`
  (notice text still contains "waiting until"), `mutating_list_matches_contract`,
  `revoke_many_batches_by_a_thousand` (unchanged behaviour, now through
  `revoke_chunk`). Every other executor test runs through `run`.

Checked by mutation before the PR: with the GitHub `revoke_batch` override
removed T1 and T2 fail; with the stop-on-429 removed T4 fails; with
`record_force` moved after the batch T7 fails. All four checks run with
`RUSTUP_TOOLCHAIN=1.99.0`.
