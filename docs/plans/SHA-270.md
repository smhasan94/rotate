# Implementation plan: SHA-270 operator permission docs

## What the code calls today

Read from `src/provider/aws.rs`, `src/consumer/aws_secrets_manager.rs`,
`src/consumer/github_actions.rs` and the wiremock models in
`tests/e2e/mod.rs`. Where the code and the ticket differ, the doc follows
the code.

- AWS provider, operator credentials: `iam:GetAccessKeyLastUsed`,
  `iam:GetUser`, `iam:ListAttachedUserPolicies`, `iam:ListUserPolicies`,
  `iam:ListGroupsForUser`, `iam:ListAccessKeys`, `iam:CreateAccessKey`,
  `iam:UpdateAccessKey`. The ticket's list misses `iam:GetUser`
  (`describe_scope` reads the owner's ARN with it), so it is added.
  `sts:GetCallerIdentity` is signed only by the leaked and the new key
  today and needs no permission; with `--check-permissions` the operator
  calls it too, to learn its own ARN for the simulation.
- Secrets Manager consumer: `secretsmanager:GetSecretValue`,
  `secretsmanager:PutSecretValue`, `secretsmanager:ListSecrets` (only for
  `tag_filters`).
- GitHub Actions consumer: list secrets, `GET .../public-key`, `PUT` the
  secret; org secrets also read the secret and its selected repositories.
- `iam:DeleteAccessKey` is never called.
- `rotate status` makes no call; `rotate rollback` uses
  `iam:GetAccessKeyLastUsed`, `iam:ListAccessKeys`, `iam:UpdateAccessKey`
  and the consumers' write permissions.

## Changes

1. `REQUIRED_ACTIONS` constants: `provider::aws::REQUIRED_ACTIONS` (the
   eight IAM actions), `provider::aws::CHECK_PERMISSIONS_ACTIONS`
   (`sts:GetCallerIdentity`, `iam:SimulatePrincipalPolicy`) and
   `consumer::aws_secrets_manager::REQUIRED_ACTIONS` (the three Secrets
   Manager actions).
2. `rotate plan --check-permissions` (new `PlanArgs`). After the plan is
   built it runs read-only probes:
   - AWS: `sts:GetCallerIdentity` with the operator credentials (an
     assumed-role ARN becomes its role ARN), then
     `iam:SimulatePrincipalPolicy` for the operator with the provider's
     actions on the key owner's ARN, and with the Secrets Manager write
     actions on each matched entry named by ARN. Each denied action becomes
     a blocker `operator lacks <action> on <resource> (IAM policy
     simulation)`. A simulation that cannot run (no
     `iam:SimulatePrincipalPolicy`, unknown owner, entry named by name) is
     a warning on stderr, not a blocker.
   - GitHub Actions: `GET .../actions/secrets/public-key` once per target
     with an updatable match. 403 or 404, or a classic token whose
     `x-oauth-scopes` lacks `repo` (repository) or `admin:org` (org), marks
     the target's matches NotUpdatable with reason `token lacks Secrets:
     write`; blockers are recomputed. A fine-grained token's permissions
     are not readable, so a 200 without `x-oauth-scopes` passes.
   - No other provider has a read-only probe; the doc says so. The plan
     JSON shape is unchanged (results go in `blockers` and consumer
     `reason`), so `docs/plan-schema.json` needs no change.
3. `docs/permissions.md`: a per-command summary (plan, apply, rollback,
   status), the full minimal IAM policy JSON (IAM user-scoped statement,
   Secrets Manager resource-scoped statement, `ListSecrets` on `*`, the
   optional check statement) with resource scoping examples and the
   explicit `iam:DeleteAccessKey` note; GitHub token requirements (classic
   `repo` / `admin:org`, fine-grained "Secrets: read and write" and
   organization "Secrets: read and write"); npm and OpenAI requirements
   (already there, kept); a `--check-permissions` section. Links
   `docs/providers.md` (SHA-266) without repeating its matrix.
4. README: mention `--check-permissions` next to the permissions link.

## Tests

- T1 (unit, covers AC1), `tests/permissions_doc.rs`: parses the policy JSON
  from `docs/permissions.md` and asserts its action set equals
  `aws::REQUIRED_ACTIONS` + `aws_secrets_manager::REQUIRED_ACTIONS` +
  `aws::CHECK_PERMISSIONS_ACTIONS`, without `iam:DeleteAccessKey`. A
  second test scans the two source files for SDK operation calls and
  asserts each one is in the constants and each constant is called, so
  the constants cannot drift from the code.
- AC1 (integration, wiremock), `tests/permissions_e2e.rs` (on the shared
  harness, so `tests/acceptance_mvp.rs` is untouched): the e2e AWS
  model gains an operator `GetCallerIdentity` answer and a
  `SimulatePrincipalPolicy` route, and can enforce a policy: any operator
  call outside it is denied. With the doc's policy enforced, `plan
  --check-permissions`, `apply` and `rollback` succeed, the plan has no
  permission blocker, and every operator action the model saw is in the
  policy. With `iam:CreateAccessKey` removed from the simulated policy the
  plan names it as a blocker.
- T2 (integration, wiremock, covers AC2), `tests/permissions_e2e.rs`: the GitHub model answers 403 on
  `public-key`; `plan --check-permissions` lists both Actions matches as
  `cannot update: token lacks Secrets: write`, the JSON reason matches, and
  `assert_no_mutations()` holds. Without the flag the probe is not made.
- T3 (unit, covers AC3), `tests/permissions_doc.rs`: the doc has each
  required heading, the IAM JSON, the GitHub scopes, npm and OpenAI
  requirements and `--check-permissions`.
- T4 (integration, wiremock, covers AC2): T2 with a canary operator token
  in `GITHUB_TOKEN` (not `ROTATE_GITHUB_TOKEN`); stdout, stderr at
  `-vvv`/`RUST_LOG=trace`, the audit log and the state file do not contain
  it.

## Out of scope

Creating policies for the user, live tests, the provider matrix itself
(SHA-266).
