# Implementation plan: SHA-204 mlock and core-dump protection for secret buffers

`SecretValue` wipes its buffer on drop (SHA-217), but while rotate runs the
bytes sit in ordinary heap pages. The kernel may write those pages to swap,
and a crash may write the whole address space to a core file, where the
secret survives the process. This ticket closes both paths where the OS
allows it: core dumps are switched off for the process at startup, and every
`SecretValue` buffer is locked in RAM (`mlock`) for as long as it lives, with
a single warning when the OS refuses.

## Context

- `SecretValue` holds `Zeroizing<Vec<u8>>` plus a redaction `Registration`
  and derives `Clone`, `Zeroize` and `ZeroizeOnDrop`. It has no method that
  grows or shrinks the vector, so its heap allocation never moves: `new`
  moves the caller's vector in, `from_reader` reads into a 4096-byte
  reservation and then wraps, `zeroize` writes zero to the whole capacity
  and clears the length but keeps the allocation. `Clone` allocates a fresh
  vector (capacity = length). So each `SecretValue`, clones included, owns
  one stable allocation from construction to drop. That is what `mlock`
  needs.
- How many are alive at once: one per finding of the input report (the
  leaked value), plus per rotation the replacement and its held clone until
  revoke (SHA-286 keeps verified replacements alive until the batch
  revoke), plus short-lived OTPs and pasted values. A report of a few
  hundred findings means a few hundred small allocations, most sharing heap
  pages.
- `RLIMIT_MEMLOCK` defaults: Linux kernels before 5.16 default to 64 KiB,
  5.16 and later to 8 MiB; systemd sessions usually set 8 MiB; containers
  inherit whatever the runtime sets (often 64 KiB, sometimes 0); root and
  processes with `CAP_IPC_LOCK` are not limited. macOS reports `unlimited`
  by default but does enforce a lower limit: with `ulimit -l 0`, `mlock`
  fails with `EAGAIN` (checked on this machine, macOS 27, arm64). Page size
  is 4 KiB on Linux x86_64 and 16 KiB on Apple silicon.
- Locks do not nest. Two `mlock` calls on one page and one `munlock` leave
  the page unlocked. Small allocations share pages, so unlocking the pages
  of one buffer when it drops would silently unlock another live secret on
  the same page.
- Locked memory must be unlocked before it is freed, after it is wiped:
  wipe while locked (the zeros never reach swap anyway, but the secret
  must not be paged out between unlock and wipe), unlock, then free. Freed
  memory that stays locked counts against the limit until the allocator
  reuses it.
- rustix is already a dependency (`termios`). Its `process` feature has
  `getrlimit`/`setrlimit` and, on Linux, `set_dumpable_behavior`
  (`prctl(PR_SET_DUMPABLE)`); `mm` has `mlock`/`munlock`; `param` has
  `page_size`. `setrlimit` and `set_dumpable_behavior` are safe functions.
  `mlock` and `munlock` are `unsafe fn`: the caller promises the range is
  mapped memory it may read. No new crate is needed.
- `lib.rs` has `#![deny(unsafe_code)]`, allowed so far only in tests.
- rotate starts child processes: `/bin/hostname` for the audit actor and,
  through aws-config, `credential_process` helpers. They inherit resource
  limits; neither needs a core dump. The Linux dumpable flag is reset by
  `execve`, so it does not reach them.

## Findings

- The redaction registry (`src/redact/registry.rs`) keeps its own copy of
  every registered value and its encoded forms in `Zeroizing<String>`.
  Those copies are wiped on removal but are not locked by this ticket.
  Copies made by reqwest, rustls and the AWS SDK are not locked either.
  Core dumps are still covered for them because the switch is process
  wide; swap is not.
- `from_reader` may reallocate while reading input over 4096 bytes. The
  old allocation is freed unwiped before the buffer is ever locked. This is
  the existing documented limit and does not change.
- macOS has no equivalent of `PR_SET_DUMPABLE`. Its options are the core
  limit (which this ticket sets) and `ptrace(PT_DENY_ATTACH)`, an
  anti-debugging call that rustix does not wrap and that would stop
  legitimate debugging. The hardened runtime of a signed release binary
  already refuses `task_for_pid` from other processes without the
  `get-task-allow` entitlement; that is a packaging matter.
- Linux `MADV_DONTDUMP` would exclude the secret pages from a core even if
  the limit were raised. With the hard core limit at 0 and the process not
  dumpable, it adds nothing that the process can lose, so it is left out.

## Decisions

- New module `src/harden.rs` owns all OS calls. `pub fn harden_process()`
  is called once, as the first statement of `main`. On Unix it sets
  `RLIMIT_CORE` to 0 soft and 0 hard, then on Linux calls
  `prctl(PR_SET_DUMPABLE, 0)`. Each call is independent; one failing does
  not skip the other. Errors are ignored: lowering a limit and clearing the
  dumpable flag never fail for an unprivileged process, and logging is not
  installed yet at that point (T1 and T2 prove the result on CI).
- Page locking lives in `harden::Locker`: a page-size and a per-page
  reference count (`HashMap<page index, count>`) in front of a small
  `PageOps` trait with `lock` and `unlock`. The real `PageOps` calls
  rustix `mlock`/`munlock`; tests plug in a refusing and a recording one.
  `Locker::lock(buf)` locks the whole capacity of a vector; on success it
  increments the count of every page the allocation touches and returns a
  `Span` (address, capacity). `Locker::unlock(buf, span)` decrements those
  counts and `munlock`s only the runs of pages that reached zero, each run
  clipped to the buffer's own allocation (so the pointer passed to the
  kernel stays inside memory rotate owns). A mismatch between `span` and
  the vector does nothing, never unlocks foreign pages. The process-wide
  locker is a `OnceLock<Mutex<Locker>>`; a poisoned lock is recovered, as
  the redaction registry does, because unlock runs in `Drop`.
- The only `unsafe` in non-test code is in `harden.rs`: one function that
  turns a vector and an offset range into a pointer and length after
  checking the range lies inside the vector's capacity, with the two
  rustix calls in `unsafe` blocks carrying `SAFETY:` comments. The module
  is `#[allow(unsafe_code)]` on those items only; `lib.rs` keeps
  `#![deny(unsafe_code)]` and its doc names the exception.
- `SecretValue.bytes` becomes a private `LockedBytes { bytes: Vec<u8>,
  locker: &'static Mutex<Locker>, span: Option<Span> }` in `secret.rs`.
  Construction moves the vector in (no copy) and locks it. `Clone`
  allocates and locks a new vector. `Zeroize` wipes the vector and keeps
  the allocation and the lock. `Drop` wipes the whole capacity, then
  unlocks, then the vector is freed. `Deref<Target = [u8]>` keeps every
  existing read of the bytes unchanged. `SecretValue` still derives
  `Zeroize` and `ZeroizeOnDrop`; nothing in its public API changes.
- A refused `mlock` (limit reached, limit 0, unsupported) leaves that
  buffer unlocked and the `SecretValue` fully usable. The first refusal of
  the process emits one `tracing::warn!`, shown at default verbosity on
  stderr: `could not lock secret values in memory (<OS error>); they may
  be written to swap. Raise the locked-memory limit (ulimit -l) to remove
  this warning`. Later refusals are silent; every new secret still tries,
  so a buffer created after others were freed can still be locked. The
  text has no value, fingerprint, length or address. The warning is
  emitted after the locker's mutex is released.
- Test hook for macOS, where there is no `/proc`: with the
  `test-commands` feature (never in releases), when
  `ROTATE_TEST_HARDENING_REPORT` names a file, `harden_process` writes
  `core_soft=<n> core_hard=<n>` and on Linux `dumpable=<0|1>` there after
  hardening. On Linux T1 also reads `/proc/<pid>/limits` of a running
  rotate, with no hook involved.
- Cargo: rustix gains the `process`, `mm` and `param` features. No new
  crate.

## Maintainer decisions (recommended, pending maintainer review)

1. **`unsafe` for `mlock`.** (a) Two audited `unsafe` blocks in
   `harden.rs` behind a safe wrapper that bounds-checks the range against
   the vector's capacity, using rustix. (b) A new crate (`region` or
   `memsec`) whose API is safe to call but which holds the same `unsafe`
   internally and adds a dependency. (c) No `mlock`; core dumps only.
   Recommended: (a). The contract is small and local; rustix is already
   audited by `cargo deny` and in the tree.
2. **Core limit: soft only or soft and hard.** (a) Soft and hard 0, so
   neither rotate nor a child can raise it again. (b) Soft 0 only, so an
   operator debugging a crash could raise it from inside. Recommended:
   (a). Debugging a crash can be done by running a build without the call.
3. **Linux `PR_SET_DUMPABLE`.** (a) Clear it on Linux: no core even if
   `suid_dumpable` or a raised limit would allow one, and other processes
   of the same user can no longer `ptrace` rotate or read its
   `/proc/<pid>/mem`, `environ` or `fd` (those become root-owned).
   `strace rotate ...` still works because tracing starts before the flag
   is cleared; attaching later needs root. (b) Leave it. Recommended: (a).
   macOS gets the core limit only; `PT_DENY_ATTACH` is not used.
4. **Pages shared between buffers.** (a) A per-page reference count in the
   process-wide locker; unlock only pages whose count reaches zero. (b)
   Page-aligned dedicated allocations for secrets (a custom `Layout`
   allocation per value), so no page is shared. Recommended: (a). (b)
   needs more `unsafe` (raw allocation and deallocation), wastes a whole
   page per secret (16 KiB on Apple silicon) and hits a 64 KiB limit after
   four to sixteen secrets.
5. **Warning: where and how often.** (a) One `tracing::warn!` per process
   on the first refusal, stderr at default verbosity, redacted like every
   log line. (b) A console line through `Console::err`. (c) Only at `-v`.
   Recommended: (a); it is what the ticket's AC2 asks for, and `--json`
   stdout stays clean.
6. **Scope of what is locked.** (a) `SecretValue` buffers only in this
   ticket; a follow-up ticket locks the redaction registry's copies
   through the same `harden` API (`src/redact` is outside this change).
   (b) Also lock the registry now. (c) `mlockall(MCL_CURRENT | MCL_FUTURE)`
   for the whole process (Linux only, needs a limit far above 8 MiB for a
   tokio and rustls process, so it would fail almost everywhere).
   Recommended: (a). The Limits section of `docs/security.md` says what is
   still not locked.

## Ticket (refined)

### Context

MVP zeroizes secret buffers on drop. It does not prevent the memory from
being swapped to disk or written in a core dump. This ticket disables core
dumps for the process and locks every `SecretValue` buffer in memory where
the platform allows, and falls back gracefully where it does not.

### Scope

In scope: `setrlimit(RLIMIT_CORE, 0)` soft and hard at startup on Unix;
`prctl(PR_SET_DUMPABLE, 0)` on Linux; `mlock` on every `SecretValue`
buffer (clones included) with a per-page reference count, wiped then
`munlock`ed before free; one warning per process when `mlock` is refused;
a `test-commands` hook that reports the core limit; docs.

Out of scope: Windows; macOS `PT_DENY_ATTACH`; `MADV_DONTDUMP`;
`mlockall`; locking the redaction registry's copies and copies held by
libraries (follow-up); reallocation copies in `from_reader`.

### Acceptance criteria

AC1. Given a Unix host, when rotate starts, then the soft and hard core
file size limits of the process are 0.
AC2. Given `mlock` is refused by the OS, when SecretValues are created,
then every creation succeeds, the values work, and exactly one warning is
logged for the process, containing no secret value.
AC3. Given a Linux host, when rotate starts, then the process is not
dumpable.
AC4. Given two live SecretValues whose buffers share a page, when one is
dropped, then the shared page stays locked; when the last one is dropped,
then its buffer is wiped before its pages are unlocked, and every page it
locked is unlocked.

### Test plan

T1 (integration) - covers AC1, AC3 - Linux: spawn `rotate plan --stdin`
with stdin held open so it blocks reading; read `/proc/<pid>/limits`, "Max
core file size" is `0 0`; when the test does not run as root,
`/proc/<pid>/status` is owned by root (not dumpable).
T2 (integration) - covers AC1, AC3 - any Unix, `test-commands`: run rotate
with `ROTATE_TEST_HARDENING_REPORT`; the report says `core_soft=0
core_hard=0`, and on Linux `dumpable=0`.
T3 (unit) - covers AC2 - a locker whose `mlock` always fails; three
SecretValues created through it hold their bytes and compare equal to
plain ones; a raw (unredacted) log capture holds exactly one WARN line,
which contains none of the values.
T4 (integration) - covers AC2 - real refusal: `sh -c 'ulimit -l 0; exec
rotate plan --stdin'` with a canary secret; exit 0 and the usual plan;
stderr has the warning exactly once and no canary. Skipped as root, where
`CAP_IPC_LOCK` ignores the limit.
T5 (unit) - covers AC4 - a recording `PageOps`: two buffers on a shared
page (page size chosen so both fall in one page); dropping the first makes
no `munlock`; dropping the second makes one `munlock` covering its
allocation, and at that call the buffer is already wiped (empty).
T6 (unit) - covers AC4 - page size 1 (no sharing): lock then unlock of one
buffer is one `mlock` and one `munlock` of the same range; a span that does
not match the buffer unlocks nothing.

### Definition of done

Every T-case passes in CI on Linux and macOS, fmt, clippy and cargo deny
pass, `docs/security.md` and `docs/requirements.md` updated, PR reviewed and
merged.

### Dependencies

Blocked by: none.

## Changes

- `Cargo.toml`: rustix features `process`, `mm`, `param` on the normal
  dependency.
- `src/harden.rs` (new): `harden_process`, `Locker`, `Span`, `PageOps`,
  `SystemPages`, `locker()`, `lock`/`unlock` free functions that warn once,
  the `test-commands` report hook, unit tests T3 (locker level), T5, T6.
- `src/lib.rs`: `pub mod harden;`, crate doc names the `unsafe` exception.
- `src/main.rs`: `rotate::harden::harden_process();` as the first line of
  `main`.
- `src/secret.rs`: `LockedBytes`; `wrap` locks; module doc no longer says
  locking is a Later ticket; T3 at `SecretValue` level.
- `tests/hardening.rs` (new): T1, T2, T4.
- Docs: `docs/security.md` safety rule 1 and the "Memory dumps" limit;
  `docs/requirements.md` threat-model mitigations; `docs/usage.md` a short
  note on the warning.
