# Implementation plan: SHA-256 apply safety rules and `--force`

Ticket edits applied with this plan:

- A failed `update` without `--force` stops the rotation at once: the
  consumer is recorded `failed`, later consumers are not touched (they keep
  the old, still valid secret), `verify` and `revoke` are not called, the
  rotation is `failed` with `failed_step: update`, exit 1. With `--force` a
  failed `update` is recorded the same way, the remaining consumers are
  still updated, `verify` still runs, and the failed consumer is one of the
  consumers `--force` revokes past. `--force` never bypasses a failed
  `create_replacement` or `verify`, or a failure to record the force itself.
- State gains `failed_step` (`create`, `update`, `verify`, `revoke`,
  `force`, ...; absent unless `step` is `failed`), so "failed at step
  update" (AC1) is in the state file and resume (SHA-258) knows where it
  stopped. The schema stays version 1: the field is optional.
- `--force` is recorded only when it changes the outcome: when the revoke
  gate would otherwise hold. Then state gets `force: true` and the audit
  log gets one `force` entry per consumer revoked past (`consumer` is the
  ref; a consumer whose `find` failed is `<name> (not searched)`), each with
  the actor, before the revoke. If that record cannot be written, the
  rotation fails at step `force` and nothing is revoked. A `--force` that
  bypassed nothing is not recorded.
- A rotation held at `verified` (consumers not all updated, no `--force`)
  can be finished by re-running `rotate apply ... --force`: a rotation at
  step `verified` goes straight to the revoke gate using the consumers in
  the state file. Nothing is created or updated again. This is the one
  resume path this ticket needs so the "re-run with --force" message is
  true; every other resume stays SHA-258.
- Messages, in the summary on stdout (one note per rotation):
  - failure before revoke: `<id>: <step> failed: <error>; stopped before
    revoke; old secret still valid; consumers: <ref> updated, <ref> failed,
    <ref> unchanged` (`skipped` for a not-updatable one);
  - hold: `<id>: N consumer(s) not updated (<refs>); re-run with --force to
    revoke anyway; the old secret is still valid`;
  - force: `<id>: revoked with --force; not updated: <refs>`;
  - revoke failure: `<id>: revoke failed: <error>; the replacement is live
    and the old secret may still be valid`.
- Exit codes are unchanged from SHA-254: 1 if any rotation failed or was
  held, else 3 if any revoke is pending, else 2 if any was skipped as
  unsupported, else 0. Other rotations in the run always continue.
- Apply prints the plan with the header `Plan to apply: N to rotate, M
  skipped. Nothing has been changed yet.`; `rotate plan` keeps `Dry run:
  nothing was changed.`

## Approach

`src/apply.rs`:

- `Executor::with_force(bool)`; `run` signature unchanged.
- `pub fn not_updated(rotation, consumers) -> Vec<String>`: refs of
  consumers not `updated`, then `<name> (not searched)` per lookup error.
- `revoke_gate(rotation, consumers, verified_at, force) -> Gate`: `Hold`
  when `not_updated` is non-empty and `force` is false; otherwise `Wait`
  for an open overlap window, else `Revoke`.
- `steps`: create and the consumer loop are untouched apart from the
  update error branch (continue under `--force`). After verify, and for a
  rotation already at `verified`, `finish` runs the gate, records the force
  (state then audit) and revokes.
- `fail` also sets `failed_step`.
- `Outcome` gains `unchanged` (planned consumer refs never touched) and
  `forced` (refs revoked past). `render_summary` writes the notes above.

`src/state.rs`: `Rotation.failed_step: Option<AuditStep>`, serde default and
skipped when absent.

`src/plan.rs`: `render_apply_table` (same body, apply header).

`src/cli.rs`: `ApplyArgs.force` (`--force`). `src/main.rs`: pass it to the
executor; print the apply header.

## Secret handling

No new value is held. Errors still go through `RedactedText` while the old
credential (the plan) and, before verify ends, the replacement are
registered. Force entries hold refs only. T8 injects error texts that
contain the old value and the replacement value and greps stdout, stderr
with `-vvv`, the audit log and the state file.

## Test mapping

CLI tests in `tests/apply_safety.rs` (`test-providers`); unit tests in
`src/apply.rs`.

- T1 (AC1): `update_failure_stops_before_revoke`; unit
  `update_failure_without_force_stops_at_once`.
- T2 (AC2): `verify_failure_never_revokes_even_with_force`; unit
  `force_never_bypasses_create_or_verify`.
- T3 (AC3): `not_updatable_holds_and_mentions_force`; unit
  `gate_holds_waits_or_revokes`.
- T4 (AC4): `force_revokes_and_records_force`,
  `held_rotation_finishes_with_force_on_rerun`; unit
  `force_records_state_and_audit_before_revoke`,
  `force_past_failed_update`.
- T5 (AC5): `second_rotation_completes_after_first_fails`.
- T6 (AC6): `revoke_failure_says_replacement_is_live`.
- T7 (AC7): `create_failure_updates_nothing`.
- T8 (AC1, AC2, AC6): `failures_never_leak_values` (update, verify with and
  without `--force`, revoke; canary per case).
- Extra: `apply_header_is_not_dry_run` (plan keeps its header);
  recorder assertion in every CLI test that no `revoke` follows a failed
  step.

## Sequence

1. State field, gate, executor and summary with unit tests.
2. CLI flag, header, main wiring; CLI tests; README and backlog notes.
3. All checks; PR.

## Risks

- SHA-257 edits the create step and `cli.rs` / `main.rs` apply path; this
  ticket leaves the create block as is and adds one flag and one builder
  call. Merge conflicts, if any, are small.
- The coordinator's `consumers_with` edit touches the same lines of
  `main.rs` apply; keep both.

## Out of scope

Resume after failure, finishing a pending revoke and `--wait` (SHA-258),
rollback (SHA-259), status (SHA-263).
