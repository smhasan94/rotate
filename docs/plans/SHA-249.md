# Implementation plan: SHA-249 Provider and consumer conformance test suite

Ticket edits applied with this plan:

- Redaction is checked without the SHA-218 redaction layer, which is being
  built in parallel. "Error text is redacted" means: no error's `Display` or
  `Debug` contains any secret value the suite fed in or received (the
  fixture's credentials, a suite-made canary, and every replacement).
  SHA-218 can tighten it later.
- The second `revoke` must return `Ok`. The trait has no "already revoked"
  outcome, so a plugin maps the provider's "already deleted" answer (404,
  `NoSuchEntity`) to `Ok(Revoked { .. })`.
- `verify` is checked both ways: it accepts the fixture's live credential
  with the right identity and rejects it with a wrong one. Rejecting alone
  would let a plugin that always errors pass.
- Manual-mode providers (D1) skip `replacement_differs`, which the report
  lists as skipped rather than passed.
- `MockConsumer::find` becomes stateful: it returns a match while that
  consumer holds the secret's fingerprint, so `update` then `find` shows the
  new one. `MockProvider` gains a revoked set: `check_valid` on a revoked
  fingerprint returns `Invalid`, and `verify` compares the identity with its
  scope. Without these the default mocks could not pass AC1 and AC4.

## Approach

A new library module `src/conformance/` exposes two async functions:

```rust
pub async fn provider_suite<F, Fut>(factory: F) -> SuiteReport
where F: Fn() -> Fut, Fut: Future<Output = ProviderFixture>;
pub async fn consumer_suite<F, Fut>(factory: F) -> SuiteReport
where F: Fn() -> Fut, Fut: Future<Output = ConsumerFixture>;
```

The factory is called once per check, so each check gets a fresh plugin and
a fresh test server. This is what makes "revoke twice" expressible against
wiremock: the plugin's test mounts a first `DELETE` answer with
`up_to_n_times(1)` and a 404 after it, and no other check sees that state.
Starting a wiremock server takes milliseconds, and the suite has ten checks.

The fixture carries the plugin, the credentials the server knows about, and
a `MutationProbe`: an async trait returning labels of every state-changing
call seen so far. `CallLog` implements it for the mocks. A plugin's
integration test implements it for its wiremock `CallRecorder` (a few lines,
mapping `RecordedCall::mutating`). Each read-only check compares the probe
before and after one call.

The suite returns a `SuiteReport` listing every check as passed, failed
(with a detail string) or skipped. It never panics on a plugin failure, so
AC2, AC3, AC5 and AC6 can assert which check failed. `assert_ok()` panics
with the report for plugin tests that only want pass or fail.

Every error a plugin returns, in any check, goes through one recorder. It
notes the method if the error text contains a known secret (that is the
`errors_redacted` result), and scrubs known secrets from the text before it
goes into a detail string. So the report itself never carries a value even
when the plugin under test leaks one.

The module is compiled unconditionally, like `provider::mock` and
`consumer::mock` already are. It adds no dependencies, the release binary
drops it as unused code, and integration tests under `tests/` reach it in
both `cargo test` and `cargo test --all-features`.

Rejected: a `conformance` cargo feature. Plain `cargo test` would then skip
plugin conformance tests (or fail to build them) unless every plugin test
sets `required-features`, which hides a skipped suite. Rejected: one fixture
shared by all checks. The revoke checks change server state, and order
dependence between checks would make failures hard to read. Rejected: a
`#[macro_export]` that generates one `#[test]` per check. It gives nicer test
names but cannot return a report for AC2 to AC6 to inspect.

## Changes

- `src/conformance/mod.rs`: `SuiteReport { suite, plugin, checks: Vec<CheckResult> }`,
  `CheckResult { name, outcome: Outcome }`, `Outcome { Passed, Failed(String), Skipped(String) }`,
  with `is_ok()`, `failed() -> Vec<&'static str>`, `detail(name)`,
  `assert_ok()`, and `Display`. `MutationProbe` trait plus its `CallLog`
  impl. `canary(like: &Credential) -> Credential` (same shape, suite-made
  value). The error recorder and scrubber.
- `src/conformance/provider.rs`: `ProviderFixture { provider, live, identity, unknown, probe }`
  and `provider_suite`. Checks: `identify_rejects_foreign` (empty value and
  one runtime-built sample per other MVP provider), `check_valid_unknown_invalid`
  (`unknown` gives `Ok(Invalid)`, `live` gives `Ok(Valid)`),
  `read_only_check_valid`, `read_only_describe_scope`, `read_only_verify`,
  `replacement_differs`, `verify_wrong_identity_fails`, `idempotent_revoke`,
  `restore_outcome` (`Restored` or `Unsupported` for the ref `revoke` gave),
  `errors_redacted` (every error seen, plus each credential method called
  with the canary).
- `src/conformance/consumer.rs`: `ConsumerFixture { consumer, old, new, secret, probe }`
  and `consumer_suite`. Checks: `find_unknown_empty`, `read_only_find`,
  `update_then_find` (each updatable match of `old` is found for `new`
  after `update`), `restore_reverses_update` (after `update` then
  `restore`, `find` for `old` returns the match again and a `ByValue` match
  is gone from `find` for `new`), `errors_redacted`.
- `src/conformance/mock.rs`: `provider_fixture(MockProvider)` and
  `consumer_fixture(MockConsumer)`, the wiring T1 to T6 use.
- `src/provider/mock.rs`: revoked set (`revoked(fingerprint)` builder;
  `revoke` adds, `restore` removes); `verify` compares identity; knobs
  `fail_after(method, ok_calls, error)` (AC2), `mutates_in(method)` (AC3),
  `leak_secret_in_errors(method)` (AC6).
- `src/consumer/mock.rs`: stateful `find`; knobs `restore_is_noop()` (AC5)
  and `leak_secret_in_errors(method)` (AC6).
- `src/lib.rs`: `pub mod conformance;`.
- `tests/conformance.rs`: both suites run from outside the crate through
  the public API, under `LogCapture`, with the probe implemented for a
  local type as a plugin test would.
- `CONTRIBUTING.md`: "Adding a provider" and "Adding a consumer" say how to
  call the suite and drop the "until SHA-249 lands" wording.

## Secret handling

The suite holds secrets only as `SecretValue` inside fixtures and reads them
with `expose_secret_str` to search and scrub error text. Detail strings are
built from method names, fingerprints, call labels and scrubbed error text.
The canary is built at runtime and matches no scanner pattern; so do the
foreign-provider samples (prefixes are concatenated at runtime). T6 checks
that a leaking plugin fails `errors_redacted` while the report's `Display`
and `Debug` and the captured tracing do not contain the value.

## Test mapping

Unit tests in `src/conformance/` (`#[tokio::test]`):

- T1 (AC1): `provider_suite_passes_on_default_mock`.
- T2 (AC2): `second_revoke_error_fails_idempotent_revoke`: `fail_after("revoke", 1, Permanent)`; only `idempotent_revoke` fails.
- T3 (AC3): `mutation_in_check_valid_fails_read_only_check_valid`: `mutates_in("check_valid")`; `read_only_check_valid` fails and its detail names `check_valid`.
- T4 (AC4): `consumer_suite_passes_on_default_mock`.
- T5 (AC5): `noop_restore_fails_restore_reverses_update`.
- T6 (AC6): `leaking_error_fails_errors_redacted` (provider, `check_valid`) and `leaking_consumer_error_fails_errors_redacted` (consumer, `update`): `errors_redacted` fails naming the method, and the canary is in neither `Display` nor `Debug` of the report.
- Extras: `manual_mode_skips_replacement_differs`, `identify_claiming_foreign_value_fails`, `verify_ignoring_identity_fails`, `mock_revoked_set_and_identity` (mock unit tests), `find_follows_current_value` (consumer mock).
- `tests/conformance.rs`: `suites_pass_from_outside_the_crate` and `leaking_plugin_report_and_logs_stay_clean` (T6 again, through `LogCapture`).

## Sequence

1. Mock changes and their unit tests; existing tests stay green.
2. Report types, probe, recorder; provider suite; T1 to T3, T6 provider half.
3. Consumer suite; T4, T5, T6 consumer half.
4. `tests/conformance.rs`, CONTRIBUTING, fmt, clippy (with and without
   features), test (both), deny; PR.

## Risks and unknowns

- PR #14 (SHA-248) also edits `src/provider/mock.rs` (latency and in-flight
  tracking around the read methods). Whichever lands second merges main and
  keeps both.
- `identify_rejects_foreign` uses one sample per MVP provider. Real
  provider tickets may add samples when they learn a format the table lacks.
- A wiremock plugin whose server answers unknown routes with 200 may pass
  `errors_redacted` without ever producing an error. Plugin tests should
  mount 401 or 404 answers for `unknown`; CONTRIBUTING says so.

## Out of scope

Real providers and consumers (SHA-251 to 253, SHA-260 to 262), which call
the suite from their own tests. The SHA-218 redaction layer. A check that
`update` refuses a not-updatable match (covered by SHA-222's contract and
each consumer's own tests).
