# Implementation plan: SHA-289 "revoke by hand" outcome

A rotation whose old credential rotate cannot revoke ends at a new,
non-terminal step `revoke_manual` with the provider's instructions, exit 4,
instead of `failed` at revoke with exit 1.

## Decisions

- Audit: no schema change. The first time apply stops at `revoke_manual` it
  writes one `revoke` entry with outcome `skipped` and the instructions in
  `error` (the field every `skipped` entry already uses for its reason). A
  re-run that finds the old secret still valid writes the same entry again.
  Confirmation writes a `revoke` entry with outcome `ok` and the text
  "revoked by hand, confirmed by check_valid".
- State: schema stays version 1. New step value `revoke_manual` and one new
  optional field on a rotation, `revoke_instructions` (text, never a value;
  absent otherwise and in older files). Older files read unchanged.
- The instructions stored are the provider's full text (for example
  `REVOKE_NEEDS_ADMIN`). The summary and the status hint drop a leading
  `manual: ` or `unsupported: ` so the line reads naturally.
- Exit codes: new `4` (`Exit::RevokeManual`). `run_status` precedence is
  failed (1) over revoke by hand (4) over pending (3) over unsupported (2).
  `rotate status` keeps its contract: a `revoke_manual` row is pending, so
  status exits 3, with the instructions as the hint.
- Confirmation on re-run has two paths, both read-only at the provider:
  - The old secret is still valid at plan time: the plan carries the
    rotation at step `revoke_manual`, and the executor calls only
    `check_valid` on it. `Invalid` records `revoked`; `Valid`, `Unknown` or
    an error leaves it at `revoke_manual` (exit 4).
  - The old secret is already invalid at plan time (the usual case once the
    operator deleted it): assessment's own `check_valid` skips it as
    `invalid`, so it never reaches the executor. The plan marks such a
    skipped secret, when the state file has a `revoke_manual` rotation for
    the same provider and fingerprint, with the new skip reason
    `revoked by hand` and the rotation id in its detail; apply then records
    that rotation `revoked` with the same ok audit entry, with no further
    call and no confirmation prompt (it is bookkeeping of a fact the
    operator brought about). `rotate plan` only shows the row.
- `GithubProvider::manual_revoke` returns `INSTALLATION_UNSUPPORTED` when
  the scope's type line names a GitHub App installation token. Legacy
  tokens are still refused by `revoke` with `Unsupported`, which apply now
  turns into `revoke_manual` with that text.
- A ghs_ token cannot pass `verify` today (no replacement can be checked
  against an installation), so apply only reaches its revoke step from a
  state file at `verified`; T2 seeds that.
- `rotate status` no longer reports the text of an `ok` audit entry as an
  error (the confirmation entry carries a detail).
- `rotate rollback` already treats any step other than `revoked` without a
  restore handle as never revoked (`NotRevoked`); a test pins this.

## Changes

- `src/state.rs`: `Step::RevokeManual`, `Rotation::revoke_instructions`.
- `src/exit.rs`: `Exit::RevokeManual = 4`.
- `src/apply.rs`: `RunResult::RevokeManual`, `RunStatus::RevokeManual`,
  manual branch in `Executor::finish` (after gate and window), check on
  re-run, `Executor::confirm_revoked_by_hand` for the plan-skip path,
  summary line and header count.
- `src/plan.rs`: step name and resume text, `REVOKED_BY_HAND` skip reason
  and `mark_revoked_by_hand`.
- `src/main.rs`: exit mapping; apply records revoked-by-hand rotations.
- `src/status.rs`: pending, hint, ok entries are not errors.
- `src/provider/github.rs`: `manual_revoke` for installation tokens.
- `src/provider/mock.rs`, `src/providers.rs`: `manual_revoke` and
  `Unsupported` failures for the mock and the scenario.
- Docs: README exit codes and steps, `docs/status-schema.json`,
  `docs/plan-schema.json`.

## Test plan mapping

- T1 (AC1): executor unit test, mock with `manual_revoke`; no `revoke` call,
  step and text, `run_status` maps to exit 4; plus a CLI run.
- T2 (AC2): CLI against the real GitHub provider and wiremock, state seeded
  at `verified` for a ghs_ token; step, stored text, no POST to
  `/credentials/revoke`, exit 4.
- T3 (AC3): `render_summary` unit test.
- T4 (AC4): `run_status` table test.
- T5 (AC5): CLI with seeded `revoke_manual` and validity invalid; and an
  executor test where `check_valid` turns Invalid after plan.
- T6 (AC6): executor and CLI, `check_valid` Valid; only `check_valid`.
- T7 (AC7): executor, `revoke` Permanent then Transient.
- T8 (AC8): executor with an injectable clock inside the window.
- T9 (AC9): plan with the GitHub provider against wiremock and a ghs_
  token; revoke row, blocker, only GET requests.
- T10 (AC10): status and rollback CLI against a seeded state file.
- T11 (AC1, AC2, AC5): leak check over stdout, stderr, state and audit for
  the T1, T2 and T5 runs.
