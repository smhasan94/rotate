# Implementation plan: SHA-264 AWS end to end with wiremock

Ticket edits applied with this plan:

- The test drives the real AWS provider and the real Secrets Manager
  consumer through the `rotate` binary. CI runs `cargo test --all-features`,
  and with `test-providers` the binary registers mocks under the real names.
  A scenario file may now say `"real_plugins": true`: the binary then
  registers the real plugins, exactly as a release build does, and the
  scenario only scripts the prompt (`"panic"`: any prompt fails the test).
  Without the feature the scenario is ignored and the real plugins are
  registered anyway, so the test passes in both builds.
- Endpoints. The AWS provider had `with_endpoint_url` for library tests but
  nothing in `rotate.yaml` reached it, and the leaked-key and replacement
  STS client is built without the environment, so `AWS_ENDPOINT_URL` cannot
  redirect it. New setting `providers.aws.endpoint_url` (an `ApiUrl`):
  STS, IAM and Secrets Manager calls go there instead of AWS (LocalStack, a
  test server). The test points it at the wiremock server.
- AC4 (`rotate status --all`): `rotate status` is still a stub on main; it
  lands with SHA-263 (Todo, blocked by SHA-258). T4 asserts the state file
  record the status command reads (step `revoked`, both fingerprints, no
  pending revoke, consumer `updated`), and a second test runs `rotate
  status --all` and asserts the row and exit 0. That test is `#[ignore]`d
  with the reason "needs `rotate status` (SHA-263)"; SHA-263 removes the
  ignore.
- AC1 "lists the IAM user": the table's `identity:` line is the user's ARN
  (`arn:aws:iam::000000000000:user/deploy-bot`); `--json` also has the scope
  line `user: deploy-bot`. Both are asserted.
- AC7 "the message says revoke was not attempted": the summary says
  `stopped before revoke; old secret still valid`. That text is asserted.
- T8 runs every command at `-vvv` (TRACE, which includes the AWS SDK's own
  events) with `RUST_LOG=trace` set as well, and also greps every request
  the server recorded. Requests that must carry a secret are exempt: the
  `PutSecretValue` bodies (apply writes the new pair, rollback the old pair;
  each is asserted to hold exactly that pair and not the other). Every
  other request body and every header of every request must hold neither
  secret access key. Responses are not checked: `CreateAccessKey` must
  return the new secret.
- Fixture: committing an AWS key id that is not the documentation example
  would trip secret scanners, and a key id ending in `EXAMPLE` is reported
  invalid without any call. The fixture
  `tests/fixtures/trufflehog_aws_e2e.ndjson` holds `@KEY_ID@` and
  `@SECRET@` placeholders; the test substitutes values built at runtime.
  The `rotate.yaml` is written by the test because it holds the server's
  port.

## Production changes

1. `providers.aws.endpoint_url: Option<ApiUrl>` in `src/config.rs`,
   documented in `docs/rotate.example.yaml`.
2. `src/providers.rs`: `aws_provider` applies `endpoint_url`; the Secrets
   Manager consumer gets a `with_endpoint_url` builder applied the same way
   (`aws_config` loader `endpoint_url`). The `test-providers` registries
   check `scenario::real_plugins()` and fall through to the real
   registration. The helpers lose their `cfg(not(test-providers))` gates.
3. Plan text bug: `revoke_action("aws")` said "deactivate the access key,
   then delete it". rotate never deletes a key (A3, A4); revoke only
   deactivates so rollback can reactivate it. New text: "deactivate the
   access key (not deleted; rollback can reactivate it)".

Any further bug the test finds is fixed minimally in this PR and listed in
the PR body. `src/apply.rs`, the executor and `src/state.rs` belong to
SHA-258 and are not touched unless a real bug forces it.

## Test design: `tests/e2e_aws.rs`

One `CallRecorder` (tests/common) per test with an `AwsModel` mounted on
`any()` ahead of the catch-all. `AwsModel` is an `Arc<Mutex<State>>`
implementing wiremock's `Respond`, so responses follow what earlier calls
changed:

- State: IAM user `deploy-bot` in account `000000000000`; access keys
  `(id, secret, status)`; Secrets Manager entries (`prod/app`, a JSON
  object holding `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and an
  unrelated field) with a version list and used request tokens; flags
  `deny_put` and the minted replacement's id and secret.
- STS `GetCallerIdentity` (query protocol, `Action=` in the form body):
  answers by the SigV4 signer. An active key gets the user's ARN; an
  inactive or unknown key gets `InvalidClientTokenId`.
- IAM `GetAccessKeyLastUsed`, `GetUser`, `ListAttachedUserPolicies`,
  `ListUserPolicies`, `ListGroupsForUser`, `ListAccessKeys`,
  `CreateAccessKey` (refuses with `LimitExceeded` past two keys) and
  `UpdateAccessKey`. Every IAM call must be signed by the operator key
  (from `AWS_ACCESS_KEY_ID` in the child's environment); any other signer
  gets `AccessDenied`, which proves decision D3.
- Secrets Manager `GetSecretValue`, `PutSecretValue` (JSON protocol,
  `x-amz-target`); `deny_put` answers `AccessDeniedException`.
- The recorder marks `Get*`, `List*` and `GetSecretValue` read-only, so
  `assert_no_mutations()` names any state-changing call.

Each child process runs with a cleared environment: the operator key pair,
`AWS_REGION`, `HOME`, `AWS_CONFIG_FILE` and `AWS_SHARED_CREDENTIALS_FILE`
inside the temp dir, IMDS disabled, `ROTATE_ACTOR`, `RUST_LOG=trace` and
the scenario. Nothing can reach real AWS or a developer's profile.

## Reuse for SHA-267

The model, runner and redaction check are written so SHA-267 can add the
GitHub Actions consumer: the runner takes extra env and config, and the
model's dispatcher falls through for requests it does not own.
