# Implementation plan: SHA-255 AWS IAM provider write side

Ticket edits applied with this plan (the first two are the user's decisions
of 2026-10-02, recorded as a comment on the ticket):

- **Scope uses operator credentials.** The leaked key signs exactly one
  call: the `sts:GetCallerIdentity` in `check_valid`. `describe_scope` moves
  to the operator's AWS credentials, through the same lazily loaded
  operator config the write side uses (`aws_config::defaults(
  BehaviorVersion::latest())`, held in a `tokio::sync::OnceCell`). This
  replaces the SHA-251 decision that the leaked key reads its own scope.
  Without operator credentials `describe_scope` fails with a message saying
  so; validity is unaffected and the plan shows `scope: unavailable: ...`.
  Building the provider still reads nothing and calls nothing.
- **MSRV raised.** `rust-version = "1.94.1"` (not `1.94`: the newest
  `aws-config` 1.12 and `aws-sdk-*` releases declare 1.94.1), the
  `.cargo/config.toml` `incompatible-rust-versions = "fallback"` file is
  deleted, and `Cargo.lock` is re-locked with `cargo update -p aws-config -p
  aws-sdk-iam -p aws-sdk-sts -p aws-sdk-secretsmanager` only, so other
  crates stay where they are. `cargo deny check` still bans the legacy
  `hyper` 0.14 / `rustls` 0.21 stack.
- The owner of the leaked key comes from `iam:GetAccessKeyLastUsed`
  (`UserName`) and its ARN from `iam:GetUser`, both with operator
  credentials. Every write method looks the user up again this way rather
  than trusting state, so a resumed run in a new process works.
- Two-key refusal surfaces in the plan: `describe_scope` calls
  `iam:ListAccessKeys` and adds `access keys: N of 2 used`; when both slots
  are taken it adds a line starting `warning: ` that names both key ids,
  their status and last-used date and says apply will refuse. The plan
  table prints scope lines that start with `warning: ` (a three-line
  change in `plan::render_table`); `--json` already carries every line.
  `create_replacement` checks again before creating and refuses with the
  same text and no `CreateAccessKey` call (AC2).
- `restore_ref` is the old key id, or `OLD:NEW` when this process created
  the replacement. Key ids never contain `:`. `restore("OLD:NEW")`
  activates `OLD`, then deactivates `NEW` (AC7). With a bare `OLD` (the
  revoke ran in a later process after an overlap wait) restore only
  reactivates the old key, leaving both keys working, which is the safe
  side; the rollback ticket can pass `OLD:NEW` from the state record
  (`replacement_ref`). `aws::restore_ref(old, new)` builds it.
- `revoke` reads `ListAccessKeys` first: key already `Inactive` is `Ok`
  with no `UpdateAccessKey` (AC6); key gone (deleted elsewhere) is `Ok`
  with `restore_ref: None`. A second revoke is therefore always `Ok`.
- `verify` retries `InvalidClientTokenId` / `SignatureDoesNotMatch` and
  retryable errors every 2 s for up to 15 s (new keys propagate slowly);
  an ARN mismatch fails at once naming both ARNs (AC4). The interval and
  budget are settable (`with_verify_timing`) so tests run in milliseconds.
- Write methods refuse anything that is not an `AKIA` key id (`ASIA`,
  malformed ids, bare tokens) with `Unsupported` and make no call.
- Operator clients have the SDK's retries disabled: a retried
  `CreateAccessKey` after a lost response could mint a second key.
- `providers.aws.region` is wired: `providers::registry_with(&ProvidersConfig)`
  passes it to `AwsProvider::with_region`; `registry()` stays as the
  default-config wrapper. `src/main.rs` switches to `registry_with` in the
  coordinator's integration PR, not here.

## Approach

`src/provider/aws.rs`:

- New fields: `operator: OnceCell<Result<SdkConfig, String>>`,
  `operator_credentials: Option<SharedCredentialsProvider>` (tests and
  embedders; `None` means the default chain), `replacements:
  Mutex<HashMap<old id, new id>>`, `verify_interval`, `verify_budget`.
- `operator()`: on first use loads `aws_config::defaults` with the resolved
  region (the SHA-251 chain, no IMDS region lookup), retries disabled, the
  SHA-251 timeouts, the endpoint URL when set and the injected credentials
  provider when set; then resolves credentials once. Failure is cached as
  the "no operator credentials" message (the SDK's own error text is
  dropped: it can name files and profiles).
- `owner(iam, key_id)`: `GetAccessKeyLastUsed` → user name and the
  last-used line. No user name → `Unsupported` (root keys: console only).
- `key_slots(iam, user)`: `ListAccessKeys` plus `GetAccessKeyLastUsed` per
  key → id, status, last used.
- `describe_scope`: owner, `GetUser` (ARN, account from the ARN), the three
  SHA-251 list reads (an `AccessDenied` stays a line, now "not visible to
  the operator credentials"), then key slots.
- `create_replacement`: owner, slots, refuse at two, `CreateAccessKey`;
  the response's `secret_access_key` `String` is moved (not copied) into a
  `SecretValue`. Remember old → new.
- `verify`: STS with the new pair (static credentials, as `check_valid`).
- `revoke` / `restore`: as in the ticket edits.

Rejected:

- Signing `describe_scope` with the leaked key (SHA-251's choice):
  overruled by the user (strict D3).
- Caching the owner from `describe_scope` in memory: `apply` may revoke in a
  later process (decision D2), so every write looks the owner up.
- Deactivating "the other key" in `restore` when only `OLD` is known:
  guesses at a key rotate may not have created.
- Failing `describe_scope` when both key slots are used: the operator would
  lose the scope lines exactly when they matter, and apply would report a
  misleading "identity unknown".
- `rust-version = "1.94"`: resolves `aws-config` 1.8.18, not the latest.

## Secret handling

New secret: moved from the SDK's `AccessKey.secret_access_key` `String`
into `SecretValue` (zeroized, registered with the redaction layer). The
SDK marks `CreateAccessKey` output sensitive and never logs its body; its
`Debug` redacts the field. The response bytes in the SDK's buffers are
outside rotate's control (noted, as for every HTTP client). Error text,
scope lines and refs are built from operation names, sanitised codes, key
ids and ARNs only.

## Risks

- `Cargo.lock`: SHA-256 and SHA-257 may touch it; take main's lock,
  re-run the `cargo update -p aws-*` line.
- `src/providers.rs`: the coordinator's PR edits `main.rs` only; after it
  calls `registry_with`, `registry()` has no caller in the binary
  (`#[allow(dead_code)]` keeps clippy quiet).
- `src/plan.rs`: SHA-257 (manual mode) changes `replacement_text`; the
  warning line is a separate three-line hunk.
- A leaked key whose owner is in another account: `GetAccessKeyLastUsed`
  is denied, so scope is unavailable and apply skips it.

## Out of scope

Deleting keys (Later, SHA-195), `ASIA` credentials, Secrets Manager,
rollback wiring of `restore_ref` into the state record.
