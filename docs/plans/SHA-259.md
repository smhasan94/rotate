# Implementation plan: SHA-259 `rotate rollback`

Ticket edits applied with this plan:

- Revoking the replacement needs a provider call that takes a reference,
  not a credential: rotate never stores the replacement value, so
  `Provider::revoke(&Credential)` cannot be used. The trait gains
  `revoke_replacement(&self, replacement_ref: &str) -> Result<(),
  ProviderError>`, mutating, with a default that returns `Unsupported`, so
  providers that do not override it (SHA-260, SHA-261, SHA-262) compile
  unchanged. The recorder shows it as `revoke_replacement` with the ref;
  that is the "provider `revoke` of the replacement ref" of AC1 and T7.
  The mock overrides it; so does the AWS provider (deactivate the key by
  id, a few lines next to `restore`), because without it an AWS rollback
  would always end with a "revoke it by hand" warning. Real-provider tests
  stay with SHA-264 apart from one wiremock case.
- A `replacement_ref` of `manual` (SHA-257) has no provider handle: no
  call, and the summary says to revoke the pasted replacement by hand.
  `Unsupported` from `revoke_replacement` is the same warning, not a
  failure.
- Provider `restore` runs only when the old secret was revoked by apply and
  the provider gave a restore handle. Apply now records that handle
  (`Revoked.restore_ref`) in the state file; it was dropped before. A
  rotation that never reached revoke (`created`, `consumers_updated`,
  `verified`, `pending_revoke`, `failed` before revoke) skips the provider
  step: the old secret is still valid. A `revoked` rotation with no handle
  is reported "unsupported: old secret cannot be reactivated, consumers
  will be restored only".
- The `needs_rollback` step named in the scope does not exist in the state
  schema and nothing sets it; it is not added. Rollback accepts a rotation
  at any step except `rolled_back`. A rotation with nothing to undo (no
  replacement, no updated consumer, old secret not revoked: a bare
  `planned` record) is reported "nothing to roll back" and left as is.
- Only consumers with status `updated` are restored (AC6). `failed` and
  `skipped` ones are listed as left as they are.
- Order, as in the ticket: provider `restore`, consumer `restore` for each
  updated consumer, `revoke_replacement`. Any error stops the rollback at
  that action: the replacement is never revoked while a consumer may still
  point at it, and consumers are never restored when reactivating the old
  secret failed with an error (as opposed to `Unsupported`). The rotation
  keeps its step, its rollback progress is saved, and a re-run continues
  from the first action not done (idempotent: no action that succeeded is
  repeated). Exit 1.
- Exit codes: 0 when every selected rotation is `rolled_back` (warnings
  included) or nothing needed rolling back; 1 when an action failed; 2 for
  usage errors, including "no rotation found for fingerprint <fp>" (AC4)
  and a confirmation mismatch (AC5). A rotation already `rolled_back` is
  reported and makes no call (re-running a finished rollback is a no-op).
- Flags: `rotate rollback [REPORT | --stdin] [--rotation <id>] [--confirm
  <id>]...`. `--rotation` narrows the match to one rotation; `--confirm`
  replaces the typed id, as for apply.

## State and audit schema (for SHA-258 and SHA-263)

State stays version 1; every new field is optional and absent in older
files.

- `Rotation.restore_ref: Option<String>`: the handle `revoke` returned for
  the old secret, written by apply when it revokes. Provider handle only
  (an AWS key id pair), never a value.
- `Rotation.rollback: Option<RollbackProgress>`, absent until a rollback
  starts. `RollbackProgress { restore_done: bool, revoke_done: bool }`:
  whether the provider restore step and the replacement revoke step are
  finished (done includes "unsupported" and "nothing to do"). A rotation
  with `rollback` present and step not `rolled_back` is a rollback in
  progress: apply (and the SHA-258 resume) must not continue it; it is
  ineligible with "a rollback is in progress; finish it with rotate
  rollback".
- `ConsumerState.holds: Option<Holds>` (`secret`, `key_id`, `key_pair`):
  which part of the credential the consumer stores, written by apply.
  Consumer `restore` needs it (the Actions key id secret must get the key
  id, not the secret). A consumer without it cannot be restored
  automatically; rollback fails at that consumer and names it.
- `ConsumerStatus::Restored`: set by rollback per consumer once restored.
- Audit: entries with step `rollback` gain an optional `action`
  (`restore_old`, `restore_consumer`, `revoke_replacement`); consumer
  entries carry the consumer ref. Audit version stays 1.

## Approach

`src/rollback.rs` (new):

- `select(rotations, inputs, rotation_filter) -> Result<Vec<Selected>,
  SelectError>`: inputs are the deduplicated `(fingerprint, credential)`
  pairs from the report or stdin (a finding with an access key id wins, as
  in assess). Pure: no provider call, no identification call.
  `SelectError::NoMatch` lists the fingerprints ("no rotation found for
  fingerprint sha256:..."); `--rotation` naming a rotation that matches no
  input is the same error.
- `RollbackPlan::of(&Rotation)`: old-secret action (`Restore(ref)`,
  `Unsupported`, `NotRevoked`), consumers to restore, consumers left,
  replacement action (`Revoke(ref)`, `Manual`, `None`), each minus what the
  saved progress says is done. `render_plan` prints it per rotation with
  the header "Rollback plan: N rotation(s). Nothing has been changed yet."
- `RollbackExecutor::run(&Rotation, &Credential) -> RollbackOutcome`:
  state save then audit entry after each action, as apply does.
- `render_summary` and `RollbackStatus` for the exit code. Warnings: "the
  old secret was not reactivated: <provider> cannot restore it; it stays
  revoked and the restored consumers hold a revoked secret", and "revoke
  the replacement <ref> by hand".

`src/apply.rs`: record `restore_ref` and `holds`; a rotation with rollback
progress is ineligible.

`src/state.rs`, `src/audit.rs`, `src/consumer/mod.rs` (serde for `Holds`),
`src/provider/mod.rs` (trait method, `MUTATING`), `src/provider/mock.rs`,
`src/provider/aws.rs`, `src/calls.rs` (`Call.reference`: the ref or
restore handle a call targeted, so tests can assert which consumer was
restored), `src/consumer/mock.rs`.

`src/cli.rs`: `RollbackArgs { input, rotation, confirm }`. `src/main.rs`:
read input, open the state store (lock), select, print the plan, confirm,
open the audit log, run, print the summary.

## Secret handling

The only value rollback holds is the old secret from the report or stdin:
in a `SecretValue`, registered with the redactor for the whole command,
used only as the argument of consumer `restore`. Matching is by
fingerprint. Errors go through `RedactedText`. The plan, the summary, the
state file and the audit log hold refs and fingerprints only. T8 runs apply
then rollback with canary old values (and greps for the mock's replacement
value too) over stdout, stderr with `-vvv`, the audit log, the state file
and the call log.

## Risks

- SHA-260 implements `Provider` in parallel; the new method has a default,
  so it compiles without changes there. No registry edits.
- SHA-258 builds on the state fields above; they are optional and
  documented here and in `src/state.rs`.

## Out of scope

Rollback with a missing state file (unsupported; documented), real
providers beyond the AWS revoke-by-id, `rotate status` (SHA-263).
