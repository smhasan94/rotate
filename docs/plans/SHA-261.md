# Implementation plan: SHA-261 npm token provider

Ticket edits applied with this plan, from the npm Registry API reference
(api-docs.npmjs.com, read 2026-10-02) and the npm CLI source
(`lib/commands/token.js`, `lib/utils/get-identity.js`):

- **Token formats.** npm permanently revoked every classic (legacy) token on
  2025-12-09. Live tokens are granular access tokens, or the two-hour
  session tokens `npm login` now issues; both are `npm_` plus 36
  alphanumerics. `identify` matches that shape (High with a detector hint
  `NpmToken`, `NpmTokenV2` or `npm-access-token`, Medium without); an
  `npm_` value of another alphanumeric length is Low and only with a hint.
  Legacy UUID-format tokens are not identified: none can still be valid.
- **The token list no longer exposes a hash key.** `GET /-/npm/v1/tokens`
  returns `key` as a token id (a UUID for current tokens) and `token`
  redacted as the first 8 and last 4 characters (`npm_aBcD...7890`), not the
  first 6. The sha512 hex `key` of the ticket is npm's old scheme. rotate
  matches an entry when its `key` equals the sha512 hex of the leaked token
  (old scheme, AC4 as written; known-answer test) or when the redacted
  `token` has a prefix of at least 8 and a suffix of at least 4 characters
  and the leaked token starts and ends with them (current scheme). Two
  entries matching by redaction is ambiguous and treated as no match.
- **Fields.** Current entries have `name`, `expiry`, `readonly`,
  `bypass_2fa`, `cidr`, `permissions`, `scopes`, `created`, `revoked`; old
  ones had `cidr_whitelist` and `automation`. Both are read. Type is
  `granular` for current entries and `publish`, `automation` or `read-only`
  (legacy) for old-scheme ones.
- **Listing needs a session token.** The reference accepts only an
  `npm login` session token on `GET /-/npm/v1/tokens`. The operator token
  comes from `ROTATE_NPM_TOKEN`, then `NPM_TOKEN` (FR24). With no operator
  token, or one npm refuses, `describe_scope` still succeeds: the scope says
  "token not visible to operator account" with the reason, and the
  username comes from `whoami` with the leaked token (read-only, as the
  GitHub provider does). `check_valid`'s result stands (AC5).
- **Revoke deletes by the listed id, never by value in the URL.** `DELETE
  /-/npm/v1/tokens/token/{token}` takes a token id or a full token value.
  rotate never puts the value in a URL (it would reach proxy and server
  logs), so `revoke` lists the operator's tokens, takes the matching
  entry's `key` (for an old-scheme entry that is the derived sha512 key,
  AC6) and deletes that, signed with the operator token. 204 or 404 is Ok
  (AC7); an entry already marked `revoked` is Ok with no DELETE. When the
  list has no match, revoke checks `whoami` with the leaked token: 401 means
  it is already gone (Ok, so revoke is idempotent); otherwise it fails
  "token not visible to operator account; delete it at
  <web>/settings/<user>/tokens". Revoke is skipped with an error, never
  sent, when the operator token is the leaked token (decision D3).
- **2FA.** Deleting a token may need a one-time password in `npm-otp`.
  OTP handling stays out of scope: a 401 carrying a `www-authenticate: OTP`
  challenge or an OTP message fails revoke with "npm requires a one-time
  password to delete tokens for this account; delete it at <url>". A 403
  from a `bypass_2fa` granular operator token fails naming that cause.
  Revoke is the last step, so either failure leaves consumers on the new
  token and the old one valid until deleted by hand.
- **`revoke_replacement`.** rotate never holds a pasted replacement's value
  and records its ref as `manual`, which rollback handles without a
  provider call. The provider overrides `revoke_replacement` for a ref that
  is an npm token id (a UUID or a 128-hex key): it deletes that id with the
  operator token, 404 being Ok. Any other ref, `manual` included, is
  `Unsupported` with no call. Nothing records a token id today; this is
  ready for when apply does.
- `restore` is always `Unsupported`: a deleted token cannot come back.

## Approach

`src/provider/npm.rs` (new), `NpmProvider::new(registry_url)` plus
`with_operator_token(Option<SecretValue>)` for tests; release builds read
the environment on first use. A small private client: base URL, lazy
reqwest client, sensitive `Authorization: Bearer` headers built in zeroized
memory, errors with the status and npm's capped `error` or `message`, never
a request URL or body.

- `identify`: `Credential::Token` only, shape as above.
- `check_valid`: `GET /-/whoami` signed with the leaked token: 200 Valid,
  401 Invalid, 429 rate limited, 5xx transient, other statuses Unknown.
- `describe_scope`: `whoami` (identity is the username), then the paged
  token list with the operator token (`?page=N&perPage=100`, following
  `urls.next` only under the registry URL, at most 50 pages). Lines:
  `user:`, then for a match `type:`, `name:`, `access:` (read-only or
  read-write), `bypass_2fa:`, `cidr:` (or `any`), `permissions:`,
  `scopes:`, `created:`, `expires:`; otherwise `token not visible to
  operator account (<reason>)`.
- `replacement_mode` Manual; `create_replacement` Unsupported, no call.
  `manual_instructions` names the granular token page
  (`https://www.npmjs.com/settings/<user>/tokens/granular-access-tokens/new`
  for the public registry) or `npm token create`, and copies the
  permissions, scopes, cidr and access lines from the scope.
- `verify`: `whoami` signed with the replacement; a different username
  fails naming both (AC8).
- `revoke`, `revoke_replacement`, `restore` as above.

`src/providers.rs`: register `NpmProvider::new(config.npm.registry)` in
release builds, with a test.

## Secret handling

The leaked token leaves rotate only in the `Authorization` header of `GET
/-/whoami` (check, scope, and revoke's already-gone check). The operator
token only signs the token list and the DELETE. The replacement only signs
`GET /-/whoami` in verify. No token value is ever in a URL or body. The
sha512 key is a one-way digest; scope lines hold the username, token name,
type, flags, cidr ranges, permissions, scopes and dates. Errors never echo
a value.

## Test mapping

Unit tests in `src/provider/npm.rs`; integration tests in
`tests/npm_provider.rs` against `CallRecorder` (DELETE is mutating; every
other npm call is a GET).

- T1 (AC1): `identify_npm_tokens_not_openai` (unit).
- T2 (AC2): `check_valid_whoami_alice` (bearer is the leaked token, only on
  the read-only whoami).

- T8 (AC8): `verify_other_username_names_both`.

- T10 (AC2, AC6): `tokens_never_in_output_logs_audit_or_state`: assess,

- T11 (AC1 to AC9): `conformance_manual_mode` (`provider_suite`).
- Plan safety: `plan_makes_no_state_changing_calls` (no DELETE).
- Extras: OTP and bypass-2FA errors, operator token equal to the leaked

- Live (`#[ignore]`, `live_` prefix, `live_guard!`):

  `live_npm_revoke` (`ROTATE_LIVE_NPM_REVOKE_TOKEN`, a throwaway token,
  with `ROTATE_NPM_TOKEN` a session token of the same account).

## Risks

- SHA-258 edits `src/apply.rs` and `src/state.rs`, SHA-262 adds the OpenAI
  provider; this ticket touches neither file and only adds a line next to
  theirs in `src/provider/mod.rs` and `src/providers.rs`.
- npm's API reference and its live behaviour may differ (the `whoami`
  endpoint is not in the reference at all; it is what the npm CLI calls).
  The gated live tests catch drift.
- Most accounts have 2FA, so automatic revoke often stops at the OTP
  challenge. The failure is safe and names the page; OTP support can follow
  as its own ticket.

## Out of scope

Creating tokens (password plus OTP), OTP handling, changing package publish
settings, legacy UUID tokens.
