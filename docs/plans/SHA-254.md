# Implementation plan: SHA-254 `rotate apply` happy path

Ticket edits applied with this plan:

- Confirmation. `rotate apply` re-plans from the same input, prints the plan
  table, then asks once per rotation `Type the rotation id <id> to
  continue:`. The prompt goes to stderr (through the console) and the answer
  is read from `/dev/tty`, never stdin, so `--stdin` keeps working. Every
  answer is collected before the first mutating call; any mismatch exits 2
  with "confirmation did not match" and nothing is changed.
- `--confirm <id>` may be repeated. Only the confirmed rotations run; an id
  that is not in the plan exits 2 before any mutating call. `--all` asks one
  prompt listing every id; the operator types `all`. `--all` and `--confirm`
  conflict (a CI caller lists ids, US11).
- No terminal and no `--confirm`: exit 2 with "no terminal to confirm on;
  pass --confirm <rotation-id>".
- Apply opens the state store (lock) before assessment, as plan does, and
  the audit log after confirmation and before the first mutating call. An
  unusable audit log exits 2 (or 1 for plain I/O) with zero mutating calls.
- Audit: one `plan` entry (outcome ok) per confirmed rotation, then one per
  step. `create`, `update`, `verify` and `revoke` carry the replacement
  fingerprint.
- Overlap window greater than 0: after `verified` the rotation is recorded
  at `pending_revoke` with `revoke_not_before`, nothing is revoked, and apply
  exits 3 saying when the revoke is due. Finishing it is SHA-258.
- Not handled yet, each skipped with a message and no call: manual
  replacement mode ("manual replacement is not supported yet"; SHA-257), a
  rotation already past `planned` (resume; SHA-258), a rotation whose scope
  (owner identity) is unknown, because verify needs it. These exit 2 when
  nothing failed (the contract's "not implemented yet").
- The non-negotiable applies now even though SHA-256 owns the full rules:
  an error in create, update or verify marks the rotation `failed` in state
  and audit (redacted error), stops that rotation, never calls revoke, and
  apply exits 1. A consumer that cannot be updated (or a lookup error) is
  not updated, is recorded `skipped`, and the rotation stops at `verified`
  without revoking: "N consumers not updated; revoke skipped". A revoke
  error marks the rotation `failed` and says the replacement is live. Other
  rotations in the run continue. `--force` and the per-consumer messages
  are SHA-256.
- `apply --json` exits 2 ("not supported yet") before reading input.
- Exit: 1 if any rotation failed or stopped before revoke; else 3 if any is
  pending revoke; else 2 if any was skipped as unsupported; else 0.

## Approach

`src/apply.rs`, library code with no printing:

- `pub trait Prompt { fn read_line(&mut self) -> Result<String, PromptError>; }`
  with `PromptError::NoTerminal` and `Io`. The binary passes `TtyPrompt`
  (`/dev/tty`); tests pass `ScriptedPrompt`.
- `pub fn confirm(all_ids: &[&str], askable: &[&str], request: &Confirmation, prompt: &mut dyn Prompt, out: &mut dyn Write) -> Result<Vec<String>, ConfirmError>`
  where `Confirmation` is `Ids(Vec<String>)`, `Interactive` or `All`.
  Returns the confirmed ids; `ConfirmError` (mismatch, unknown id, no
  terminal) maps to exit 2.
- `pub fn eligibility(rotation: &PlannedRotation) -> Result<(), Ineligible>`:
  manual mode, step past `planned`, missing scope. Ineligible rotations are
  never prompted for.
- `pub struct Executor<'a> { providers, consumers, store: &mut StateStore, audit: &mut AuditLog, clock: fn() -> OffsetDateTime }`
  and `pub async fn run(&mut self, rotation: &PlannedRotation) -> Outcome`.
  Steps, each persisting state then appending audit:
  `plan` audit → `create_replacement` (`created`, `replacement_ref`,
  `replacement_fingerprint`) → `update` per updatable consumer (consumer
  `updated`; not-updatable `skipped`) → `consumers_updated` → `verify(new,
  scope.identity)` → `verified` → `revoke_gate` → `revoke` → `revoked`.
- `Outcome { rotation_id, provider, fingerprint, replacement_fingerprint, consumers, result: RunResult }`
  where `RunResult` is `Revoked`, `PendingRevoke { not_before }`,
  `Held { reason }` (stopped at verified by the gate), `Failed { step, error }`
  or `Skipped(Ineligible)`. `run_status` maps a run to its exit class. The binary prints a summary table from these.
- `pub fn revoke_gate(&PlannedRotation, &[ConsumerState], verified_at) -> Gate`: `Revoke`, `Hold(reason)`,
  `Wait(not_before)`. It is the single place SHA-256 adds `--force` and
  SHA-258 adds the clock and `--wait`.
- The replacement credential lives in a local of `run` and is dropped
  (zeroized) when the rotation ends. It is never in `Outcome`.

`src/main.rs`: `apply()` mirrors `plan()`: open the store, assess, build,
assign ids, print the table, classify, confirm, open the audit log, run the
executor per confirmed rotation, print the summary. Inputs stay alive until
every message is printed.

`src/cli.rs`: `apply` gets its own `ApplyArgs { input: InputArgs, confirm: Vec<String>, all: bool }`.

`src/providers.rs` (feature `test-providers` only): the scenario gains
`prompt` (`{"answers": [...]}`, `"panic"` or `"no_tty"`), per-provider
`fail` (method to error text), per-consumer `fail` (method to error text)
and `consumer_state` (a path the binary writes each mock consumer's held
fingerprint to on exit). `providers::test_prompt()` returns the scripted
prompt when the scenario sets one.

Rejected: a pseudo-terminal crate for T1 (a new dependency for one test;
the injectable prompt is what the ticket offers as the alternative);
reading the answer from stdin (breaks `--stdin`); prompting only once for
many rotations without `--all` (one typed id per rotation is A8);
refusing an overlap window up front (D2 says record and exit 3, and the
state is usable); stopping the whole run on the first failed rotation (the
per-rotation outcome is what SHA-256 AC5 needs anyway).

## Secret handling

The replacement is a `SecretValue`, so it is registered with the redactor
while alive and zeroized on drop. State and audit take `Fingerprint`s and
`replacement_ref` (a provider-side id, never a value); errors go through
`AuditEvent::with_error` (redacted) and the console. The prompt answer is a
rotation id, not a secret. The scripted prompt and exported consumer state
hold ids and fingerprints only.

## Test mapping

CLI tests in `tests/apply_cli.rs` under `test-providers`; unit tests in
`src/apply.rs` with `MockProvider` and `MockConsumer`.

- T1 (AC1): `typed_mismatch_exits_2_without_mutations`; unit `confirm_rejects_mismatch`.
- T2 (AC2): `typed_id_runs_steps_in_order` asserts the call order exactly;
  unit `executor_runs_create_update_verify_revoke`.
- T3 (AC3): `confirm_flag_skips_prompt` (scripted prompt panics if called).
- T4 (AC4): `wrong_confirm_id_exits_2_without_mutations`.
- T5 (AC5): `audit_has_every_step_with_fingerprints`.
- T6 (AC6): `state_ends_revoked_with_consumers_updated`.
- T7 (AC7): `consumer_holds_replacement_fingerprint` (exported consumer
  state); unit `executor_runs_create_update_verify_revoke` checks
  `MockConsumer::current`.
- T8 (AC2, AC5, AC6): `apply_never_leaks_old_or_new_value`: `-vvv`, canary
  old value and the mock's replacement value absent from stdout, stderr
  (tracing), audit, state and call log.
- Safety extras: `revoke_is_last_mutating_call`; `injected_failure_never_revokes`
  (create, update, verify failures: no revoke, state `failed`, exit 1);
  `not_updatable_consumer_holds_before_revoke`; `manual_mode_is_skipped`;
  `no_terminal_without_confirm_exits_2`; `overlap_records_pending_revoke_exit_3`.

## Sequence

1. CLI args and `src/apply.rs` (confirm, eligibility, executor) with unit tests.
2. `main.rs` wiring and summary output.
3. Scenario extensions, CLI tests, smoke check, README; all checks; PR.

## Risks

- `src/providers.rs` gets one registration line each from SHA-251, SHA-252
  and SHA-253; this ticket edits only the feature-gated scenario module.
- `/dev/tty` behaviour differs in CI (no terminal): tests always script the
  prompt; the no-terminal path is its own test.

## Out of scope

`--force` and per-consumer failure messages (SHA-256), manual mode
(SHA-257), resume, `--wait` and finishing a pending revoke (SHA-258),
rollback (SHA-259), status (SHA-263).
