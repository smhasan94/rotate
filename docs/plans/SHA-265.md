# Implementation plan: SHA-265 leakage audit test

One test file, `tests/leakage.rs`, that runs the binary through every
command and mode with distinctive canaries and then searches everything the
process could have written. It builds on the existing harnesses rather than
adding a new one.

## Canaries

Each test generates fresh canaries: a 32-char core from `[A-Za-z0-9/+]`
(the `/` and `+` make the URL-encoded form differ from the raw one), from a
seed of the clock, the process id and a counter.

- Mock runs (`test-providers` scenario, npm mock): the old secret is
  `npm_` + 28 canary chars (32 in all; the mock identifies by prefix), and
  the manual-mode pasted value is a 32-char canary. The mock mints its own
  automatic replacement (`npm_npm-replacement-<n>`); that value is searched
  for too, labelled as the mock replacement.
- Real-plugin runs (`tests/e2e` harness, AWS IAM + Secrets Manager + GitHub
  Actions against wiremock): an AWS secret access key must be 40 chars, so
  the old and replacement secrets are an 8-char prefix plus a 32-char
  canary core; the operator's AWS secret and the operator's GitHub token
  are canaries too. The sweep searches for the full values and for each
  core on its own. `E2e` gains a constructor that takes these values
  (`E2e::start_with_github_values`); the existing constructors keep their
  fixed values. `E2e::run` also points `TMPDIR` at a directory inside the
  test's temp dir so it can be swept.

## The sweep

`Sweep` holds every needle: for each canary, the raw value, its
URL-encoding, lower and upper hex, and standard and URL-safe base64 at all
three byte alignments (the part of the encoding that does not depend on the
neighbouring bytes, so a canary embedded anywhere in a base64 blob is still
found). One `regex::bytes::Regex` alternation of the escaped needles scans
each buffer (Aho-Corasick underneath). A hit records the place (stream
name or file path), the byte offset, the canary's label and the encoding.
The failure message lists hits by place, offset, label and encoding, never
the bytes. File names are checked as well as file contents.

After each run the sweep covers stdout, stderr (which holds the trace log:
every run is `-vvv` with `RUST_LOG=trace` unless it tests a lower level),
every file under the working directory and under the run's `TMPDIR`.
Inputs the test wrote itself (the report, the scenario, a replacement
file) live outside the swept directories or are listed as inputs and
skipped by exact path. Directories are walked without following symlinks
and files are read in parallel with scoped threads.

## Runs (T1, AC1)

Mock (`test-providers`), each sequence in a fresh directory:

1. Automatic: `plan` (human, `--json`, `-v` without `RUST_LOG`), `apply
   --confirm` with `--overlap 0s`, `status`, `status --json`, `status
   --all`, then `rollback --confirm` with the consumers holding the
   replacement, then `status --all --json`. `apply --json` and `rollback
   --json` (usage errors) too.
2. Manual: the pasted value through the scripted prompt, through
   `--replacement-from-env` and through `--replacement-file` (the file
   lives in an input directory outside the swept tree).
3. Failures at each step: `find` on a consumer, `create_replacement`,
   consumer `update`, `verify`, `revoke`; each failure text contains the
   old canary, as an upstream that echoes the secret would; plus a
   rollback whose provider `restore` is unsupported.
4. Panic and error paths: `__test-console` (`test-commands`) in `out`,
   `error`, `panic` and `json` modes with the canary on stdin, and an
   `apply` whose scenario prompt panics after the plan holds the secrets.

Real plugins (`tests/e2e` harness with GitHub): `plan` (human and
`--json`), `apply --overlap 0s`, `status --all --json`, a second
rotation's `apply` with the Actions `PUT` denied (stops before revoke),
then `rollback`. `assert_requests_clean` is reused for the requests.

## Planted leak (T2, AC2)

A new feature `leak-canary-test` (never in releases; CI's
`--all-features` turns it on) adds a hook in `main.rs`: when
`ROTATE_TEST_PLANT_LEAK` is `stdout`, `stderr` or a relative file name,
the binary writes the first input secret, raw, once to that place, after
reading its input. No other source file changes.

T2 runs the leakage test binary itself (`std::env::current_exe()`) as a
subprocess, filtered to a child test that does nothing unless
`ROTATE_LEAK_CHILD` names a target. The child runs `plan --stdin` with the
hook on and sweeps. The parent asserts, for each of the three targets, that
the child failed, that its output names the place and a byte offset, and
that the sweep finds no canary in the child's own output.

## File modes (T3, AC3)

After a full apply and rollback sequence (mock) and after the real-plugin
apply, every file under `.rotate/` (state, audit log, lock) must be 0600
and the directory 0700. Every T1 sequence also checks this after each run.

## Speed (T4, AC4)

A temp directory of 1,000 files of 1 MiB of printable pseudo-random bytes
(one file with a canary planted at a known offset). The sweep must finish
in under 30 s and report exactly that one hit with its file and offset.
If debug builds of `regex` are too slow for that, the test profile
optimises the `regex-automata`, `aho-corasick` and `memchr` packages.

## Outcome

- Failure runs cover provider `check_valid`, `describe_scope`,
  `create_replacement`, `verify` (a foreign pasted value) and `revoke`,
  consumer `find`, `update` and `restore`.
- Real leak found: when `check_valid` or `describe_scope` failed with text
  that echoed the secret, the plan printed that text after the skipped
  finding's credential had dropped, so the redactor no longer knew the
  value and the secret reached stdout. `assess` now redacts the error text
  while the credential is alive; a unit test in `assess.rs` covers it.
- The sweep of 1,000 x 1 MiB runs in a few seconds in a debug build; no
  profile change was needed.

## Out of scope

Memory inspection (later mlock ticket); live providers.
