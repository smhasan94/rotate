# Implementation plan: SHA-250 Planner and `rotate plan`

Ticket edits applied with this plan:

- Exit codes follow the existing CLI contract (`src/exit.rs`, SHA-214):
  input and config errors, and a state file that is locked, too new or
  corrupt, exit 2; a plain I/O error writing the state file exits 1.
  Blockers, skipped rows and consumer lookup errors still exit 0.
- Skipped rows cover every secret that is not rotated: `invalid`,
  `unsupported`, `not rotatable` (canary, gitleaks key id only) and
  `unknown` (the validity check failed). Each has a reason word and an
  optional detail. A secret whose validity is unknown is not planned: rotate
  never rotates what it could not check. Re-run `plan` once the check works.
- A consumer whose `find` fails is listed under the rotation as a lookup
  error and adds a blocker: apply will refuse to revoke without `--force`,
  because not every consumer is known to be updated (NFR5).
- Rotation id: `rot-` plus 8 hex characters. Plan reuses the id of any
  rotation in the state file for the same provider and fingerprint that is
  not finished (`revoked` or `rolled_back`); otherwise it makes a new one.
  A rotation already past `planned` is left untouched and its step is shown,
  so a second `plan` never rewinds an `apply` in progress.
- If another rotate process holds the state lock, plan fails at once with
  the store's message and exit 2, before any provider call.
- The D4 name convention and the `rotate.yaml` mappings are merged by the
  planner (`plan::consumer_names`) into `SecretRef::names`.
- The audit log is not written by `plan` (it changes nothing). T8 checks the
  audit path is absent or holds no value.

## Approach

`src/plan.rs`, library code with no printing:

- `pub struct Plan { overlap_window: Overlap, rotations: Vec<PlannedRotation>, skipped: Vec<Skipped> }`.
- `pub struct PlannedRotation { rotation_id, provider: &'static str, fingerprint, credential: Credential, scope: Option<Scope>, scope_error, replacement_mode: ReplacementMode, consumers: Vec<PlannedConsumer>, lookup_errors: Vec<LookupError>, revoke_action: &'static str, overlap_window, blockers: Vec<String>, step: Step, sources }`. It holds the credential for apply (SHA-254), so it has no `Serialize`.
- `pub struct PlannedConsumer { consumer: &'static str, consumer_match: ConsumerMatch }`.
- `pub struct Skipped { fingerprint, provider: Option<&'static str>, reason: &'static str, detail: Option<String>, sources }`.
- `pub async fn build(assessed: Vec<Assessed>, consumers: &ConsumerRegistry, providers: &ProviderRegistry, config: &Config) -> Plan`: valid secrets become rotations with `SecretRef` names from `consumer_names` and `ConsumerRegistry::find_all`; everything else is skipped with no consumer call. Only `find` is called on consumers, and assessment calls only `check_valid` and `describe_scope`.
- `pub fn assign_ids(plan: &mut Plan, store: &mut StateStore) -> Result<(), StateError>`: reuse or mint ids, upsert new and `planned` rotations at step `planned`, copy the stored step onto the plan.
- `pub fn consumer_names(provider, &ConsumersConfig) -> ConsumerNames { secret, key_id }` with the D4 table: aws `AWS_SECRET_ACCESS_KEY` / key id `AWS_ACCESS_KEY_ID`; github `GITHUB_TOKEN`, `GH_TOKEN`, `GH_PAT`; npm `NPM_TOKEN`; openai `OPENAI_API_KEY`; plus `secret_names` / `key_id_names` from config, deduped in order. SHA-253 uses the same function to tell which names hold the key id.
- Revoke wording per provider: aws "deactivate the access key, then delete it", github "revoke the token (credential revocation API)", npm "delete the access token", openai "delete the API key".
- Replacement wording: automatic "create a new <provider> credential for <identity>"; manual "manual: you will be asked to paste the new secret".
- Blockers: one line per not-updatable consumer count and per lookup error: "1 consumer cannot be updated; apply will refuse to revoke without --force"; "no consumers found" is a note, not a blocker.
- `pub fn render_table(&Plan) -> String`: one block per rotation (id, provider, fingerprint, identity, replacement, consumers with match method and updatable or reason, revoke, overlap, blockers), then a "Skipped" table.
- `pub fn render_json(&Plan) -> String`: `{"version": 1, "overlap_window", "rotations": [...], "skipped": [...]}` through view structs; `docs/plan-schema.json` (draft 2020-12, `additionalProperties: false`) describes it.

`src/main.rs` `plan()`: open the state store first (fail fast on the lock),
assess, build, assign ids, render, one print site. SHA-246's console takes
over the print when it lands.

Test scenarios. `src/providers.rs` gains `consumers()` next to `registry()`.
Without the `test-providers` feature both registries stay empty of mocks and
nothing below compiles in. With it, `ROTATE_TEST_SCENARIO` names a JSON file
that sets per-provider `validity` and `mode`, and mock consumers with matches
by fingerprint (`ref`, `method`, `holds`, `not_updatable`), and a
`call_log` path. Every mock shares one `CallLog`, which the binary writes to
`call_log` (target, method, mutating, fingerprint per line) before exiting,
so CLI tests can assert zero mutating calls across providers and consumers.

Rejected: a scenario section in `rotate.yaml` (`deny_unknown_fields` would
need a feature-gated field in the release config type); hard-coded named
scenarios (tests need fingerprints of runtime values); asserting mutations
only in library tests (AC2 is about the command).

Schema validation: `jsonschema` as a dev-dependency with default features
off (no HTTP resolver). `cargo deny check` passes with it.

- `src/plan.rs` (new), `src/lib.rs` (`pub mod plan;`).
- `src/main.rs`: `plan()` path only.
- `src/providers.rs`: `consumers()`, scenario loading and call-log export under the feature.

- `tests/plan_cli.rs` (new); `tests/assess_cli.rs` updated for the new JSON shape.

## Secret handling

`PlannedRotation` holds the credential and has no `Serialize`; JSON goes
through views with fingerprints, consumer refs and reasons only. Consumer
refs and `NotUpdatable` reasons come from plugins, which must keep them
value-free (SHA-222). The state file stores fingerprints only (SHA-220).
The call log written for tests holds fingerprints only.

## Test mapping

CLI tests in `tests/plan_cli.rs` under `#[cfg(feature = "test-providers")]`,
plus unit tests in `src/plan.rs`.

- T1 (AC1): `plan_lists_replacement_consumers_revoke_and_overlap`; unit `build_valid_secret_with_two_matches`.
- T2 (AC2): `plan_makes_no_mutating_calls` reads the exported call log; unit tests end with `log.assert_no_mutations()`.
- T3 (AC3): `not_updatable_consumer_is_a_blocker_exit_0`.
- T4 (AC4): `invalid_secret_is_skipped_without_lookup` (no `find` call for its fingerprint).
- T5 (AC5): `json_validates_against_schema_and_has_no_value`.
- T6 (AC6): `rotation_ids_stable_across_runs`; unit `assign_ids_reuses_open_rotation` and `assign_ids_keeps_later_step`.
- T7 (AC7): `manual_mode_replacement_wording`.
- T8 (AC1, AC5): `plan_never_leaks_canary`: table and `--json` with `-vvv`; canary absent from stdout, stderr (tracing), state file and audit path.
- Extras: `locked_state_file_exits_2`, `consumer_lookup_error_is_a_blocker`, `consumer_names_merges_convention_and_config`.

## Sequence

1. `consumer_names`, `build`, renderers, unit tests.
2. `assign_ids` with the state store; unit tests.
3. Scenario and consumer registry in `src/providers.rs`; `main.rs` wiring.
4. Schema, CLI tests, README; all checks; PR.

## Risks

- `src/main.rs` conflicts with SHA-246 (console). Whoever lands second merges
  and routes the plan print through the console.
- The JSON shape of `plan --json` changes from the SHA-248 array to the plan
  document; `tests/assess_cli.rs` moves with it.

## Out of scope

Apply and `--confirm` (SHA-254), real consumers (SHA-252, SHA-253), real
providers, audit records for plan.
