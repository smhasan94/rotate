# Implementation plan: SHA-340 recorded terminal demo of plan and apply

## Context

The README explains rotate in text only. A short recording of the MVP
success scenario (a TruffleHog report with a leaked AWS key used by one
GitHub Actions secret and one Secrets Manager entry; `rotate plan`,
`rotate apply` with the typed confirmation, `rotate status` and the audit
log) shows the value at a glance. It must run with no real credentials,
show no secret value, and not rot.

## Findings

- The `test-providers` feature already registers mock providers under the
  four real names, and mock consumers from a JSON scenario named by
  `ROTATE_TEST_SCENARIO` (`src/providers.rs`, module `scenario`). The
  scenario sets each consumer's matches by fingerprint (`by_name` or
  `by_value`, `holds: secret | key_pair`), a call log path (JSON lines of
  `target`, `method`, `mutating`, `fingerprint`, `reference`), and the
  confirmation `prompt` (`{"answers": [...]}` is a `ScriptedPrompt`). The
  mocks make no network call and need no credentials. Nothing new is
  needed to drive the demo.
- A TruffleHog record with `DetectorName: AWS` is assigned to the `aws`
  provider by the detector hint, so the mock AWS provider takes the
  finding as a key pair. Its replacement is `AWS-key-1` /
  `mock_aws_aws-replacement-1`, a constant the leak sweep also searches
  for.
- `tests/fixtures/trufflehog_aws_e2e.ndjson` (SHA-264) is a TruffleHog
  record with `@KEY_ID@` and `@SECRET@` placeholders, filled at run time so
  no key is committed. The demo keeps its own copy under
  `tests/fixtures/demo/` so the e2e fixture can change without changing
  the recording.
- The fingerprint the mocks match is `sha256:` plus the first 16 hex
  characters of the SHA-256 of the secret half (`src/secret.rs`), which a
  shell computes with `sha256sum` or `shasum -a 256`.
- The rotation id is random per plan (`plan::mint_id`) and kept in
  `.rotate/state.json`, so the script reads it from there after `plan`.
- apply prints `Type the rotation id <id> to continue: ` to stderr with no
  newline. Rust's stdout is line-buffered, so with stderr merged into
  stdout the question lands between the plan and the summary, as at a
  terminal.
- The SHA-265 `Sweep` (`tests/common/sweep.rs`) searches buffers and
  directory trees for canaries in every encoding and is reused as is.
- The MVP acceptance test (SHA-267) runs the real plugins against wiremock
  inside the Rust test process; a shell script cannot start that server,
  so the demo uses the mocks instead.
- Neither `vhs` nor `asciinema` is installed on the machine that wrote
  this plan; the image is rendered by a maintainer (command below).

## Decisions

All recommended, pending maintainer review.

- `scripts/demo.sh` is the demo. It makes a run directory (`DEMO_DIR`, or a
  temporary one removed on exit) with `work/` (the report as
  `trufflehog.json`, `rotate.yaml`, `.rotate/`) and `mock/` (the scenario
  and one call log per command). The fake key pair is random, made in the
  script (`DEMO_KEY_ID`, `DEMO_SECRET` override it for the test), and is
  never printed. It runs `rotate plan trufflehog.json`, `rotate apply
  trufflehog.json`, `rotate status --all` and prints the audit log's step,
  outcome, fingerprint and consumer per line. It needs bash, sed, awk, tr
  and a SHA-256 tool, nothing else; with no `ROTATE_BIN` it builds the
  `test-providers` binary with cargo.
- The typed confirmation is the scenario's scripted prompt answering with
  the id plan assigned, the test build's stand-in for the keyboard; the
  script echoes the answer after the question (sed over the merged
  output) so the recording shows what was typed. apply still goes through
  the same confirmation code as at a terminal. See maintainer decision 5.
- `rotate.yaml` (`tests/fixtures/demo/rotate.yaml`) sets `overlap_window:
  0s` so the old key is revoked in the same run, and names `acme/api` and
  `prod/app` as a release build would; the mocks ignore the consumer
  sections.
- The first two lines of the demo say it is simulated: a test build with
  mock AWS, GitHub Actions and Secrets Manager, no real credentials, no
  network, a fake key. The README alt text says the same.
- `DEMO_PACE=<seconds>` adds pauses and clears the screen between steps
  for the recording; it is 0 in tests.
- `docs/demo/demo.tape` builds nothing: it expects `ROTATE_BIN` or a
  previous `cargo build --features test-providers`, hides the setup, and
  runs `scripts/demo.sh` with `DEMO_PACE`. Output `docs/demo/demo.gif`.
- `tests/demo.rs` (`#![cfg(all(unix, feature = "test-providers"))]`) runs
  the script with `bash` in a cleared environment (only `PATH`, `HOME` and
  `TMPDIR` inside the run directory, proxies pointed at a closed loopback
  port, no AWS or GitHub credentials), `ROTATE_BIN` set to the test build,
  `DEMO_DIR` in a temp dir and canary key values. `cargo test
  --all-features` already runs on Linux and macOS in CI, so `ci.yml` does
  not change.
- No `src/` change. CHANGELOG, Cargo.toml and CI files are untouched.

## Maintainer decisions

1. Recording tool.
   - (a) charmbracelet `vhs` tape: a committed script, re-rendered the
     same way by anyone; GIF, WebM or PNG output. Needs vhs, ttyd and
     ffmpeg on the machine that renders.
   - (b) asciinema plus `agg`: records a live session; the cast is
     reproducible only by re-recording by hand.
   - (c) a static SVG (one terminal screenshot): smallest and sharpest,
     but no motion and still needs a renderer.

   Recommendation: (a), with `scripts/demo.sh` doing the work so the tape
   is a few lines.
2. GIF or SVG, and size.
   - (a) GIF at about 1100x720, 14 pt font, 2 to 3 s per step: GitHub
     renders it in the README everywhere; expected well under 2 MB as
     the frames are mostly static text.
   - (b) animated SVG (svg-term from an asciinema cast): a few hundred KB
     and crisp, but needs the asciinema toolchain and does not animate in
     every viewer.

   Recommendation: (a). If a render exceeds 2 MB, lower `Framerate` and
   `Width` in the tape before anything else.
3. Where the image lives.
   - (a) `docs/demo/demo.gif` next to `docs/demo/demo.tape`, in git.
   - (b) a GitHub release asset or an uploaded attachment URL.

   Recommendation: (a): versioned with the code, under 2 MB, no LFS.
4. Simulated build. The demo must use the `test-providers` build (no
   credentials, no network, no real account touched). How the reader
   knows:
   - (a) the first lines of the recording and the alt text say
     "simulated, mock providers";
   - (b) also a caption line under the image in the README.

   Recommendation: (a) now; (b) only if reviewers find the alt text
   easy to miss, since the ticket allows one README line.
5. Typed confirmation.
   - (a) the scripted prompt plus an echo of the answer (this plan);
   - (b) `--confirm <id>` (the documented non-interactive path), which
     does not show the confirmation step;
   - (c) a real terminal prompt typed by vhs. The id is random per plan,
     so the tape cannot know it; this would need a small scenario field
     in `src/providers.rs` (for example `rotation_id_seed`, making
     `mint_id` deterministic under `test-providers`).

   Recommendation: (a). Revisit (c) if a real keystroke-level recording
   is wanted.
6. Keeping it from rotting.
   - (a) `tests/demo.rs` runs `scripts/demo.sh` in the default test run
     (Linux and macOS in CI), with no `ci.yml` change;
   - (b) a separate CI step calling the script;
   - (c) also render the tape in CI (vhs-action) and fail on a diff.

   Recommendation: (a). (c) is slow and the GIF bytes are not stable
   across renders; re-render by hand when the output changes.

## Rendering

From the repository root, with vhs installed (`brew install vhs`):

```sh
cargo build --features test-providers
ROTATE_BIN=$PWD/target/debug/rotate vhs docs/demo/demo.tape
ls -l docs/demo/demo.gif   # must stay under 2 MB
```

## Tests

- T1 (AC1) `t1_demo_runs_plan_apply_status`: exit 0; stdout has the dry-run
  plan, `Type the rotation id <id> to continue: <id>`, `Apply: 1 revoked`
  and a status row with `revoked` and `done`; `mock/plan.jsonl` has no
  mutating call; `mock/apply.jsonl` mutating calls are exactly
  `aws.create_replacement`, `github-actions.update`,
  `aws-secrets-manager.update`, `aws.revoke`; every call targets a mock;
  `.rotate/` is 0700 with 0600 files.
- T2 (AC2) `t2_demo_shows_no_secret`: the `Sweep` with the canary secret
  half and the mock replacement secret over the script's stdout and stderr and every file under the run directory
  except the input report; every `sha256:` token printed is the 16-hex
  fingerprint form and the leaked key's fingerprint is among them.
- T3 (AC3): once `docs/demo/demo.gif` is rendered and the README line
  added, a test that the README has `![<alt>](docs/demo/demo.gif)` with
  non-empty alt text naming plan, apply, status and the audit log, and
  that the file is under 2 MB.

## Ticket (as filed)

### Context

The README explains rotate in text only. A short recording of the MVP
success scenario makes the value clear at a glance: a TruffleHog report
with a leaked AWS key used by a GitHub Actions secret and a Secrets
Manager entry, then `rotate plan`, `rotate apply` and the audit log. It
must run with no real credentials and show no secret value.

### Scope

In scope:

- A reproducible recording script (for example a charmbracelet `vhs` tape
  at `docs/demo/demo.tape`) driving the `test-providers` build with a
  `ROTATE_TEST_SCENARIO` that mocks AWS, GitHub Actions and Secrets
  Manager.
- A shell wrapper (`scripts/demo.sh`) that sets up a temporary directory,
  fixture report and rotate.yaml, so the demo commands also run without
  `vhs`.
- The rendered GIF (or SVG) embedded near the top of the README; the file
  size is kept small (target under 2 MB).
- A CI check that runs the demo commands and their exit codes without
  recording, so the demo cannot rot.

Out of scope: video hosting, asciinema.org uploads, a website.

### Acceptance criteria

- AC1. Given a checkout and the `test-providers` build, when
  `scripts/demo.sh` runs, then plan exits 0, apply exits 0 after the typed
  confirmation, and status shows the rotation done, with no network access
  beyond loopback.
- AC2. Given the demo run, when every stream and file it wrote is swept,
  then the fixture's secret value appears nowhere, and every fingerprint
  shown is the redacted form.
- AC3. Given the README, when it is rendered, then the demo image appears
  with alt text describing the steps, and the image file is under 2 MB.

### Test plan

- T1 (integration, tests/demo.rs or CI step) - covers AC1 - run
  `scripts/demo.sh` in CI on Linux and macOS; assert the exit codes and
  status output.
- T2 (integration) - covers AC2 - the Sweep over the demo's outputs and
  files with the fixture value as canary.
- T3 (unit) - covers AC3 - assert the README references the image with alt
  text and the file size is under the limit.

### Definition of done

All T-cases pass in CI, fmt, clippy and cargo deny pass, docs updated, PR
reviewed and merged.

### Dependencies

Blocked by: none
