# Implementation plan: SHA-251 AWS IAM provider read side

Ticket edits applied with this plan:

- Credentials for the read side: `check_valid` **and** `describe_scope` sign
  with the leaked key pair itself, never the operator's credentials. Both
  are read-only calls in which the leaked key answers questions about
  itself (`sts:GetCallerIdentity`, then the IAM reads on its own user), so
  `rotate plan` needs no operator AWS setup and never loads the default
  credential chain. This is the narrow "test itself, read-only" exception
  to D3 the ticket already makes for `check_valid`; rotate still never uses
  the leaked key to change anything. The operator chain (`aws-config` with
  `sso` and `credentials-process`) is first used by the write side
  (SHA-255).
- Consequence: a leaked key often has no IAM read permissions on itself. An
  `AccessDenied` on any of the four IAM calls becomes a scope line ("not
  visible to the leaked key: AccessDenied") instead of failing the scope.
  User name and account id always come from the `GetCallerIdentity` ARN, so
  AC5's user and account lines are always present.
- `ReplacementMode` has no `Unsupported` variant and the mode is per
  provider, not per credential. For an `ASIA` key `check_valid` returns
  `Unknown { reason: "temporary credential: revoke by rotating the source" }`
  without any network call (an `ASIA` key cannot sign without its session
  token, which findings do not carry, so STS would wrongly say Invalid). The
  planner already skips Unknown secrets with their reason, so the plan
  shows the message and no replacement step (AC6). `describe_scope` and the
  write methods return `ProviderError::Unsupported` for `ASIA` keys.
- AC4 retries: the SDK's own retries are disabled (`RetryConfig::disabled()`)
  so the one retry policy is assessment's (SHA-248, three attempts by
  default). A 503 maps to `ProviderError::Transient`; T4 runs `check_valid`
  through `assess` and wiremock verifies exactly three requests.
- Canary tokens (`extra.is_canary`): a `Credential` does not carry the
  finding's metadata, so the provider cannot see the flag. Assessment
  already marks canaries not rotatable before any provider call; the
  provider adds no path around that. A test runs an AWS canary finding
  through `assess` with the real provider and asserts wiremock saw zero
  requests.
- Added: AWS documentation example keys (key id ending in `EXAMPLE`, as in
  `AKIAIOSFODNN7EXAMPLE`) are `Invalid` without a network call. Scanners
  find them in docs and tests all the time, and it keeps the plain
  `cargo test` CLI runs (which feed the example key from the fixtures to a
  binary with the real provider registered) off the network.
- `create_replacement`, `verify`, `revoke` and `restore` return
  `ProviderError::Unsupported("... (SHA-255)")` until SHA-255. T9 asserts the
  read-side checks pass and that only the four write-side checks fail.

## Approach

`src/provider/aws.rs`, `pub struct AwsProvider`:

- `AwsProvider::new()` holds settings only: optional region, optional
  endpoint URL, and a `tokio::sync::OnceCell<Region>`. Constructing and
  registering it reads nothing and calls nothing.
- Builders: `with_region(impl Into<String>)` (from `providers.aws.region`),
  `with_endpoint_url(impl Into<String>)` (tests point STS and IAM at
  wiremock).
- Region, resolved lazily on the first call: the configured region, else
  `AWS_REGION` / `AWS_DEFAULT_REGION`, else the shared config profile, else
  `us-east-1` (`aws_config::meta::region::RegionProviderChain` without IMDS,
  so no network). IAM is global; the region only picks the STS endpoint.
- Per call, an STS or IAM client is built from `Config::builder()` with
  `BehaviorVersion::latest()`, the region, the endpoint URL when set,
  `RetryConfig::disabled()`, a timeout config (connect 5 s, operation 30 s)
  and `Credentials::new(key_id, secret, None, None, "rotate-leaked-key")` as
  a static provider. No `aws_config::load_from_env`.
- `identify` (pure): `KeyPair` whose key id is `AKIA|ASIA` + 16 uppercase
  alphanumerics and whose secret is 40 chars of `[A-Za-z0-9/+]`: `High` when
  the detector is `AWS` or `aws-access-token` (case-insensitive), else
  `Medium`. A bare token shaped like a key id: `Low` (check_valid then says
  to pass `KEY_ID:SECRET`). Anything else: `None`.
- `check_valid`: `Token` returns `Unsupported` (needs the key id). `ASIA`
  returns the temporary-credential `Unknown`. Example key returns `Invalid`.
  Otherwise `sts:GetCallerIdentity` signed with the pair: success is
  `Valid`; error code `InvalidClientTokenId` or `SignatureDoesNotMatch` is
  `Invalid`; throttling codes and 429 are `RateLimited`; 5xx, timeouts and
  dispatch failures are `Transient`; anything else `Permanent`.
- `describe_scope`: `GetCallerIdentity` for the ARN (the `Identity`) and
  account. When the ARN is an IAM user (`arn:...:iam::<acct>:user/<path>/<name>`):
  `GetAccessKeyLastUsed` (service, region, date), `ListAttachedUserPolicies`,
  `ListUserPolicies`, `ListGroupsForUser`, each paginated by `Marker` up to
  20 pages. Lines: `account: <id>`, `user: <name>`, `last used: <service> in
  <region> at <date>` or `last used: never`, `attached policy: <name>`,
  `inline policy: <name>`, `group: <name>`. A non-user principal (root) gets
  a `principal: root user` line and no IAM calls.
- Error text is built by rotate, never copied from the response: operation
  name, a sanitised error code (`[A-Za-z0-9.]`, at most 64 chars) and the
  HTTP status. The server's message is dropped, so a hostile or echoing
  endpoint cannot put a value into plan output.
- `replacement_mode()` is `Automatic` (SHA-255 implements it).

Rejected:

- Operator credentials for `describe_scope` (the ticket's wording): makes
  `plan` depend on a configured AWS environment and the default chain
  (which may hit IMDS or SSO) for a read the leaked key can answer itself.
- Hand-written SigV4 over reqwest: more security-sensitive code to own
  (SHA-273 decision 2).
- One cached client: the credentials differ per finding, so the client is
  per call; building one is cheap next to a network round trip.
- A per-credential replacement mode for `ASIA`: changes the trait for one
  case the planner already handles through `Unknown`.

## Changes

- `Cargo.toml`: `aws-config`, `aws-sdk-iam`, `aws-sdk-sts` with
  `default-features = false` per SHA-273. `Cargo.lock` resolved with
  `CARGO_RESOLVER_INCOMPATIBLE_RUST_VERSIONS=fallback` so the crate's

  `test-providers` (the feature keeps registering the mock under `aws`).
- `tests/aws_provider.rs` (new): wiremock, conformance, leak, canary and
  live tests.
- `CONTRIBUTING.md` or README: none beyond the provider's doc comments; the
  least-privilege doc for operator permissions arrives with SHA-255.

## Secret handling

The secret leaves `SecretValue` once per call: inside
`expose_secret_str(|s| Credentials::new(key_id, s, ...))`. The SDK keeps it
in `Zeroizing<String>`, redacts it in `Debug`, and uses it only to derive
the SigV4 signing key; the request carries the key id and a signature,
never the secret. No `Scope` line, `Unknown` reason or error message is
built from response text or from the credential other than the key id
(not a secret). Tests capture tracing at TRACE level (the SDK logs canonical
requests there) and assert the secret is absent from logs, rendered
assessment table and JSON, error text, scope lines and every recorded
request (headers and bodies).

## Test mapping

Unit tests in `src/provider/aws.rs`; integration tests in
`tests/aws_provider.rs` against `common::CallRecorder`, with AWS query
actions `Get*` and `List*` marked read-only. Key ids and secrets are built
at runtime; no literal matches a secret-scanning pattern.

- T1 (AC1): unit `identify_aws_fixture_high_github_none` (plus
  `identify_shapes` for Medium, Low and None).
- T2 (AC2): `check_valid_valid_signed_with_leaked_key_id` asserts `Valid`,
  the `Authorization` header holds `Credential=<key id>/` and not the secret.
- T3 (AC3): `check_valid_invalid_client_token_id`, also
  `SignatureDoesNotMatch`.
- T4 (AC4): `check_valid_503_three_attempts_unknown` through `assess`,
  `expect(3)`.
- T5 (AC5): `describe_scope_lists_user_account_last_used_policies`; plus
  `describe_scope_access_denied_is_a_line`.
- T6 (AC6): `asia_key_is_temporary_unknown_without_calls` through `assess`
  and `plan::build`: skipped `unknown` with the message, no rotation, zero
  requests.
- T7 (AC7): every wiremock test ends with `assert_no_mutating_actions`
  (no body with `Action=Create`, `Update`, `Delete` or `Put`), plus
  `rec.assert_no_mutations()`.
- T8 (AC2, AC5): `secret_never_in_logs_output_or_requests` runs T2 and T5
  paths with a TRACE capture and renders the assessment table and JSON.
- T9 (AC1, AC3, AC7): `conformance_read_side` runs `provider_suite`.
- Extras: `canary_finding_never_reaches_aws` (zero requests),
  `example_key_is_invalid_without_calls`, `token_credential_is_unsupported`,
  `new_makes_no_calls` (construct and register, zero requests),
  `live_aws_check_valid_and_scope` (`#[ignore]`, `live_guard!`, keys from
  `ROTATE_LIVE_AWS_ACCESS_KEY_ID` / `ROTATE_LIVE_AWS_SECRET_ACCESS_KEY`).

## Sequence

1. Dependencies, `cargo deny check`.
2. `AwsProvider` with identify and error mapping; unit tests.
3. STS and IAM calls; wiremock tests T2 to T7.
4. Conformance, leak, canary, live tests; registry; smoke script; PR.

## Risks

- `Cargo.lock`: SHA-252 adds the same `aws-config` line. Whoever lands
  second takes main's `Cargo.lock` and rebuilds.
- `src/providers.rs`: SHA-252 and SHA-253 register consumers in the same
  file, different function; a textual merge only.
- `providers.aws.region` is not passed in yet: `registry()` takes no config
  and `src/main.rs` belongs to SHA-254. The env and profile region apply
  until main passes the config (`AwsProvider::with_region`).
- Binary size: `aws-lc-rs` and the SDK add a few MB; the reqwest provider
  unification from SHA-273 stays optional.

## Out of scope

Create, verify, revoke, restore (SHA-255); operator credentials; Secrets
Manager (SHA-252); least-privilege docs (SHA-255).
