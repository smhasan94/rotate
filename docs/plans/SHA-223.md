# Implementation plan: SHA-223 Report parsers

Ticket edits applied with this plan:

- For a TruffleHog AWS finding, `raw` is the secret access key, not the
  `Raw` field. A TruffleHog 3.97.9 run on fake keys showed `Raw` holds only
  the access key id, `RawV2` holds `<id>:<secret>`, and a `SecretParts`
  object holds both halves by name. `ExtraData` holds `account`,
  `resource_type` and `is_canary`, never the key id. The parser reads
  `SecretParts` first and falls back to `RawV2` (strip the `Raw` prefix and
  one optional `:`) for older versions without `SecretParts`. An AWS record
  with neither is skipped with a warning; it has no usable secret.
- `extra` stays `BTreeMap<String, String>` as SHA-221 defined it: non-secret
  values only. The ticket's `SecretValue or String` variant is dropped.
  Parsers write `access_key_id` and, when TruffleHog flags a canary token,
  `is_canary = "true"`. A canary key alerts its owner on any API call, so
  SHA-251's `check_valid` should look at this flag.
- gitleaks `Match` is not read. It is the secret plus surrounding text, so
  reading it would make a second copy of the value. `Secret` alone is used.
- The `--format` flag is wired up in SHA-250, which adds the report path
  argument to `plan`. This ticket adds `ReportFormat` (a `clap::ValueEnum`) and
  `parse_report(input, Option<ReportFormat>)`; AC3 is tested at that API.
- Warnings are returned as data (`ParsedReport::warnings`) and also emitted
  with `tracing::warn!`. `tracing` and `serde_json` move from dev-dependencies
  to dependencies.
- T4 becomes an integration test so it can use `tests/common::LogCapture`.
  T7 covers `Debug` output and tracing. Stdout and stderr have no code path
  yet; the CLI leak test arrives with SHA-250 and SHA-265.

## Real output shapes

TruffleHog 3.97.9 `filesystem --json --no-verification`, one object per line:
`SourceMetadata.Data.<SourceKind>.{file, line, commit?}`, `DetectorName`
(`"AWS"`, `"Stripe"`), `Raw`, `RawV2` (empty string for single-part
secrets), `ExtraData` (string map or null), `SecretParts` (`{"key": ...}`
for single-part, `{"access_key_id", "secret_access_key"}` for AWS),
`Verified`. The `git` source uses `Data.Git` with `commit`.

gitleaks 8.30.1 `dir -f json`: a pretty-printed array of `{RuleID, Secret,
Match, File, StartLine, Commit, ...}`. `Commit` is `""` outside git mode.
gitleaks reports an AWS key id (`aws-access-token`) and its secret half
(`generic-api-key`) as two unrelated findings, so a gitleaks AWS finding
carries only the key id. The parser keeps it as is; SHA-248 must report it
as not rotatable from this input (use TruffleHog or `--stdin`). I'll leave
this note on SHA-248.

## Approach

`src/report/mod.rs` holds `ReportFormat`, detection, `ParsedReport`,
`ParseWarning` and `ReportError`. `src/report/trufflehog.rs` and
`src/report/gitleaks.rs` each expose one `parse(&[u8]) -> ParsedReport`-style
function. Typed private serde structs per format; no `serde_json::Value`, which
would put every secret into plain `String`s.

Secret fields deserialize straight into `SecretValue` through its existing
`Deserialize` impl, so they land in zeroized memory. `read_report` reads the
file into a `Zeroizing<Vec<u8>>` sized from file metadata, so the input copy
of every secret is wiped too.

gitleaks is parsed as `Vec<&RawValue>` (borrowed from the input, feature
`raw_value`) then each element on its own. One bad element is skipped with a
warning instead of failing the file. The element's line comes from its byte
offset in the input. A file that is not a valid JSON array at all fails with
`ReportError::Malformed`.

Rejected: `serde_json::Value` as an intermediate step, which leaves secrets in
unwiped strings. Rejected: putting serde error text into warnings. serde_json
echoes input in data errors (`invalid type: string "...", expected u64`), so
warnings and errors carry only the error category, line and column.

## Changes

- `Cargo.toml`: `serde_json = { version = "1", features = ["raw_value"] }`
  and `tracing = "0.1"` move to `[dependencies]` (both MIT or Apache-2.0,
  already in the lock file).
- `src/report/mod.rs`:
  - `#[derive(Debug, Clone, Copy, PartialEq, Eq, clap::ValueEnum)] pub enum ReportFormat { Trufflehog, Gitleaks }`, `Display` as `trufflehog` / `gitleaks`.
  - `pub fn detect_format(input: &[u8]) -> Detected` where `Detected` is `Empty | Format(ReportFormat) | Unrecognized`: skip a UTF-8 BOM and ASCII whitespace, then `[` means gitleaks and `{` means TruffleHog.
  - `pub struct ParsedReport { pub format: Option<ReportFormat>, pub findings: Vec<Finding>, pub warnings: Vec<ParseWarning> }` (`format` is `None` for an empty input).
  - `pub struct ParseWarning { pub format: ReportFormat, pub line: usize, pub reason: SkipReason }`; `pub enum SkipReason { InvalidJson { column: usize }, WrongShape { column: usize }, EmptySecret, AwsWithoutSecretHalf }`. `Display`: `trufflehog line 2 skipped: not valid JSON (column 7)`.
  - `#[derive(thiserror::Error)] pub enum ReportError { Io { path, source }, FormatMismatch { requested, detected }, Unrecognized, Malformed { format, line, column } }`. Mismatch text: `--format gitleaks was given but the report looks like trufflehog`.
  - `pub fn parse_report(input: &[u8], format: Option<ReportFormat>) -> Result<ParsedReport, ReportError>`: empty or whitespace-only input returns an empty report whatever the format; mismatch is checked before parsing. Each warning is also emitted as `tracing::warn!(%warning)`.
  - `pub fn read_report(path: &Path, format: Option<ReportFormat>) -> Result<ParsedReport, ReportError>`.
- `src/report/trufflehog.rs`: split on `\n`, skip blank lines, line numbers 1-based over the whole file. Record struct: `DetectorName: String`, `Raw: Option<SecretValue>`, `RawV2: Option<SecretValue>`, `SecretParts: Option<AwsParts>` (`access_key_id: Option<String>`, `secret_access_key: Option<SecretValue>`; other keys ignored without allocating), `ExtraData: Option<Extra>` (`is_canary: Option<String>`), `SourceMetadata: Option<SourceMetadata>` where `Data` is a one-entry map of source kind to `{ file, line, commit }`. A missing file becomes `SourceLocation::file("<unknown>")`. The detector `"AWS"` takes the AWS path above.
- `src/report/gitleaks.rs`: element struct `RuleID`, `Secret: SecretValue`, `File`, `StartLine: Option<u64>`, `Commit: Option<String>` (empty means `None`).
- `src/lib.rs`: `pub mod report;`.
- `tests/fixtures/`:
  - `trufflehog.ndjson`: AWS in 3.97 shape from a git source with a commit; a GitHub token from the filesystem; an npm token from the filesystem.
  - `trufflehog_aws_legacy.ndjson`: one AWS record with no `SecretParts` (`RawV2` fallback).
  - `trufflehog_malformed.ndjson`: three lines, line 2 is garbage that contains a canary string.
  - `gitleaks.json`: `aws-access-token`, `github-pat`, `npm-access-token`, one with a commit.
  - `empty.json`: zero bytes.
  - `README.md`: every value is fake and must stay fake. Values use AWS's documented `EXAMPLE` keys or contain `FAKE`, and avoid valid provider checksums so GitHub push protection and scanners do not flag them.
- `docs/report-formats.md`: supported scanners and tested versions, field mapping for each, the AWS and gitleaks limitations above.

## Secret handling

Secrets exist only as `SecretValue` after parsing. The AWS `Raw` and
`SecretParts.access_key_id` are read as `SecretValue` and exposed once to
build the `access_key_id` string, which is not secret. Warning and error
text is built from line, column, format and a fixed reason; it never
includes input bytes or serde's message. `ParsedReport` and `ParseWarning`
derive `Debug`, which is safe because `Finding`'s `Debug` prints the
fingerprint.

Known gap: when a JSON string has escape sequences, serde_json decodes it
through its own scratch buffer, which is not wiped. TruffleHog and
gitleaks escape only quote, backslash and control characters, and none
appear in the four MVP providers' token formats. I'll record this in
`docs/report-formats.md`.

## Test mapping

Unit tests are in `src/report/*.rs` and load fixtures with `include_bytes!`.

- T1 (AC1): `trufflehog_fixture_parses_three_findings`: detectors, files,
  lines, the commit on the git record, and hard-coded expected fingerprints.
- T2 (AC2): `gitleaks_fixture_parses_three_findings`: same checks.
- T3 (AC3): `detects_format_from_first_byte` (both fixtures, BOM and leading
  whitespace) and `forced_wrong_format_names_both`.
- T4 (AC4): `tests/report_leak.rs::malformed_line_is_skipped_with_line_number`:
  two findings, one warning whose text contains `line 2`, garbage absent from
  the warning text and from the `LogCapture` output.
- T5 (AC5): `trufflehog_aws_has_key_id_in_extra` (SecretParts shape) and
  `trufflehog_aws_legacy_uses_raw_v2` (fallback): `extra["access_key_id"]`,
  and `raw` fingerprint equals the secret half's fingerprint, not the key
  id's or `RawV2`'s.
- T6 (AC6): `empty_input_is_empty_report` for zero bytes, whitespace only,
  and `[]`, with and without a forced format.
- T7 (AC1, AC2, AC4): `tests/report_leak.rs::parsed_reports_never_render_secrets`:
  parse every fixture under `LogCapture`; assert no fixture secret appears in
  `{:?}`/`{:#?}` of the reports, the warnings' `Display`, or tracing output.
- Extras: `wrong_type_field_does_not_echo_input` (a `line` field holding the
  canary string as a JSON string: the warning omits it),
  `aws_without_secret_half_is_skipped`, `gitleaks_bad_element_skipped_with_line`,
  `gitleaks_empty_commit_is_none`, `unrecognized_first_byte_errors`.

## Risks and unknowns

- Older TruffleHog versions may join `RawV2` without the `:`. The fallback
  strips the key-id prefix and then an optional `:`, so both forms work.
- TruffleHog source kinds other than `Git`, `Github` and `Filesystem` may
  use other field names; those findings still parse, with file `<unknown>`.
- GitHub push protection could flag a fixture value. If it does, change the
  value so its checksum fails rather than bypassing the block.

## Out of scope

Stdin input (SHA-247), provider identification and dedupe (SHA-248), CLI
flags for report path and `--format` (SHA-250), Betterleaks and GitHub alert
formats (SHA-202).
