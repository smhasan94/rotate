# Implementation plan: SHA-258 resume, idempotency and the overlap window

Ticket edits applied with this plan:

- `needs_rollback` becomes a real step (`Step::NeedsRollback`), set by
  apply when a rotation must be resumed with a replacement whose value is
  gone. It is not terminal: `status` lists it, `plan` keeps its id, and
  `rollback` handles it like any unfinished rotation (restore the updated
  consumers, revoke the replacement; the old secret was never revoked).
  Apply never acts on it again; it is skipped with "run rotate rollback".
  The state file stays version 1: older files never contain the value, and
  every other field is unchanged.
- Resume works from the stored record (step, `failed_step`,
  `replacement_ref`, consumers), not from the plan alone:

  | stored step | resume |
  |---|---|
  | `planned`, or `failed` with no `replacement_ref` | full run; nothing was created |
  | `created`, or `failed` at create/update with a `replacement_ref` | update only the consumers not `updated`, then verify, using the replacement this process still holds; without it, mark `needs_rollback` and update nothing (AC6) |
  | `consumers_updated`, or `failed` at verify | verify again, read-only, then the revoke gate (AC5) |
  | `verified`, `pending_revoke`, or `failed` at force/revoke | the revoke gate, then revoke (AC2, AC3) |
  | `revoked` | already rotated: filtered out before assessment, zero calls (AC7) |
  | `needs_rollback`, or a rollback in progress | skipped, no call |

- Re-verifying in a new process needs the replacement, which rotate never
  stores. The provider trait gains `verify_replacement(replacement_ref,
  identity)`, read-only, default `Unsupported`, so SHA-261 and SHA-262
  compile unchanged. AWS implements it (the key named by the ref exists,
  is Active, and belongs to the leaked key's IAM user); the mock records it.
  When the replacement is held in memory the full `verify` is used instead.
  `Unsupported` (GitHub, any `manual` ref) marks the rotation
  `needs_rollback` with that reason.
- The in-memory replacement (ticket: "held in memory only when the process
  did not exit") lives in the `Executor`, keyed by rotation id, from create
  until verify passes. A second `run` of the same rotation in the same
  process (T8) uses it. The CLI runs each rotation once per process, so
  from the CLI a rotation that stopped after create always becomes
  `needs_rollback`.
- A pending revoke keeps the `revoke_not_before` recorded when it was
  verified: a re-run with a different `--overlap` does not move it. The
  window is computed from an injectable clock (`Executor::with_clock`; the
  test scenario sets `clock_offset_secs`).
- `--wait` (apply only): when the gate waits, the pending revoke is saved
  first, a note goes to stderr ("waiting until ..."), apply sleeps until
  `revoke_not_before` and then revokes in the same process. Interrupting
  the sleep leaves a normal pending revoke.
- `plan` and `apply` drop findings whose fingerprint's latest rotation is
  `revoked` (and not being rolled back) before identification, so no
  provider or consumer call is made for them. They are listed under
  Skipped with reason `already rotated` and the note "rotation <id>
  already rotated on <date>; nothing to do". A rotation being rolled back
  keeps its id in `plan`, so apply reports "a rollback of it is in
  progress" instead of starting a new rotation.
- Audit: every completed step a resume does not repeat gets an entry with
  outcome `skipped` (create, each consumer already updated, verify), and a
  revoke deferred by the window gets `revoke` / `skipped` with the time.
  `needs_rollback` is recorded as a `failed` entry at the step that could
  not continue (update or verify) with the reason.
- Exit codes: 3 while a revoke is pending (first run and early re-runs,
  with the remaining time in the summary); 0 when revoked (including
  `--wait`) or when everything was already rotated; 1 for failed, held or
  `needs_rollback` (also a re-run that skips a `needs_rollback` rotation).

## State and audit schema (for SHA-263 `rotate status`)

- `Step::NeedsRollback`, JSON `needs_rollback`: not terminal, listed by
  `list_in_progress`. The reason is in the audit log, not the state file.
- `pending_revoke` plus `revoke_not_before` (RFC 3339) is the pending
  revoke; `status` can compare it with now. Unchanged fields.
- No other state change. Audit version stays 1 (outcome `skipped` exists).
- `plan --json`: `state` gains `needs_rollback` and `revoked` (a revoked
  rotation being rolled back); skipped `reason` gains `already rotated`.

## Approach

`src/state.rs`: the new step, `is_terminal` unchanged.

`src/provider/mod.rs`, `mock.rs`, `aws.rs`: `verify_replacement`.

`src/apply.rs`:

- `eligibility`: every unfinished step except `needs_rollback` is eligible;
  `Ineligible::NeedsRollback` and `Ineligible::Finished(step)` replace
  `InProgress`. `eligibility_in` still checks the rollback first.
- `Executor`: `held` replacements, `with_wait(bool)`, a `resume_point`
  from the record, a consumer loop that skips consumers already updated,
  `verify` by credential or by ref, and a gate that reuses a stored
  `revoke_not_before`. `RunResult::NeedsRollback { reason }`;
  `PendingRevoke` gains `remaining`.
- Summary notes: "revoke pending until <t> (in 9m 59s); the old secret
  stays valid until then; re-run rotate apply after that time to revoke
  it", and for `needs_rollback` "the replacement value from the earlier
  run is gone, so the remaining consumers cannot be updated; run rotate
  rollback with the same input to restore the consumers and revoke the
  replacement, then apply again".

`src/plan.rs`: `already_rotated(findings, store)` split, skipped entries,
`assign_ids` keeps a rotation being rolled back, state wording per step.

`src/cli.rs`, `src/main.rs`, `src/providers.rs`: `--wait`, the filter in
`build_plan`, the scenario clock.

`docs/plan-schema.json`, README.

## Secret handling

The only new place a value lives is the executor's `held` map: zeroized
`Credential`s, registered with the redactor while alive, dropped with the
executor. Nothing new is written to state or audit except steps, refs,
fingerprints and times. T9 runs T1, T2 and T5 with canary old values at
`-vvv` and checks stdout, stderr (tracing), the audit log, the state file
and the call log for the old value and the mock replacement value.

## Risks

- SHA-261 and SHA-262 implement `Provider`; the new method has a default.
- SHA-264 tests AWS end to end; `verify_replacement` is additive.
- SHA-263 reads the state file; the new step is documented above.

## Out of scope

Re-supplying a manual replacement by pasting it again to resume after an
exit (possible follow-up: the fingerprint can be checked against
`replacement_fingerprint`), `rotate status` (SHA-263).
