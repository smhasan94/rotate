# Implementation plan: SHA-262 OpenAI API key provider

## What OpenAI's API allows today

Checked against OpenAI's current API reference (developers.openai.com,
Admin API: projects, project API keys, project service accounts) on
2026-10-02. Where it differs from the ticket, the ticket is adjusted as
below.

- **Key prefixes.** `sk-proj-` (project key owned by a user),
  `sk-svcacct-` (project service-account key), `sk-admin-` (organization
  Admin API key), and the legacy user key `sk-` plus 48 alphanumerics.
  Bodies are `[A-Za-z0-9_-]`. Other vendors also use `sk-` (`sk-ant-`,
  `sk-or-`), so a bare `sk-` value is claimed only in the exact legacy shape.
- **Validity.** `GET /v1/models` with the key: 200 valid, 429 valid
  (rate limited or out of quota, but authenticated), 401 invalid. A
  restricted key without the models read permission also answers 401, with
  "insufficient permissions"/"Missing scopes" in the message; that is read
  (never copied into an error) and reported as valid. Anything else is
  `Unknown`. Admin keys cannot call non-admin endpoints, so an `sk-admin-`
  key is identified but `check_valid` returns `Unknown` ("admin key:
  rotate it at platform.openai.com/settings/organization/admin-keys") with
  no call, and the plan skips it.
- **Scope.** `GET /v1/organization/projects` (cursor pages, `limit`,
  `after`, `has_more`, `last_id`) and `GET
  /v1/organization/projects/{id}/api_keys` per project. Each key has `id`,
  `name`, `redacted_value`, `created_at`, `last_used_at`, and `owner`
  (`type` `user` with `user.{name,email}` or `service_account` with
  `service_account.{id,name}`). The leaked key is matched by the
  `redacted_value` head and tail (prefix and last characters). More than one
  match across the organization is an error, never a guess.
- **Replacement.** `POST /v1/organization/projects/{id}/service_accounts`
  with `{"name": ...}` returns the service account and an unredacted
  `api_key.value` and `api_key.id`. This is the only time OpenAI returns the
  value.
- **Delete, and the gap.** `DELETE
  /v1/organization/projects/{id}/api_keys/{key_id}` deletes a user-owned
  project key. OpenAI documents that it returns an error "if the key
  belonged to a service account". The ticket assumed the reverse (user keys
  undeletable, service-account keys deletable). So:
  - user-owned key: revoke is the `api_keys` DELETE, 404 is already gone;
  - service-account key: the only API that removes it is `DELETE
    /v1/organization/projects/{id}/service_accounts/{sa_id}`. rotate does
    that only when the listing shows the leaked key is the account's only
    key; otherwise revoke is manual (deleting the account would kill its
    other keys);
  - a key in no project the admin key can list (legacy user key) has no
    project, so it gets no scope, and apply skips it.
  AC7 ("user key the listing marks as not deletable") becomes "a key the
  Admin API cannot delete": a service-account key whose account holds other
  keys. The plan's revoke row names the dashboard and apply makes no DELETE.
- **`revoke_replacement`.** Possible: the replacement is a service account
  rotate created, so rollback deletes that service account by id (404 is
  already gone). `replacement_ref` is `openai:<project_id>:<sa_id>:<key_id>`
  (ids only).
- **Not readable.** OpenAI does not expose a key's permissions (All,
  Restricted, Read only) through the Admin API. The replacement service
  account gets the default `member` role and all permissions; the scope says
  so.
- **Rotation id.** `Provider::create_replacement` receives the credential
  only, and SHA-258 owns the executor, so the service account is named
  `rotate-<fingerprint hex>` (the 16 hex characters of the leaked key's
  fingerprint, which the audit log ties to the rotation id) rather than
  `rotate-<rotation-id>`.

## Approach

`src/provider/openai.rs`, `OpenAiProvider::new(api_url, AdminKey)`:

- `AdminKey::Env(name)` (release: `providers.openai.admin_key_env`,
  default `OPENAI_ADMIN_KEY`), `AdminKey::Value(SecretValue)` (tests),
  `AdminKey::None`. Construction reads nothing. `replacement_mode` checks
  only whether the variable is set and non-empty; the value is read into a
  `SecretValue` when an admin call is made. If the admin key is the leaked
  key, every admin call refuses (decision D3).
- Own small reqwest client: bearer header built in zeroized memory and
  marked sensitive; errors carry endpoint, status and OpenAI's `error.code`
  or `error.type` only, never `error.message` (a 401 message echoes part of
  the key). Bodies read into zeroized buffers; the create response is
  decoded straight into `SecretValue`.
- `identify`: token only. Known prefix plus a 20 to 255 byte body, or the
  exact legacy shape: `High` with an OpenAI hint, `Medium` without.
- `check_valid`: `GET /v1/models` signed with the key, as above.
- `describe_scope`, admin key set: projects then keys, matched by
  `redacted_value`. Identity is the project id. Lines: `project:`, `key:`,
  `owner:`, `created:`, `last used:`, `permissions:` note, and a `warning:`
  line when revoke must be manual. No match is an error naming the
  dashboard. Without an admin key: `GET /v1/models` with the key for the
  `openai-organization` (and `openai-project` when present) response
  headers, identity from those, lines `scope unavailable: set
  OPENAI_ADMIN_KEY` and a warning that verify can only check that the
  pasted key works in the same organization.
- `create_replacement`: re-find the key, `POST .../service_accounts` named
  `rotate-<fp>` in its project. Refuses without an admin key.
- `verify`: `GET /v1/models` with the new key, then with an admin key, the
  new key must be in the identity project's key listing; without one, the
  organization header must match.
- `revoke`: re-find the key; user key, DELETE `api_keys/{id}`; sole key of a
  service account, DELETE `service_accounts/{sa_id}`; 404 Ok. Otherwise, or
  without an admin key, `Unsupported` with no call.
- `restore`: `Ok(Unsupported)`. `revoke_replacement`: DELETE the service
  account named in the ref; 404 Ok.
- `manual_instructions`: create a key in the same project at
  platform.openai.com/api-keys.

Shared, minimal:

- `Provider::manual_revoke(&self, scope: Option<&Scope>) -> Option<&'static
  str>` (default `None`) in `src/provider/mod.rs`; `plan::build` uses it
  for the revoke row and adds a blocker. Two lines in `src/plan.rs`; no
  change to `src/apply.rs`.
- Conformance: `idempotent_revoke` and `restore_outcome` report `Skipped`
  when the first revoke is `Unsupported`, so the suite runs in manual mode.
- `src/config.rs`: `providers.openai.api_url` (default
  `https://api.openai.com`).
- `src/providers.rs`: register `OpenAiProvider` in release builds.

## Secret handling

The leaked key signs `GET /v1/models` only. The admin key signs the Admin
API calls only. The new key signs `GET /v1/models` in `verify` only. No
value goes into a request body, URL, error, scope line, ref, log or file.
Matching uses `redacted_value` from OpenAI; rotate never prints any part of
a key.

Unit tests in `src/provider/openai.rs`; integration tests in
`tests/openai_provider.rs` against `CallRecorder` (DELETE and POST are
mutating; every check is a GET).

- T1 (AC1): `identify_prefixes_and_not_others` (unit).
- T2 (AC2): `check_valid_maps_status`.
- T3 (AC3): `describe_scope_matches_redacted_value`.
- T4 (AC4): `no_admin_key_scope_message_and_manual_mode` (unit) and
  `manual_scope_reads_org_header` (wiremock).
- T5 (AC5): `create_replacement_posts_service_account`.
- T6 (AC6): `revoke_deletes_user_key_with_admin_bearer`, 404 Ok.
- T7 (AC7): `undeletable_key_plan_row_and_no_delete_after_apply`.
- T8 (AC8): `restore_unsupported` (unit).
- T9 (AC2, AC5, AC6): `keys_never_in_output_logs_audit_or_state`: plan and
  full apply at TRACE; leaked, new and admin key absent from table, JSON,
  summary, terminal, logs, audit, state, outcome; on the wire each key only
  in the Authorization header of its allowed calls.
- T10 (AC1 to AC8): `conformance_automatic_mode` and
  `conformance_manual_mode`.
- Plan safety: `plan_makes_no_state_changing_calls`.
- Extras: service-account revoke, `revoke_replacement`, ambiguity, admin
  key equal to leaked key, registration.
- Live (`#[ignore]`, `live_` prefix, `ROTATE_LIVE_TESTS=1`):
  `live_openai_check_valid` (read-only) and `live_openai_rotate_cycle`
  (admin key: create a replacement, verify, then `revoke_replacement`).

## Risks

- OpenAI may change `redacted_value` formatting; the matcher accepts `...`
  and `*` masks and the live test catches drift.
- A key whose permissions were restricted gets an unrestricted replacement.
- Manual mode and undeletable keys end apply at the revoke step with
  `Unsupported`; a "manual revoke" outcome belongs in the executor
  (SHA-258).

## Out of scope

Admin key rotation, usage and billing data, legacy keys outside projects.
