# Implementation plan: SHA-222 Consumer trait, registry and MockConsumer

Ticket edits applied with this plan:

- `update` and `restore` both take `&Credential` (the new and the old one)
  instead of `&Replacement` and `&SecretValue`. An AWS rotation changes the
  access key id as well as the secret, so restoring an `AWS_ACCESS_KEY_ID`
  consumer needs the old key id, which a bare `SecretValue` does not carry.
  A credential also covers manual mode (D1), where the operator pastes the
  replacement and no `Replacement` exists.
- `ConsumerMatch` gains `holds: Holds { Secret, KeyId, KeyPair }`. Decision D4
  maps `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` to two separate
  Actions secrets. A Secrets Manager JSON entry can hold both. `update` writes
  the part the match holds, and `ConsumerMatch::value_fingerprint` gives real
  consumers and the mock one rule for which fingerprint a consumer stores.
- `SecretRef` carries `key_id: Option<String>` next to the fingerprint, so a
  consumer can match the key-id half (it is not secret).
- Failure injection adds `fail_for(method, consumer_ref, error)` next to
  `fail_next` and `fail_always`, because AC5 targets the second of two matches.
- `update` on a match marked not updatable returns
  `ConsumerError::NotUpdatable` with the same reason. A real consumer must do
  the same; the engine refusing is not enough.

## Approach

`src/consumer/mod.rs` holds the trait, value types, `ConsumerError`,
`MUTATING` and `ConsumerRegistry`. `src/consumer/mock.rs` holds
`MockConsumer`. It mirrors `src/provider/` so the two read the same way. Both
write to `calls::CallLog`, so a single log can prove a dry run made no
mutating calls across providers and consumers.

`ConsumerError` is its own type rather than a reuse of `ProviderError`. It
has the same retry classification plus `NotUpdatable`, which has no provider
equivalent.

Rejected: building the D4 name-convention table into the trait. Which names
to look for depends on the provider and on `rotate.yaml` (SHA-214). The
engine (SHA-250) builds the list into `SecretRef::names`, and consumers only
read it. Rejected: serde derives on `ConsumerMatch` now. The state file
(SHA-220) and plan JSON (SHA-250) will choose their own stable schema.

## Changes

- `src/consumer/mod.rs`:
  - `pub const MUTATING: &[&str] = &["update", "restore"]`, `pub fn is_mutating(&str) -> bool`.
  - `pub struct SecretRef { pub provider: String, pub fingerprint: Fingerprint, pub key_id: Option<String>, pub names: Vec<String> }`, with `SecretRef::new(provider, &Credential)` and `.with_names(..)`. Holds no value.
  - `pub enum MatchMethod { ByValue, ByName }` (FR11: Actions secrets are always `ByName`).
  - `pub enum Holds { Secret, KeyId, KeyPair }`.
  - `pub struct NotUpdatable { pub reason: String }`: `Display` is the reason, unchanged.
  - `pub struct ConsumerMatch { pub consumer_ref: String, pub match_method: MatchMethod, pub holds: Holds, pub updatable: Result<(), NotUpdatable> }` with `is_updatable()` and `value_fingerprint(&Credential) -> Result<Fingerprint, ConsumerError>`. `KeyId` fingerprints the key id, `Secret` and `KeyPair` fingerprint the secret, and `KeyId` against a `Token` is `Unsupported`.
  - `pub struct UpdateReceipt { pub consumer_ref: String, pub version: Option<String> }` (Secrets Manager version id; `None` for Actions).
  - `pub enum ConsumerError { RateLimited { retry_after }, Transient(String), Permanent(String), Unsupported(String), NotUpdatable(NotUpdatable) }` via `thiserror`, plus `is_retryable()`.
  - `#[async_trait] pub trait Consumer: Send + Sync { fn name(&self) -> &'static str; async fn find(&self, secret: &SecretRef) -> Result<Vec<ConsumerMatch>, ConsumerError>; async fn update(&self, target: &ConsumerMatch, new: &Credential) -> Result<UpdateReceipt, ConsumerError>; async fn restore(&self, target: &ConsumerMatch, old: &Credential) -> Result<(), ConsumerError>; }`.
  - `pub struct ConsumerRegistry`: `new`, `register(Arc<dyn Consumer>)`, `get`, `names`, `iter`, and `find_all(&SecretRef) -> Vec<ConsumerFindings>`. Each consumer is asked in registration order, and one consumer's error is kept next to the others' results rather than stopping the loop (`ConsumerFindings { consumer: &'static str, result }`).
- `src/consumer/mock.rs`:
  - `MockConsumer::new(name)`, `.matching(fingerprint, ConsumerMatch)` (repeatable; `find` returns every match registered for the fingerprint, in order), `.log(CallLog)`, `call_log()`, `fail_next`, `fail_always`, `fail_for(method, consumer_ref, error)`.
  - Helpers `ConsumerMatch::by_value(ref)`, `::by_name(ref)`, `.holding(Holds)`, `.not_updatable(reason)` (in `mod.rs`, usable by real consumers' tests too).
  - In-memory `current: HashMap<consumer_ref, Fingerprint>`, seeded with the match's fingerprint when it is registered. `update` sets it to `target.value_fingerprint(new)`, and `restore` to `value_fingerprint(old)`. `current(ref) -> Option<Fingerprint>` is how tests read it.
  - Every method records `Call { target: name, method, mutating, fingerprint }` first (`find` records the `SecretRef` fingerprint, `update` the new credential's, `restore` the old's), then checks per-ref, queued and standing failures in that order. `update` then refuses a not-updatable match.
  - `Debug` prints name, call count and the `current` fingerprints.
- `src/lib.rs`: `pub mod consumer;`.
- `tests/consumer_leak.rs`: T6.
- `CONTRIBUTING.md`: "Adding a consumer" section after "Adding a provider".

## Secret handling

Neither `SecretRef`, `ConsumerMatch`, `UpdateReceipt` nor `NotUpdatable`
holds a value. The mock stores fingerprints only and drops each credential
when the call returns. `consumer_ref` and `reason` strings reach the plan
and the audit log, so CONTRIBUTING says a real consumer must never put a
value in them. The SHA-218 redaction layer is the backstop.

## Test mapping

Unit tests are in `src/consumer/mock.rs` and `src/consumer/mod.rs`, using `#[tokio::test]`.

- T1 (AC1): `find_returns_both_matches_non_mutating`.
- T2 (AC2): `not_updatable_reason_round_trips` (also through `ConsumerError` when `update` is attempted).
- T3 (AC3): `update_stores_replacement_fingerprint_mutating`.
- T4 (AC4): `restore_puts_old_fingerprint_back`.
- T5 (AC5): `fail_for_second_match_only`: first `Ok`, second the injected error, log length 2, `current` changed only for the first.
- T6 (AC3, AC4): `tests/consumer_leak.rs::secret_never_reaches_recorder_or_logs`. A canary old value and replacement go through `find`, `update` and `restore` on a `KeyPair` match and a `KeyId` match under `LogCapture`. Asserts that neither value appears in `{:?}` of the mock, matches, receipts, errors, the call log or tracing, and that the fingerprints do.
- Extras: `key_id_match_stores_key_id_fingerprint`, `key_id_match_rejects_token`, `queued_then_standing_failures`, `registry_find_all_keeps_errors_per_consumer`, `registry_get_and_names`, `error_retryable_classification`, `mutating_list_matches_contract`, `shared_log_with_mock_provider` (one `CallLog` across a `MockProvider` and a `MockConsumer`; `assert_no_mutations` after `check_valid` plus `find` passes).

## Sequence

1. Value types, `ConsumerError`, `MUTATING`, `value_fingerprint`; extras green.
2. Trait and `MockConsumer` without failure injection; T1 to T4.
3. Failure injection; T5 and failure extras.
4. `ConsumerRegistry`; registry extras and the shared-log extra.
5. `tests/consumer_leak.rs` T6; CONTRIBUTING; fmt, clippy, test, deny; PR.

## Risks and unknowns

- `Holds` is decided by each consumer at `find` time. GitHub Actions will
  decide it from the secret name (SHA-253), and Secrets Manager from the JSON
  key that matched (SHA-252). If a consumer stores something else, such as a
  connection string, it is reported `NotUpdatable` with a reason.
- `Result<(), NotUpdatable>` in a struct field is awkward to serialize. That
  is deferred to SHA-220 and SHA-250, which may map it to their own schema.

## Out of scope

Real consumers (SHA-252, SHA-253), D4 name tables and `rotate.yaml` mappings
(SHA-214, SHA-253), the engine and planner (SHA-250, SHA-254), the
conformance suite (SHA-249).
