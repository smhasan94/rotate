# SHA-292: npm, make the operator token requirement match npm

Ticket: SHA-292 (parent SHA-191). Blocked by SHA-270 (merged).

## Research outcome

Question: can an npm granular access token (GAT), with or without 2FA
bypass, call `GET /-/npm/v1/tokens` (list) and
`DELETE /-/npm/v1/tokens/token/{key}` (delete)?

Answer: **no for the list, whatever the token's settings.** The delete is
open to a GAT without 2FA bypass, but rotate deletes by the id it reads
from the list, so a GAT cannot drive revoke on its own. The operator token
stays an `npm login` session token. This is the ticket's "if no" branch.

| Token kind | `GET /-/npm/v1/tokens` | `DELETE /-/npm/v1/tokens/token/{key}` |
| --- | --- | --- |
| `npm login` session token (two hours) | yes | yes; `npm-otp` header needed when the account has 2FA |
| Granular access token, no 2FA bypass | no | yes, with `npm-otp` when the account has 2FA |
| Granular access token with `bypass_2fa` | no | no: 403 Forbidden (since 2026-07-31) |
| Classic (automation, publish, read-only) | revoked by npm on 2025-12-09 | revoked |

Sources (read 2026-10-04; no call was made to the real registry):

1. npm Registry API reference, https://api-docs.npmjs.com/ . List tokens,
   "Authorizations: npmSessionToken", "Only accepts `npmSessionToken`".
   Delete token, "Authorizations: npmSessionToken, npmAccessToken,
   granularAccessToken"; "`npm-otp` header required if user has 2FA
   enabled"; "Granular Access Tokens with `bypass_2fa: true` are not
   permitted", answered with 403 Forbidden; "Token deletion requires an
   interactive 2FA challenge".
2. GitHub changelog, 2026-07-31, "Restricting npm bypass-2FA granular access
   tokens",
   https://github.blog/changelog/2026-07-31-restricting-npm-bypass-2fa-granular-access-tokens/ .
   Bypass-2FA GATs can no longer perform "Creating or deleting tokens",
   among other account, org and package management actions.
3. GitHub community discussion #201329, "Upcoming changes to npm 2FA-bypass
   granular access tokens (GATs)",
   https://github.com/orgs/community/discussions/201329 . Same list,
   announced ahead of the change.
4. GitHub changelog, 2025-12-09, "npm classic tokens revoked, session-based
   auth and CLI token management now available",
   https://github.blog/changelog/2025-12-09-npm-classic-tokens-revoked-session-based-auth-and-cli-token-management-now-available/ .
   `npm login` now gives "a two-hour session token"; classic tokens are
   revoked.
5. GitHub changelog, 2025-11-05, "npm security update: Classic token
   creation disabled and granular token changes",
   https://github.blog/changelog/2025-11-05-npm-security-update-classic-token-creation-disabled-and-granular-token-changes/ .
   Write GATs enforce 2FA by default, "Bypass 2FA" is opt-in, write GATs
   last at most 90 days.
6. npm docs, "About access tokens", https://docs.npmjs.com/about-access-tokens/ ,
   and `npm token`, https://docs.npmjs.com/cli/v11/commands/npm-token .
   Neither says which token kinds may manage tokens; source 1 is the only
   one that does, and it agrees with what the code saw in SHA-261 and
   SHA-270.

Uncertainty: source 1 is npm's own API reference and is explicit, so the
verdict is firm for the public registry. Other registries
(`providers.npm.registry`) may differ; rotate still reports their 401 or
403 on the list as "needs a session token".

Consequence for the brief: npm revoke cannot run unattended from a GitHub
Action. A session token lasts two hours and cannot be minted
non-interactively, so an unattended run needs a fresh `npm login` (by a
person) shortly before it.

## Changes ("if no" branch)

Code stays on the session token. What changes:

1. `Provider::revoke_blocker(&self, credential, scope) -> Option<String>`,
   a new pure trait method (default `None`, no network) for "apply will
   fail at revoke" conditions the provider can see from its configuration
   and the scope read. `PlannedRotation` gets a `revoke_blocker` field;
   `plan::blockers` appends it, so `--check-permissions` keeps it when it
   recomputes blockers.
2. `NpmProvider::revoke_blocker`:
   - no operator token: blocker naming `ROTATE_NPM_TOKEN`, the required
     kind (`npm login` session token, not a granular access token), the
     two-hour expiry and the need for a fresh `npm login` for unattended
     runs (AC2);
   - operator token is the leaked token: blocker (decision D3);
   - the list refused the operator token (401 or 403): blocker naming the
     kind needed (AC3).
3. The scope line for a refused list names the kind needed and the expiry
   (AC3). The 403 for a 2FA-bypass GAT on delete keeps naming the page to
   delete the token by hand.
4. One sentence, `npm::OPERATOR_REQUIREMENT`, is the token-kind sentence in
   `docs/permissions.md`, `docs/providers.md` and `docs/backlog.md` (AC4).
   The backlog gets an SHA-292 row and a note correcting the SHA-261 text
   that said an automation or granular token is enough. README: only the
   npm sentence, minimally.
