# Implementation plan: SHA-389 release attestations

The release workflow publishes build provenance for the four tarballs and
`SHA256SUMS`, and the release checks, the README and the GitHub Action
verify it with `gh attestation verify`. Today the only check is the
checksum, and `SHA256SUMS` comes from the same release as the tarball, so
it catches corruption but not replaced assets.

## Findings

- `actions/attest-build-provenance` v4.2.2 (2026-08-06, commit
  `4d101475d8b20a2381f78447822ac1eab6504dd8`, a lightweight tag) takes
  exactly one of `subject-path` (globs or a list), `subject-digest` with
  `subject-name`, or `subject-checksums` (a `sha256sum`-format file). It
  wraps `actions/attest` and needs `id-token: write` and
  `attestations: write`. A job's `permissions:` replaces the workflow's,
  so the job also lists `contents: read`.
- `gh attestation verify <file> --repo OWNER/REPO` fetches the
  attestations for the file's sha256 from the GitHub API and checks them
  against Sigstore public good. `--signer-workflow
  [host/]owner/repo/path/to/workflow` pins the workflow that signed (a
  prefix match on the certificate's SAN, host github.com by default),
  `--source-ref refs/tags/vX.Y.Z` pins the ref it ran on, and
  `--deny-self-hosted-runners` refuses attestations made on self-hosted
  runners. gh reads the token from `GH_TOKEN` and the host from `GH_HOST`;
  nothing goes on the command line. gh 2.101 is current; older gh may lack
  `attestation` or one of these flags.
- `action/install.sh` downloads the tarball and `SHA256SUMS` into a
  `mktemp -d` directory that an `EXIT` trap removes, checks the checksum,
  then installs and runs the binary. `action.yml`'s install step gets its
  inputs through `env:`; the inputs step runs `run.sh --check-inputs`
  first, which is where every other input is validated (exit 2, one line
  naming the input, never the value).
- `tests/action.rs` runs `install.sh` against wiremock with
  `ROTATE_RELEASE_BASE`, using the crate version (0.3.0) and the real
  `PATH`; T8 checks every action.yml input has a docs table row.
- Releases v0.1.0 to v0.3.0 have no attestations. The `verify` job runs
  `scripts/verify-release.sh` with `GH_TOKEN` already in its environment;
  `action-install` runs `install.sh` on the published release.
- A runner on GitHub Enterprise Server or GHE.com gets a `github.token` for
  that host, which cannot read attestations on github.com.

## Decisions

- A separate `attest` job, tag pushes only (`if: github.event_name ==
  'push' && github.ref_type == 'tag'`), `needs: [version, checksums]`,
  holding `id-token: write`, `attestations: write` and `contents: read`;
  no other job and not the workflow gets either. It downloads the tarballs
  and `SHA256SUMS`, checks `sha256sum -c` and that exactly four tarballs
  are listed, then runs the action twice, pinned by SHA with a `# v4.2.2`
  comment: `subject-checksums: dist/SHA256SUMS` (the four tarballs) and
  `subject-path: dist/SHA256SUMS`. `publish` needs `attest`, so a failed
  attestation publishes nothing. Pull requests skip it.
- The verify command, everywhere:

  ```sh
  GH_HOST=github.com gh attestation verify <tarball> \
    --repo smhasan94/rotate \
    --signer-workflow smhasan94/rotate/.github/workflows/release.yml \
    --source-ref refs/tags/vX.Y.Z \
    --deny-self-hosted-runners
  ```

- Version gate: a release is attested when its version without the
  pre-release suffix is greater than 0.3.0 (so `0.4.0-rc.1` and `0.3.1`
  are, `0.3.0` and `0.3.0-rc.1` are not). No API probe.
- `install.sh` gets `ROTATE_VERIFY_ATTESTATION` (`auto`, `true`, `false`;
  empty means `auto`; anything else exit 2 naming the input). Before any
  download it works out why the attestation cannot be checked, if at all,
  in this order: the version is 0.3.0 or older; the runner is not on
  github.com (`GITHUB_SERVER_URL`); `gh` is not on `PATH`; `gh attestation
  verify --help` fails or lacks `--signer-workflow` or `--source-ref`.
  `true` with a reason: exit 2 before downloading. `auto` with a reason: a
  `::notice` after the checksum passes, naming the reason and saying the
  checksum was checked. Otherwise, after the checksum, the verify command
  above (gh's output to stdout); failure: `attestation check failed for
  <tarball>; nothing was installed`, exit 1, and the trap removes the
  download before anything is extracted. `false`: no check, no notice.
  `rotate-binary` skips the whole download, attestation included.
- `action.yml`: input `verify-attestation` (default `auto`); the inputs
  step passes it as `VERIFY_ATTESTATION` and `run.sh` checks it like
  `upload-audit`; the install step passes it as
  `ROTATE_VERIFY_ATTESTATION` and `GH_TOKEN: ${{ github.token }}` in
  `env:`.
- `scripts/verify-release.sh`: after the checksums, the verify command for
  each of the four tarballs and `SHA256SUMS`; a missing or bad attestation
  fails the script. For 0.3.0 and older it says there are none and goes
  on, so old releases can still be re-verified. `action-install` sets
  `ROTATE_VERIFY_ATTESTATION: "true"` and `GH_TOKEN`, so the release run
  proves the Action path end to end.
- README: the tested install block stays checksum-only; an optional
  `gh attestation verify` command follows it, for 0.4.0 and later.

## Steps

1. Tests first (`tests/action.rs`), failing.
2. `run.sh` input check, `install.sh` mode, reason, notice and verify.
3. `action.yml` input and env.
4. `release.yml`: `attest` job, `publish` needs it, `action-install` env,
   header comment; `scripts/verify-release.sh`.
5. Docs: README, `docs/github-action.md` (input row, the download-check
   paragraph, limits), `docs/releasing.md` (job table, verifying a
   release), `docs/backlog.md` row.
6. fmt, clippy, test, deny, actionlint.
