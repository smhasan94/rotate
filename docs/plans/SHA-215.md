# Implementation plan: SHA-215 Release workflow for Linux and macOS binaries

Ticket edits applied with this plan:

- The workflow also runs on `pull_request` (only when `release.yml` or
  `ci/release-version.sh` change) and on `workflow_dispatch`. Those runs
  build, smoke-test, package and checksum all four targets but never
  publish. This is how the PR proves the build half without a tag.
- A `verify` job runs after each publish and does T1 to T3 against the real
  release: five assets, `sha256sum -c --ignore-missing` on the Linux x86_64
  tarball, and `./rotate --version` ends with the version.
- T1 to T4 need a tag push, which the repo owner does: `v0.0.1` for T1 to
  T3, and `v9.9.9` (deleted afterwards) for T4. The version check itself is
  a script tested locally for both cases.

## Approach

One workflow, `.github/workflows/release.yml`, five jobs:

1. `version`: `ci/release-version.sh` reads `version` from `[package]` in
   `Cargo.toml`. On a tag push it fails unless the tag is `v<version>`
   (AC4). Every other job depends on it, so a mismatch uploads nothing.
2. `build`: matrix over the four targets, each on a native runner so the
   binary can run: `x86_64-unknown-linux-gnu` on `ubuntu-22.04`,
   `aarch64-unknown-linux-gnu` on `ubuntu-22.04-arm` (22.04 for an older
   glibc), `x86_64-apple-darwin` on `macos-15-intel`, `aarch64-apple-darwin`
   on `macos-latest`. `cargo build --release --locked --target <t>`, no
   features (so `test-providers` never ships), then `rotate --version` must
   end with the version (AC3 on every run). Packs
   `rotate-<version>-<target>.tar.gz` with `rotate`, `LICENSE` and
   `README.md` at the top level and uploads it as a workflow artifact.
3. `checksums`: downloads the four tarballs, writes `SHA256SUMS`, checks it
   with `sha256sum -c`, uploads it.
4. `publish` (tag push only): `gh release create <tag> --verify-tag
   --generate-notes` with the four tarballs and `SHA256SUMS` (AC1).
5. `verify` (tag push only): downloads from the release and checks AC1 to
   AC3.

Security: top-level `permissions: contents: read`; only `publish` gets
`contents: write`. No cache action in the release path (cache poisoning).
The tag reaches scripts through `env`, never through `${{ }}` inside `run`.

Rejected: `cross` or a cross linker for aarch64 Linux. Native arm runners
are free for public repos and let the smoke test run. Rejected:
`softprops/action-gh-release`. The `gh` CLI is already on the runner and
keeps third-party code out of the job that holds write access.

## Changes

- `.github/workflows/release.yml`: the five jobs above; `concurrency`
  per ref, never cancelled.
- `ci/release-version.sh`: prints `version=<v>` for `$GITHUB_OUTPUT`;
  with a tag argument, exits 1 and names both versions on a mismatch.
- No README change here: SHA-213's README already says binaries come from
  GitHub Releases, and install steps belong with the first real release.
  The tarball includes `README.md` only if it exists, so the two PRs can
  merge in either order.

## Test mapping

- T1 (AC1): `verify` job counts five assets. Owner pushes `v0.0.1`.
- T2 (AC2): `verify` job runs `sha256sum -c --ignore-missing`. Also
  `checksums` checks every tarball on every run, including the PR.
- T3 (AC3): `build` runs `--version` on every target on every run; `verify`
  runs it on the downloaded Linux x86_64 tarball.
- T4 (AC4): `ci/release-version.sh` run locally with `v0.0.1` (passes) and
  `v9.9.9` (fails). Owner pushes `v9.9.9` once, sees the `version` job fail
  and no release, then deletes the tag.

## Out of scope

Signing, notarization, Homebrew, cargo-binstall, Windows.
