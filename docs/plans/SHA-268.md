# Implementation plan: SHA-268 live tests for AWS and GitHub

wiremock proves the code matches what we believe STS, IAM, Secrets Manager
and the GitHub REST API do (`tests/e2e_aws.rs`, `tests/acceptance_mvp.rs`,
`tests/leakage.rs`). This ticket proves the belief against the real
services, behind `ROTATE_LIVE_TESTS=1`, with a dispatch-only workflow and a
page describing the throwaway accounts. The ticket was written on
2026-09-30; the tree has moved since, so the plan starts from what exists.

Already in the tree, found while planning:

- `tests/common/mod.rs` has `live_enabled`, `require_env` and the
  `live_guard!` macro (SHA-216). `tests/live_smoke.rs` is a gate smoke test
  only, and `ci.yml` greps for it by name.
- Eleven `live_*` tests exist beyond the smoke test, each `#[ignore]` and
  guarded: `live_aws_check_valid_and_scope` and `live_aws_rotate_round_trip`
  (`tests/aws_provider.rs`, need a standing key pair in
  `ROTATE_LIVE_AWS_ACCESS_KEY_ID` / `ROTATE_LIVE_AWS_SECRET_ACCESS_KEY`),
  `live_secrets_manager_find_is_read_only` (`ROTATE_LIVE_SM_SECRET`),
  `live_github_actions_find` (`ROTATE_LIVE_GITHUB_REPO`),
  `live_github_check_valid_and_scope` (`ROTATE_LIVE_GITHUB_TOKEN`),
  `live_github_revoke` (`ROTATE_LIVE_GITHUB_REVOKE_TOKEN`), two npm and two
  OpenAI tests. Four of the files carry their own copy of a `live_env`
  helper that prints `skipped: <NAME> not set`.
- The real plugins can be driven through the `rotate` binary with a
  scenario file `{"real_plugins": true, "prompt": "panic"}` in
  `ROTATE_TEST_SCENARIO` (SHA-264). `cargo test --all-features` builds the
  binary with `test-providers`, which registers mocks unless that file says
  otherwise; without the feature the variable is ignored. The live tests
  always write it.
- The AWS provider and the Secrets Manager consumer take the operator
  credentials from `aws_config`'s default chain and the region from
  `providers.aws.region`, else `AWS_REGION`. The GitHub Actions consumer
  reads `ROTATE_GITHUB_TOKEN`, then `GITHUB_TOKEN`. GitHub rejects Actions
  secret names starting with `GITHUB_`, and `GITHUB_TOKEN` inside a job is
  the workflow token, so the live PAT travels as `ROTATE_GITHUB_TOKEN`.
- `tests/leakage.rs` has the `Sweep` (every canary in raw, URL-encoded, hex
  and base64 form, over buffers and directory trees) and
  `assert_private_state`; both are private to that binary.

## Decisions

1. The AWS live test drives the release binary (`assert_cmd::cargo::cargo_bin`,
   as `tests/e2e_aws.rs` does), not the library `Executor`: the point is to
   prove the shipped path, including config loading, `--confirm`, the audit
   log and the state file, against AWS. It runs `plan`, `plan
   --check-permissions`, `apply`, `status --all` and `rollback`. Rollback is
   not in the ticket's scope line, but it replaces the restore coverage of
   `live_aws_rotate_round_trip`, which this plan removes (see 5), and costs
   two more SDK assertions on keys the test already owns.
2. Two IAM users: the operator (whose static key is in `AWS_ACCESS_KEY_ID` /
   `AWS_SECRET_ACCESS_KEY`, AC2) and the target (`ROTATE_LIVE_AWS_USER`),
   which holds no key at rest. The test creates the "leaked" key on the
   target with the SDK, so the test is self-contained and D3 holds (rotate
   never signs an IAM call with the leaked key). A target with any key at
   start fails the test naming the key ids: it means an earlier cleanup did
   not finish, and the page says how to clear it by hand. Nothing is
   deleted that the test did not see created in this run or by rotate in
   this run.
3. The GitHub live test drives the Actions consumer as a library
   (`GithubActionsConsumer::from_config`, then `find`, `update`, `restore`).
   There is no GitHub-held secret the binary could rotate end to end without
   burning a token per run, and the binary path for this consumer is proven
   by `tests/acceptance_mvp.rs`. The value check is a `workflow_dispatch`
   run of a one-step workflow in the test repository that prints
   `fingerprint=sha256:<hex>`, the first 16 hex digits of the `SHA-256`
   digest of the named secret (the same shape as
   `rotate::secret::Fingerprint`), read back from the job's plain-text log
   endpoint. Alternatives rejected: `updated_at` on
   `GET .../secrets/{name}` proves a write, not the value; artifacts come
   back as zip (new dependency); step names cannot carry runtime values.
   Two dispatches per run (after update, after restore), each bounded to
   five minutes of polling.
4. Failure injection (AC6, T6) is in the test harness, not the binary. The
   harness runs the scenario under `catch_unwind`, always runs cleanup, and
   then either re-raises the panic (cleanup complete) or panics with the
   original message plus `left behind: ...` naming each key id or entry it
   could not clean. `ROTATE_LIVE_FAIL_AFTER` (`create` or `apply` for AWS,
   `update` for GitHub) makes the scenario panic at that point; T6 runs the
   same scenario with the injection forced from code, so it is a live test
   of its own and the variable stays for use by hand.
5. Consolidate the live tests. Removed as superseded: `tests/live_smoke.rs`,
   `live_aws_check_valid_and_scope`, `live_aws_rotate_round_trip` (needs a
   standing key and leaves a deactivated one behind, which would fill the
   target's second slot), `live_secrets_manager_find_is_read_only`,
   `live_github_actions_find`. Kept, as the manual checks the ticket asks to
   document: `live_github_check_valid_and_scope`, `live_github_revoke`, the
   two npm and the two OpenAI tests. Their four `live_env` copies move to
   `tests/common`. The ci.yml grep that names `live_smoke` becomes a count of
   every `live_` test reported ignored.
6. Variables. Credentials are secrets of the `live-tests` environment with
   the names the code already reads: `AWS_ACCESS_KEY_ID`,
   `AWS_SECRET_ACCESS_KEY`, and `ROTATE_LIVE_GITHUB_TOKEN`, which the
   workflow exports as both `ROTATE_GITHUB_TOKEN` (consumer) and
   `ROTATE_LIVE_GITHUB_TOKEN` (the kept provider check). Names are
   environment variables, not secrets: `AWS_REGION`, `ROTATE_LIVE_AWS_USER`,
   `ROTATE_LIVE_AWS_SECRET_ID`, `ROTATE_LIVE_GITHUB_REPO`. Optional with
   defaults: `ROTATE_LIVE_GITHUB_SECRET` (`ROTATE_LIVE_CANARY`),
   `ROTATE_LIVE_GITHUB_WORKFLOW` (`fingerprint.yml`).
7. Timeout. `timeout-minutes: 15` on the test step, as the ticket says; the
   job gets 30 so a cold `cargo build --all-features --tests` on a fresh
   cache cannot eat the test budget. `concurrency: live-tests`, never
   cancelling: two runs would fight over the target's two key slots. Within
   `tests/live_aws.rs` a `static SERIAL: Mutex<()>` serialises the two
   key-creating tests; cargo runs test binaries one after another, so the
   command in CLAUDE.md needs no `--test-threads=1`.
8. No new dependencies: the SDK crates, `reqwest`, `regex`, `base64`,
   `urlencoding` and `tokio` are already available to integration tests.
   `cargo deny` is unchanged. Rust toolchain in the workflow is
   `dtolnay/rust-toolchain@stable`, as in `ci.yml`.

### `tests/live_aws.rs`

`LiveAws` holds the names from the environment, an IAM, a Secrets Manager
and an STS client built with `aws_config::defaults(BehaviorVersion::latest())`
from the test process environment, a temp root (`work/`, `inputs/`, `home/`,
`tmp/`), the `Sweep` canaries (operator secret, leaked secret, later the
replacement), every run's stdout and stderr, and a `Cleanup` record:
`keys: Vec<String>` (key ids on the target to delete) and
`entry: Option<SecretValue>` (the entry's original `SecretString`, to put
back).

`run_scenario(fail_after: FailAfter) -> Result<(), String>` builds a tokio
runtime, runs the scenario under `catch_unwind(AssertUnwindSafe(..))`, runs
`cleanup()` (delete every key id recorded plus every key `ListAccessKeys`
now shows on the target, put the original value back when `entry` is set,
remove the temp root), and decides: panic re-raised when cleanup left
nothing; `"<original message>; left behind: <list>"` when it did; a plain
panic naming the leftovers when the scenario passed but cleanup failed.
Nothing prints raw child output before the sweep has passed on it.

The scenario:

1. `ListAccessKeys(target)` must be empty, else fail naming the ids.
   `GetSecretValue(entry)` keeps the original string.
2. `CreateAccessKey(target)`; record the id. Poll `GetCallerIdentity`
   signed with the new pair every 2 s for up to 60 s until it succeeds
   (IAM propagation; otherwise `rotate plan` would report it invalid).
3. `PutSecretValue(entry, {"AWS_ACCESS_KEY_ID", "AWS_SECRET_ACCESS_KEY",
   "DATABASE_HOST": "db.internal"})`; mark the entry for restore.
4. Write `inputs/report.ndjson` from `tests/fixtures/trufflehog_aws_e2e.ndjson`
   with `@KEY_ID@`/`@SECRET@` substituted (the only plaintext on disk,
   0600 inside a 0700 temp dir, never swept, removed at cleanup),
   `work/rotate.yaml` (`consumers.aws_secrets_manager.secrets: [<entry>]`,
   `providers.aws.region: <AWS_REGION>`) and `inputs/scenario.json`.
   `FailAfter::Create` panics here.
5. `rotate plan report.ndjson`, exit 0: the table has `identity:
   arn:aws:iam::<account>:user/<target>`, the consumer ref
   `aws-secrets-manager:<entry>#$.AWS_SECRET_ACCESS_KEY|$.AWS_ACCESS_KEY_ID`
   and `by value`. Afterwards `ListAccessKeys` still shows the one Active
   key and `GetSecretValue` the same `VersionId`: the dry run changed
   nothing, measured on the service.
6. `--json plan report.ndjson --check-permissions`, exit 0, `blockers: []`.
   This checks the policy in `docs/live-tests.md` live, so the entry must be
   given as an ARN (a name is not simulated; `docs/permissions.md`).
7. `apply report.ndjson --confirm <id>`, exit 0 (default overlap `0s`).
   `ListAccessKeys`: the leaked key Inactive and exactly one other key
   Active; record its id. `GetSecretValue`: `AWS_ACCESS_KEY_ID` is the new
   id, `AWS_SECRET_ACCESS_KEY` differs from the leaked secret and is 40
   chars, `DATABASE_HOST` kept. The replacement secret, which only the entry
   can tell the test, becomes a canary and every output collected so far is
   swept again. Audit: `plan`, `create`, `update`, `verify`, `revoke`, all
   `ok`, `fingerprint` of the leaked secret and `replacement_fingerprint` of
   the new one. State: `step` is `revoked`.
8. `status --all`, exit 0, the row says `revoked`. `FailAfter::Apply` panics
   here.
9. `rollback report.ndjson --confirm <id>`, exit 0: leaked key Active,
   replacement Inactive, the entry holds the leaked pair with
   `DATABASE_HOST`, state `rolled_back`, every `rollback` audit entry `ok`.

The child runs like `E2e::run`: `env_clear`, `HOME=<root>/home` with empty
`AWS_CONFIG_FILE` and `AWS_SHARED_CREDENTIALS_FILE`, the operator key pair
and `AWS_SESSION_TOKEN` when set, `AWS_REGION`,
`AWS_EC2_METADATA_DISABLED=true`, `ROTATE_ACTOR=live-tests`,
`ROTATE_TEST_SCENARIO`, `RUST_LOG=trace`, `TMPDIR=<root>/tmp`,
`SSL_CERT_FILE` when set, `-vvv`, stdin null, cwd `work/`. After every run:
sweep stdout, stderr and `scan_dir(root, skip [inputs/])`, then
`assert_private_state(work)`.

Tests in the file: `live_aws_rotate_end_to_end` (`FailAfter::from_env()`),
`live_aws_cleanup_after_injected_failure` (forces `FailAfter::Create`,
expects `Err`, then asserts `ListAccessKeys(target)` is empty and the entry
holds its original string), and the non-ignored
`t2_skips_naming_the_missing_variable` (spawns
`std::env::current_exe()` with `--ignored --exact live_aws_rotate_end_to_end
--nocapture`, `env_clear`, `ROTATE_LIVE_TESTS=1`; asserts exit 0 and
`skipped: AWS_ACCESS_KEY_ID not set` on stderr). Variable order:
`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_REGION`,
`ROTATE_LIVE_AWS_USER`, `ROTATE_LIVE_AWS_SECRET_ID`.

### `tests/live_github.rs`

`live_github_actions_update_and_restore`: `live_guard!`, then
`ROTATE_GITHUB_TOKEN` and `ROTATE_LIVE_GITHUB_REPO` (skip naming the first
missing), the two optional names. A `LogCapture` subscriber is set for the
test. Canaries: `original` and `replacement` (32 random chars from
`sweep::canary`) and the PAT.

1. `ConsumersConfig` with `github_actions.targets = [repo]`;
   `GithubActionsConsumer::from_config(&consumers, &GithubConfig::default())`.
2. `find(SecretRef::new("npm", &Credential::Token(original)).with_names([name]))`
   returns one match: ref `github-actions:<repo>:<name>`, `ByName`,
   updatable. The provider name is arbitrary: the consumer never checks a
   value, only names.
3. `update(match, original)` seeds the value the test knows. From here the
   guard restores `original` on any failure.
4. `update(match, replacement)`; `fingerprint_via_dispatch(nonce)` equals
   `fp(replacement)`. `FailAfter::Update` panics here.
5. `restore(match, original)`; `fingerprint_via_dispatch(nonce)` equals
   `fp(original)`.
6. Sweep the captured log and the `Display` of every error and match for
   the three canaries.

`fingerprint_via_dispatch`, with a plain `reqwest::Client` (Bearer PAT,
`X-GitHub-Api-Version: 2022-11-28`, a `User-Agent`): `GET /repos/{repo}`
for `default_branch`; `POST
/repos/{repo}/actions/workflows/{file}/dispatches` with `{"ref", "inputs":
{"nonce", "secret_name"}}` (204); poll `GET
/repos/{repo}/actions/runs?event=workflow_dispatch&per_page=20` every 10 s
for at most 5 min for the run whose `display_title` is `fingerprint <nonce>`
and `status` is `completed` (its `conclusion` must be `success`); `GET
.../runs/{id}/jobs` for the job id; `GET .../jobs/{id}/logs`, which
redirects to plain text (reqwest drops `Authorization` on the cross-host
redirect); return the first `fingerprint=(sha256:[0-9a-f]{16})`. The log
holds the fingerprint only; GitHub masks the value itself as well.

`live_github_cleanup_after_injected_failure` forces `FailAfter::Update`,
expects `Err`, then one dispatch shows `fp(original)`. The non-ignored
`t2_skips_naming_the_missing_variable` spawns
`live_github_actions_update_and_restore` as above and expects `skipped:
ROTATE_GITHUB_TOKEN not set`.

## Maintainer setup

Provision these by hand before the first dispatch. Everything is throwaway
and scoped to the live tests; nothing here touches a real workload.

AWS, in one account and one region (`<account>`, `<region>`):

1. IAM user `rotate-live-target`, no policies, no keys. Only the test
   creates and deletes its keys. Its keys can call nothing but
   `sts:GetCallerIdentity`, which is all rotate's validity check needs.
2. Secrets Manager entry `rotate-live/e2e`, any string value (for example
   `{"placeholder": "rotate-live"}`); the test restores it. Note its ARN
   (`arn:aws:secretsmanager:<region>:<account>:secret:rotate-live/e2e-XXXXXX`).
3. IAM user `rotate-live-operator` with one access key (the workflow
   secrets) and this inline policy: the `docs/permissions.md` policy with
   each `Resource` narrowed, plus delete for cleanup.

   ```json
   {
     "Version": "2012-10-17",
     "Statement": [
       { "Sid": "RotateIamAccessKeys", "Effect": "Allow",
         "Action": ["iam:GetAccessKeyLastUsed", "iam:GetUser",
                    "iam:ListAttachedUserPolicies", "iam:ListUserPolicies",
                    "iam:ListGroupsForUser", "iam:ListAccessKeys",
                    "iam:CreateAccessKey", "iam:UpdateAccessKey"],
         "Resource": "arn:aws:iam::<account>:user/rotate-live-target" },
       { "Sid": "LiveTestCleanup", "Effect": "Allow",
         "Action": "iam:DeleteAccessKey",
         "Resource": "arn:aws:iam::<account>:user/rotate-live-target" },
       { "Sid": "RotateSecretsManagerEntries", "Effect": "Allow",
         "Action": ["secretsmanager:GetSecretValue", "secretsmanager:PutSecretValue"],
         "Resource": "arn:aws:secretsmanager:<region>:<account>:secret:rotate-live/e2e-*" },
       { "Sid": "RotateCheckPermissions", "Effect": "Allow",
         "Action": "iam:SimulatePrincipalPolicy",
         "Resource": "arn:aws:iam::<account>:user/rotate-live-operator" },
       { "Sid": "RotateWhoAmI", "Effect": "Allow",
         "Action": "sts:GetCallerIdentity", "Resource": "*" }
     ]
   }
   ```

   `LiveTestCleanup` is the harness's, not rotate's: rotate never calls
   `iam:DeleteAccessKey`.

GitHub:

4. A private repository `<owner>/rotate-live` with Actions enabled, a
   repository secret `ROTATE_LIVE_CANARY` (any value) and
   `.github/workflows/fingerprint.yml` on the default branch:

   ```yaml
   name: fingerprint
   run-name: fingerprint ${{ inputs.nonce }}
   on:
     workflow_dispatch:
       inputs:
         nonce: { description: "Set by the live test", required: true, type: string }
         secret_name: { description: "Repository secret to fingerprint", required: true, type: string }
   permissions: {}
   jobs:
     fingerprint:
       runs-on: ubuntu-latest
       timeout-minutes: 2
       steps:
         - env:
             VALUE: ${{ secrets[inputs.secret_name] }}
           run: printf 'fingerprint=sha256:%s\n' "$(printf '%s' "$VALUE" | sha256sum | cut -c1-16)"
   ```

5. A fine-grained PAT for that repository only: Actions read and write
   (dispatch, runs, logs), Secrets read and write, Metadata read. Set an
   expiry and note it; the preflight will name the variable when the token
   has expired and `find` fails.

