# Implementation plan: SHA-271 v0.1.0 release

The release workflow (SHA-215) already builds four tarballs, writes
`SHA256SUMS`, publishes on a `v*` tag and checks the x86_64 Linux asset.
This ticket adds the changelog, the version bump, release notes taken from
the changelog, a verify script run on Linux and macOS after publishing, and
README install steps that CI runs as written.

## Decisions (2026-10-04)

- No crates.io publish: the name `rotate` is taken by an unrelated crate.
  `publish = false` stays; the install path is GitHub Releases.
- AC3 is a smoke check. rotate checks validity with the leaked key itself,
  so the "missing operator credential" path needs a live key, which CI does
  not have. The smoke check uses `tests/fixtures/trufflehog.ndjson` (AWS
  documentation keys, which rotate reports invalid without a call; fake
  GitHub and npm tokens): exit 0, the dry-run line, every finding skipped,
  no panic, no fixture secret in the output.
- The tag is pushed only after this PR merges and with the maintainer's
  go-ahead. The workflow checks the tag matches `Cargo.toml`.

## Changes

- `CHANGELOG.md`, Keep a Changelog format: a 0.1.0 section with commands,
  providers, consumers, safety guarantees and known limits.
- `Cargo.toml` and `Cargo.lock`: 0.1.0.
- `ci/changelog-section.sh <version>`: prints that version's changelog
  section, without its heading. Fails when there is none. The publish job
  uses it as `--notes-file`, replacing `--generate-notes`.
- `scripts/verify-release.sh <tag>`: downloads the four tarballs and
  `SHA256SUMS`, checks there are exactly four sums and that every one
  verifies, extracts the host's tarball, checks `--version` is
  `rotate <version>`, then runs the smoke check.
- `scripts/readme-install.sh`: extracts the block between
  `<!-- install:start -->` and `<!-- install:end -->` in `README.md` and
  runs it with `bash -eu`, so CI runs exactly what users copy.
- `.github/workflows/release.yml`:
  - `verify` becomes a matrix (ubuntu-22.04 x86_64, macos-latest aarch64)
    that checks the five assets and that the notes contain the changelog
    heading (T1), then runs the verify script (T2, T3).
  - New `install` jobs run the README block in a `debian:bookworm-slim`
    container and on macOS (T4).
  - On pull requests the changelog extraction and README extraction run
    as a dry check, without a release.
- README: a status line for the release, and an Install section with the
  `curl` and checksum block. `docs/usage.md` Install points to it, with
  build-from-source kept as the alternative.
- `tests/user_docs.rs`: the changelog has a section for the `Cargo.toml`
  version, and the README install block names that version.

## After merge

1. Ask the maintainer, then tag `v0.1.0` on main and push the tag.
2. Watch the release workflow: publish, verify (both runners), install.
3. `gh release view v0.1.0 --json assets,body` as T1 by hand as well.
