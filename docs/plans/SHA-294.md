# Implementation plan: SHA-294 pre-release cleanup

Five small fixes found while writing the user docs (SHA-269) and the
SHA-293 sweep. The overlap window is the common case: after `rotate apply`
exits 3 with a pending revoke, a re-run and `status` must not look broken.

## 1. Ticket ids in `--help` (AC1, T1)

`src/cli.rs` doc comments become clap help. Drop every `(SHA-NNN)` from
`///` comments there. T1 (`tests/cli.rs`) runs `--help` and `-h` for the
root and every subcommand and fails on `SHA-\d+`.

## 2. Re-apply during the overlap window (AC2, T2)

Root causes, all in the plan a re-run builds:

- The AWS provider's `describe_scope` warns when both key slots are used.
  At `pending_revoke` the second key is the rotation's own replacement,
  recorded as `replacement_ref`. `assign_ids` knew the stored record but
  only copied its id and step.
- The plan lists what `find` matches now. The Secrets Manager entry is
  matched by value; it now holds the replacement, so it no longer matches
  the leaked secret and drops out.
- The `overlap:` row prints this run's window (`0s` by default), while
  apply keeps the recorded `revoke_not_before`.

Fix: `assign_ids` carries the stored record onto the plan
(`PlannedRotation::recorded`: consumers with their status and
`revoke_not_before`). Once the record has a replacement, scope `warning:`
lines naming its `replacement_ref` are replaced by a plain scope line
(`replacement: <ref>, created by rotation <id>`). The table marks consumers
with their recorded status (`updated (recorded)`) and adds recorded
consumers the plan did not find; at `pending_revoke` the overlap row shows
the recorded time and what is left of it. `--json` gains an optional
`recorded` object per rotation (`docs/plan-schema.json`, additive; version
stays 1). Apply's own behaviour does not change: it already used the
recorded consumers and time.

T2: `tests/leakage.rs` (`RealRun`, real AWS and GitHub plugins, canary
values): apply `--overlap 1h` (exit 3), plan and apply again (exit 3): no
two-key warning, three consumers, recorded revoke time, no new
`CreateAccessKey`; then with the clock past the window, apply revokes.
Unit half in `plan::tests`.

## 3. Pending revoke in `status` (AC3, T3)

Apply keeps writing the skipped `revoke` audit entry with "overlap window
open until ..." (it is a useful audit record). `status::rows` drops that
entry as a last error when the rotation is at `pending_revoke` and the
entry is a `skipped` revoke: the hint already says when the revoke is due.
A failed revoke (`failed` outcome, step `failed`) still shows. No JSON
field changes; the `error` description in `docs/status-schema.json` says
when it is null.

T3: `status::tests` unit test; integration in the T5 runs (status while
pending, then after the real failure).

## 4. `GITHUB_TOKEN` convention name (AC4, T4)

This amends decision D4 (consumer name conventions) in
`docs/requirements.md`: the GitHub convention no longer includes
`GITHUB_TOKEN`. Noted after merge, in SHA-298.

GitHub rejects Actions secret names starting with `GITHUB_`. Drop it from
`consumer_names` for GitHub, `docs/config.md`, `docs/usage.md`,
`docs/rotate.example.yaml` and D4 in `docs/requirements.md`. Operator token
variables (`src/github.rs` `TOKEN_VARS`) are unchanged. T4: unit test in
`plan::tests`, plus a sync test in `tests/user_docs.rs` comparing the
`config.md` table with `consumer_names`.

## 5. Resumed revoke error text (AC5, AC6, T5, T6)

`Executor::steps` already knows whether this process holds the verified
replacement: `held.remove(id)` returns it after verify in the same process,
and nothing when the run resumes at revoke. That decides an
`UpstreamText` passed to `finish`:

- `Redacted` (replacement alive and registered): today's behaviour
  (SHA-293).
- `Summary` (never held): a failed revoke keeps only
  `revoke_error_summary`: provider, kind of failure, the operation rotate
  named (`iam:...` or `METHOD /path`), the HTTP status, and a provider
  error code from a short allowlist; pattern-redacted; at most 200
  characters. An `Unsupported` revoke becomes revoke-by-hand with the
  generic instructions and that summary. This is what stdout,
  `revoke_instructions` and the audit entry get.

T5: unit test in `apply::tests` and `tests/leakage.rs` runs (mock npm
provider, error echoing the replacement, which no pattern matches):
resumed after the window (clock offset) and with `--wait` in a new
process, for a failed and a refused revoke; summary format asserted;
sweep clean. T6: `apply::tests::revoke_text_echoing_the_replacement_is_redacted`
unchanged and passing.

## T7

T2, T3 and T5 run under the leakage `Sweep` with canary values: stdout,
