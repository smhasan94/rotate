# Implementation plan: SHA-267 MVP acceptance test

The brief's "Success for MVP" paragraph as one CI test file,
`tests/acceptance_mvp.rs`: a TruffleHog report with a leaked AWS key that one
GitHub Actions repository (`acme/api`) and one Secrets Manager entry
(`prod/app`) hold. `rotate plan` shows the full plan and changes nothing;
`rotate apply` rotates end to end; the secret value appears nowhere.

Ticket edits applied with this plan:

- One Actions consumer, two matches. The Actions consumer (SHA-253) makes
  one ByName match per secret name, so `acme/api` holding both convention
  names gives two matches: `github-actions:acme/api:AWS_ACCESS_KEY_ID`
  (holds `key_id`) and `github-actions:acme/api:AWS_SECRET_ACCESS_KEY`
  (holds `secret`), plus the Secrets Manager ByValue match. AC1 asserts
  these three rows. AC3 "update (two, one per consumer)" becomes three
  `update` entries, one per match, each naming its `consumer`, so both
  consumers are covered. AC4 "consumers 2/2" becomes 3/3 (three matches).
- AC4 (`rotate status --all`): `rotate status` is still a stub on main and
  SHA-263 builds it in parallel. As in SHA-264, T4 asserts the state record
  the status command reads (step `revoked`, no pending revoke, all three
  consumers `updated`), and `t4_status_all_shows_revoked` runs the command
  and asserts the row, `3/3` and exit 0. It is `#[ignore]`d with "needs
  `rotate status` (SHA-263)"; SHA-263 removes the ignore.
- AC6 re-run. SHA-258 holds the replacement value only inside the process
  that created it; rotate never stores it. A re-run in a new process after
  a failed consumer update therefore cannot write the Actions secret: it
  marks the rotation `needs_rollback`, makes no state-changing call and
  exits 1 (SHA-258 AC6). The CLI cannot "update only the Actions secret and
  then revoke" without storing the secret, which the safety rules forbid.
  T6 follows the recovery path rotate actually offers:
  1. 403 on the Actions PUT: exit 1, summary "stopped before revoke", old
     key Active, no `UpdateAccessKey`, Actions secrets unchanged.
  2. Fix the model, re-run apply: exit 1, step `needs_rollback`, zero
     mutating requests, old key still Active.
  3. `rotate rollback --confirm <id>`: exit 0, consumers restored, the
     replacement deactivated, the old key Active.
  4. The inactive replacement still counts toward IAM's two-key limit, and
     rotate never deletes a key, so the test deletes it in the model, as an
     operator would in the console, then plans and applies again: a fresh
     replacement, one PUT per Actions secret, then the old key is revoked.
  The two-key gap after rollback is reported in the PR as not covered by
  the MVP.
- Overlap: apply runs with `--overlap 0s` so revoke happens in the same
  run; the test asserts the final `revoked` state and exit 0.
- Fixture: reuse `tests/fixtures/trufflehog_aws_e2e.ndjson` (one AWS
  finding with runtime-substituted placeholders).

## Shared harness

Move the AWS model and the runner from `tests/e2e_aws.rs` into
`tests/e2e/mod.rs` (a directory module, so Cargo does not build it as its
own test target), used by both `e2e_aws.rs` and `acceptance_mvp.rs`. The
SHA-264 tests stay unchanged in behaviour.

Additions:

- `GithubModel`, a wiremock `Respond` over `Arc<Mutex<_>>` for one
  repository: `GET /repos/acme/api/actions/secrets` (lists
  `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and an unrelated
  `SLACK_WEBHOOK`), `GET .../public-key` (the public half of a test
  `crypto_box` key pair), `PUT .../{name}` which checks `key_id`, opens the
  sealed box with the private half and stores the plaintext, and answers
  403 when `deny_put` is set. Every request must carry `Authorization:
  Bearer <operator token>`, otherwise 401.
- Priorities: wiremock priority 1 is the highest, so the AWS model moves to
  priority 2 and the GitHub routes (`path_regex("^/(repos|orgs)/")`) mount
  at priority 1.
- The read-only predicate only classifies AWS requests; GitHub requests
  are classified by method, so an Actions `PUT` counts as a mutation for
  `assert_no_mutations()`.
- `E2e::start_with_github()` writes `consumers.github_actions.targets:
  [acme/api]` and `providers.github.api_url` (the same server) into
  `rotate.yaml` and puts `ROTATE_GITHUB_TOKEN` in the child environment.
  The runner also checks every output and file for the GitHub token.
- `assert_requests_clean` also checks GitHub requests: no secret access
  key in any header or body (the PUT body is ciphertext).

No production change is planned. Any bug the test finds is fixed minimally
and listed in the PR.
