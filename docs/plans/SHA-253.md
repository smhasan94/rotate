# Implementation plan: SHA-253 GitHub Actions secrets consumer

Ticket edits applied with this plan:

- One match per secret name, not one match naming both AWS names. The
  consumer contract (SHA-222) gives every `ConsumerMatch` one `holds`, so a
  repo with both AWS convention names yields two ByName matches:
  `github-actions:acme/api:AWS_ACCESS_KEY_ID` (holds `KeyId`) and
  `github-actions:acme/api:AWS_SECRET_ACCESS_KEY` (holds `Secret`). AC1 and
  AC8 are reworded to match: `find` lists the key-id match before the secret
  match for each target, so the engine's in-order updates PUT the id first.
- Mappings are per provider, not per target. `rotate.yaml` (SHA-213) has
  `consumers.github_actions.secret_names` and `key_id_names` keyed by
  provider, applied across every target; AC2's fixture becomes
  `secret_names: {aws: [PROD_AWS_SECRET]}`. The names come from
  `plan::consumer_names`, which merges the D4 convention with the mappings;
  the consumer reuses it to tell key-id names from secret names and never
  repeats the table.
- Environment secrets move out of scope: the config has no field for them.
  A later ticket can add `environments` per target.
- Operator token: `ROTATE_GITHUB_TOKEN`, falling back to `GITHUB_TOKEN`
  (FR24). The rotate-specific name wins so an Actions job can pass an admin
  PAT without shadowing the job token. Missing token with targets configured
  makes `find` fail with a message naming both variables (a lookup-error
  blocker in the plan); with no targets the consumer makes no call at all.
- A 403 on a target (for example org secrets without `admin:org`) is a
  target-level NotUpdatable match carrying GitHub's message, like the 404
  case. 401, 429/rate limit and 5xx fail `find` for the whole consumer.
- T9 runs at the library level: `rotate apply` (SHA-254) does not call
  consumers yet. The audit-log half of T9 moves to SHA-254, which owns the
  audit records for update and restore.

## Approach

`src/github.rs`, a small GitHub REST client that SHA-260 (GitHub token
provider) reuses:

- `GithubClient::new(api_url, Option<SecretValue>)` builds nothing that
  touches the network or the OS trust store; the reqwest client is built on
  the first request (`OnceLock`).
- `operator_token(lookup)` / `operator_token_from_env()`:
  `ROTATE_GITHUB_TOKEN`, then `GITHUB_TOKEN`, empty counts as unset, read
  into `SecretValue`.
- `get_json`, `get_paged` (`per_page=100`, follows `Link: rel="next"` only
  when the next URL is under the configured base, so the token never goes to
  another host), `put_json`. Headers: `Authorization: Bearer` marked
  sensitive, `Accept: application/vnd.github+json`,
  `X-GitHub-Api-Version: 2022-11-28`, `User-Agent: rotate/<version>`.
  30 s request timeout.
- `GithubError { RateLimited { retry_after }, NoToken, Status { status,
  message }, Transport(String) }`. 429, or 403 with
  `x-ratelimit-remaining: 0`, is `RateLimited` with `retry-after` or
  `x-ratelimit-reset`. The message is GitHub's JSON `message` field, capped,
  never the request. `From<GithubError> for ConsumerError` maps 5xx and
  transport to `Transient`, the rest to `Permanent`.

`src/consumer/github_actions.rs`, `GithubActionsConsumer` named
`github-actions`:

- `new(client, &ConsumersConfig)`; `from_config(&ConsumersConfig,
  &GithubConfig)` reads the operator token from the environment. Neither
  makes a call.
- `find`: no targets or no names, return empty with no call. Otherwise list
  repo secrets (`GET /repos/{o}/{r}/actions/secrets`) and org secrets
  (`GET /orgs/{org}/actions/secrets`), keep names in `SecretRef::names`,
  key-id names first. `holds` is `KeyId` for names in
  `consumer_names(provider).key_id`, else `Secret`. 404 gives a
  `github-actions:<target>` match, not updatable, "not found or token lacks
  access"; 403 gives the same with GitHub's message. Other targets are still
  checked.
- `update` / `restore` share one write: refuse not-updatable matches
  (`ConsumerError::NotUpdatable`), parse the ref back to a configured
  target and name, pick the value (`Secret` the secret half, `KeyId` the
  key id, `KeyPair` unsupported), `GET .../actions/secrets/public-key`,
  seal, `PUT .../actions/secrets/{name}` with `encrypted_value` and
  `key_id`. Org secrets first `GET` the secret's `visibility`, and for
  `selected` the repository ids, and send them back unchanged.
- Sealing: `crypto_box` 0.9 with `seal` (RustCrypto, Apache-2.0 OR MIT,
  pure Rust, libsodium `crypto_box_seal` construction: X25519, XSalsa20-
  Poly1305, BLAKE2b nonce). The plaintext is only read inside
  `expose_secret`; the ciphertext is base64-encoded.

Rejected: `sodiumoxide` (unmaintained, C libsodium build), `dryoc` (one
maintainer, wider API than needed), hand-rolling the box from `x25519-dalek`
and `crypto_secretbox` (more crypto code to own). Rejected: the
`octocrab` client (large tree, its own error and auth model, harder for the
redaction rules). Rejected: one match per target naming both AWS names
(conflicts with the single `holds` per match).

Registration: `providers::consumers()` keeps its signature (SHA-254 owns
`src/main.rs`) and calls a new `consumers_with(&ConsumersConfig,
&GithubConfig)` with defaults, so the consumer is registered but has no
targets and makes no call. Switching `main.rs` to `consumers_with` with the
loaded config is a one-line change for SHA-254.

- `src/github.rs` (new), `src/consumer/github_actions.rs` (new),

- `src/providers.rs`: register `GithubActionsConsumer`.
- `Cargo.toml`: `reqwest` moves to `[dependencies]` with

  to `[dependencies]`.
- `tests/github_actions.rs` (new); `CONTRIBUTING.md` and `README.md` note
  the token variables.

## Secret handling

Values stay `SecretValue` until sealed inside `expose_secret`; only the
sealed, base64 ciphertext is in a request. The key id is not secret but is
handled the same way. The operator token is a `SecretValue` and goes into
a sensitive header. Errors carry status and GitHub's message, never a body
or a value. `consumer_ref` holds target and secret name only.

## Test mapping

Integration tests in `tests/github_actions.rs` against wiremock
(`CallRecorder`), plus unit tests in the two modules.

- T1 (AC1): `find_matches_aws_convention_names_by_name`.
- T2 (AC2): `find_matches_mapped_name_without_defaults`.
- T3 (AC3): `update_puts_sealed_value_that_decrypts_to_replacement`; unit
  `seal_known_answer_libsodium_vector` (ciphertext made with libsodium
  through PyNaCl, opened with `crypto_box`) and `seal_round_trip`.
- T4 (AC4): `update_org_secret_preserves_selected_visibility`.
- T5 (AC5): `restore_puts_old_value`.
- T6 (AC6): `find_lists_404_target_as_not_updatable_and_checks_others`,
  `find_lists_403_org_with_api_message`.
- T7 (AC7): `find_makes_no_mutating_calls`, `no_targets_makes_no_calls`.
- T8 (AC8): `aws_pair_puts_key_id_then_secret`.
- T9 (AC3, AC5): `values_and_token_never_leak`: canaries through find,
  update, restore and failing calls with tracing captured; absent from logs,
  errors, refs and request bodies.
- T10 (AC1 to AC8): `conformance` runs `consumer_suite` (ByName) against a
  stateful wiremock responder.
- Extras: `rate_limit_maps_to_retry_after`, `pagination_follows_link`,
  `next_link_to_other_host_is_refused`, `missing_token_fails_find`,
  `operator_token_prefers_rotate_variable`, and `live_github_actions_find`
  (`#[ignore]`, `ROTATE_LIVE_TESTS=1`, needs `ROTATE_LIVE_GITHUB_REPO`).

## Sequence

1. Cargo lines, `cargo deny check`.
2. `src/github.rs` with unit tests.
3. Consumer, sealing, registration.
4. Integration tests, conformance, docs; all checks; PR.

## Risks

- `src/providers.rs` is also touched by SHA-252 (Secrets Manager
  registration): both add one line, so the merge is trivial.
- `Cargo.toml` and `Cargo.lock` change in SHA-251 and SHA-252 too; take
  main's lock and rebuild.
- The CLI does not search Actions secrets until `main.rs` passes the loaded
  config (SHA-254).

## Out of scope

Environment, Dependabot and Codespaces secrets; the GitHub token provider
(SHA-260); reading values (impossible); retries with backoff (engine).
