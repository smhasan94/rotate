# Implementation plan: SHA-339 Homebrew tap

Install today is the README curl block against GitHub Releases. Most users
are on macOS, where `brew install` is the expected path, and crates.io is
not an option (the name `rotate` is taken). The maintainer created the
public tap `smhasan94/homebrew-rotate` (a README and LICENSE only). This
ticket adds a formula template and a render script here, a release job that
pushes the rendered formula to the tap, a CI check that `brew audit
--strict` and `brew style` accept it, and a release check that `brew
install smhasan94/rotate/rotate` works.

## Findings

- `release.yml` builds four targets: `x86_64-unknown-linux-gnu` (Ubuntu
  22.04), `aarch64-unknown-linux-gnu` (Ubuntu 22.04 arm), `x86_64-apple-darwin`
  and `aarch64-apple-darwin`. Each tarball is `rotate-<version>-<target>.tar.gz`
  with `rotate`, `LICENSE` and `README.md` at its top level (no directory),
  so Homebrew stages it as is and `bin.install "rotate"` finds the binary.
- `SHA256SUMS` is `sha256sum` output: `<64 hex>  <file>`, one line per
  tarball. `scripts/verify-release.sh` already strips an optional `*`
  binary marker; the render script does the same.
- `publish` is the only job with `contents: write`, and only on a tag.
  `verify`, `install-linux` and `install-macos` run after it against the
  published release.
- Scripts are tested by the workflows that use them (`readme-install.sh`
  in the `notes` job, `verify-release.sh` in `verify`) and Rust integration
  tests run shell where it matters (`tests/lint.rs`). `cargo test` runs on
  Linux and macOS in `ci.yml` on every pull request.
- No formula named `rotate` exists in homebrew-core (`brew info rotate`
  finds none), so the short name `rotate` works once the tap is added, and
  `smhasan94/rotate/rotate` always works.
- `brew audit` refuses a path argument; the formula must sit in a tap. A
  throwaway local tap (`brew tap-new --no-git`) is enough.
- Since Homebrew 6.0.0 a third-party tap's formulae load only when trusted.
  `brew install user/tap/formula` trusts that one formula; a short name
  after `brew tap` needs `brew trust` first. The README therefore uses the
  full name `smhasan94/rotate/rotate` for install and upgrade.
- No `docs/releasing.md` exists; release steps live only in `release.yml`
  comments and the SHA-215 and SHA-271 plans.

## Decisions

- Template plus bash render script. `packaging/homebrew/rotate.rb.tmpl`
  holds the formula with `@VERSION@` and one `@SHA256_<TARGET>@`
  placeholder per target. `scripts/render-formula.sh <version>
  <SHA256SUMS>` prints the formula on stdout. It checks the version is
  `X.Y.Z` (an optional pre-release or build suffix allowed), reads the four
  expected names `rotate-<version>-<target>.tar.gz`, requires exactly one
  line each with a 64-character lowercase hex checksum, and fails listing
  every missing target by name (and every malformed or duplicate line).
  After substitution it fails if any `@...@` placeholder is left. Values
  are validated before they reach `sed`, so no escaping is needed. Bash
  only, so it runs on the Ubuntu and macOS runners and on a laptop with no
  Ruby or Homebrew.
- The formula: `desc`, `homepage`, no `version` line (`brew audit
  --strict` rejects it as redundant with the version scanned from the
  URL), `license "Apache-2.0"`,
  `on_macos`/`on_linux` each with `on_arm`/`on_intel` holding `url` and
  `sha256`, `bin.install "rotate"`, and a `test do` that checks `rotate
  --version` prints `rotate <version>`. No `livecheck` (the tap is updated
  by the release, not by `brew bump`), no `head`, no bottles.
- T1 is a Rust integration test, `tests/homebrew.rs`, that runs the script
  with bash, so it runs in `cargo test` on Linux and macOS in every pull
  request without touching `ci.yml`. Fixtures live next to the template in
  `packaging/homebrew/fixtures/` (a fake `SHA256SUMS` for version 1.2.3 and
  the expected `rotate.rb`).
- T2 is a new workflow, `.github/workflows/homebrew.yml`, on macos-latest
  for pull requests that touch `packaging/**`, the render script or the
  workflow itself (and manual runs): render the fixture, copy it into a
  local tap, `brew audit --strict --formula` and `brew style`.
- `release.yml` gets a `homebrew` job after `publish` and `verify`, on
  macos-latest: download the published `SHA256SUMS` with `gh release
  download`, render, audit and style the rendered formula in a local tap
  (the same check as T2 on the real file), then check out the tap with
  `HOMEBREW_TAP_TOKEN`, write `Formula/rotate.rb`, and commit "rotate
  <version>" as github-actions[bot] and push to `main`. When the formula is
  already identical (a re-run) it commits nothing and says so. When the
  secret is empty the first step prints a `::notice::` and every later
  step is skipped, so the job and the release stay green. The job has
  `contents: read` only; the token is used only by `actions/checkout` for
  the tap and the `git push`, never echoed.
- T4 is a `brew-install` job after `homebrew`, on macos-latest, only when
  the tap was updated (job output): `brew install smhasan94/rotate/rotate`,
  check `rotate --version` prints `rotate <version>`, `brew test`, then
  `brew uninstall` and `brew untap`.
- Docs: a Homebrew block in the README install section (outside the
  `install:start`/`install:end` markers, so `readme-install.sh` is
  unchanged), a line in `docs/usage.md` install, and a new
  `docs/releasing.md` with the release steps, what the release workflow
  does, the tap update and the one-time token setup.

## Maintainer decisions

Recommended, pending maintainer review.

1. How the formula is generated.
   - (a) Template plus bash render script. Needs nothing but bash; the
     test compares the whole output.
   - (b) A Ruby script. Natural for a Ruby file, but adds a Ruby
     dependency to the release path and the tests.
   - (c) `sed` the version and checksums into the tap's file in place.
     No template in this repo, so the formula cannot be reviewed or tested
     here.
   - Recommendation: (a).
2. How the release job writes to the tap.
   - (a) A fine-grained personal access token in the secret
     `HOMEBREW_TAP_TOKEN`, repository access "only
     smhasan94/homebrew-rotate", permission Contents: read and write.
     Simple; expires (set a reminder).
   - (b) A deploy key with write access on the tap, private half as a
     secret. Scoped to the one repository and does not expire, but needs
     SSH setup in the job.
   - (c) A GitHub App installed on the tap. Most auditable; most setup.
   - Recommendation: (a), as the ticket says. Missing secret means a notice
     and a green release.
3. Commit straight to the tap's `main` or open a pull request there.
   - (a) One direct commit per release. Matches AC3; the tap has no CI to
     wait for.
   - (b) A pull request the maintainer merges. One more manual step per
     release.
   - Recommendation: (a).
4. Where the T2 audit runs.
   - (a) A new `homebrew.yml` on macos-latest, only for pull requests that
     touch packaging. Keeps `ci.yml` as the four checks, costs macOS
     minutes only when packaging changes.
   - (b) A job in `ci.yml` on every pull request.
   - Recommendation: (a). The release job also audits the real formula
     before pushing it.
5. A workflow in the tap itself (`brew test-bot`, bottles).
   - (a) None for v1: the tap holds one generated file, prebuilt binaries
     need no bottles, and this repo audits the formula before every push.
   - (b) `brew test-bot` on pushes to the tap.
   - Recommendation: (a). Revisit if someone other than the release job
     ever commits to the tap.
6. When the `homebrew` job runs.
   - (a) After `verify`, so a release whose assets fail verification never
     reaches brew users.
   - (b) Right after `publish`.
   - Recommendation: (a). A flaky verify can be re-run; the homebrew job
     follows.
7. Seeding the tap with v0.2.0.
   - (a) The maintainer commits the v0.2.0 formula rendered from the
     published `SHA256SUMS` now, so the README's `brew install` works
     before the next tag.
   - (b) Wait for the next tag.
   - Recommendation: (a).

## Ticket text

### Context

Install today is the README curl block from GitHub Releases (crates.io is
not an option: the name `rotate` is taken). Most of the target users are on
macOS, where `brew install` is the expected path. The maintainer chose a
separate tap repository, `smhasan94/homebrew-rotate`, on 2026-10-06.
Release assets are `rotate-<version>-<target>.tar.gz` for aarch64/x86_64
Apple Darwin and Linux GNU, plus `SHA256SUMS`.

### Scope

In scope:

- `Formula/rotate.rb` in the tap: `on_macos`/`on_linux` × `on_arm`/`on_intel`
  URLs and checksums for the four release targets, `bin.install "rotate"`,
  and a `test do` block running `rotate --version`.
- A formula template and a render script in this repo (for example
  `packaging/homebrew/rotate.rb.tmpl` and `scripts/render-formula.sh`) that
  fill version and checksums from `SHA256SUMS`.
- A `homebrew` job in `.github/workflows/release.yml` after `publish`:
  render the formula, then commit and push it to the tap using a
  fine-grained token secret (`HOMEBREW_TAP_TOKEN`, Contents: write on the
  tap only). It is skipped with a notice when the secret is missing.
- A README install section for Homebrew, and docs on how a release updates
  the tap.

Out of scope: homebrew-core submission, bottles built by Homebrew, Windows,
other package managers.

### Acceptance criteria

- AC1. Given a `SHA256SUMS` file and a version, when the render script
  runs, then the formula names the four release URLs for that version with
  their checksums from the file, and it fails, naming the target, if any
  target is missing.
- AC2. Given the rendered formula, when `brew audit --strict` and `brew
  style` run on it in CI, then they pass.
- AC3. Given a published release and the token secret, when the release
  workflow runs, then the tap's `Formula/rotate.rb` is updated to that
  version in one commit; given no secret, then the job is skipped with a
  notice and the release still succeeds.
- AC4. Given the tap updated to the latest release, when `brew install
  smhasan94/rotate/rotate` runs on macOS, then `rotate --version` prints
  that version.

### Test plan

- T1 (integration, script test) - covers AC1 - render from a fixture
  `SHA256SUMS`; compare to an expected formula; a missing target fails with
  its name.
- T2 (CI job on macos-latest) - covers AC2 - render from a fixture and run
  `brew audit --strict --formula` and `brew style` on it.
- T3 (release workflow, after merge) - covers AC3 - the next tag updates
  the tap; the job log shows the commit.
- T4 (release workflow, after merge) - covers AC4 - a `brew-install` verify
  job on macos-latest installs from the tap and checks `--version`.

### Definition of done

All T-cases pass in CI, fmt, clippy and cargo deny pass, docs updated, PR
reviewed and merged. T3 and T4 are confirmed on the next tag.

### Dependencies

Blocked by: none. The maintainer adds the `HOMEBREW_TAP_TOKEN` secret
before the next tag.
