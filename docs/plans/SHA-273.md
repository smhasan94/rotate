# Implementation plan: SHA-273 License and advisory policy for the TLS and AWS stacks

Ticket edits applied with this plan:

- The premise has changed since the ticket was filed. `ring` 0.17.14 is
  `Apache-2.0 AND ISC`, both already allowed, and no MPL-2.0 crate appears
  in any tree. `webpki-roots` 1.x moved to CDLA-Permissive-2.0. The decision
  is no longer "allow MPL-2.0 and ring" but which TLS roots and AWS SDK
  features to use.
- The real blocker is advisories, not licenses. The AWS SDK's default
  features pull a legacy HTTP stack (`hyper` 0.14, `rustls` 0.21,
  `rustls-webpki` 0.101, `h2` 0.3) with four open RUSTSEC advisories. The
  ticket's out-of-scope line ("changing HTTP or TLS stacks to avoid the
  question") is kept: this ticket picks SDK features, it does not swap stacks.

## Findings (T1)

`cargo deny check` with the current `deny.toml` on scratch crates, latest
versions on 2026-10-01:

| Tree | licenses | advisories | crates |
|---|---|---|---|
| A: `reqwest` 0.12 `rustls-tls` (bundled roots) | rejected: `webpki-roots` 1.0.9, CDLA-Permissive-2.0 | ok | 130 |
| B: `reqwest` 0.12 `rustls-tls-native-roots` | ok | ok | 136 |
| C: `aws-config`, `aws-sdk-sts`, `aws-sdk-iam`, `aws-sdk-secretsmanager`, default features | ok | 4 vulnerabilities (h2 0.3.27 RUSTSEC-2026-0258; rustls-webpki 0.101.7 name constraints x2 and CRL panic) | 224 |
| D: same SDK crates, `default-features = false`, `default-https-client` + `rt-tokio` | ok | ok | 192 |

Tree D uses `aws-lc-rs` and `aws-lc-sys` (C, built with the system C
compiler). All four release targets build natively (Linux and macOS on x86_64
and aarch64, no cross-compiling, no musl).

## Decision

1. HTTP for providers: `reqwest` with `rustls-tls-native-roots` (OS trust
   store). No license allowlist change. Trusting the OS store means corporate
   TLS-inspecting proxies and private CAs work. A distroless or `scratch`
   image needs CA certificates installed; noted in CONTRIBUTING.
2. AWS: the official SDK crates with `default-features = false` and
   `default-https-client`, `rt-tokio` (plus `behavior-version-latest`, `sso`,
   `credentials-process` on `aws-config`). Rejected: hand-written SigV4 and
   credential chain. It would be more security-sensitive code to own.
3. `deny.toml` `[bans]` denies `hyper` < 1, `rustls` < 0.23,
   `rustls-webpki` < 0.102 and `h2` < 0.4 with a reason, so a dependency
   change cannot bring the legacy stack back. Tree C then fails `bans` as
   well as `advisories`.
4. Not now: unifying `reqwest` onto the `aws-lc-rs` provider so one crypto
   library ships instead of two. SHA-251 can do it if the binary size
   matters; it needs `rustls-tls-native-roots-no-provider` and installing the
   provider at startup.
5. CDLA-Permissive-2.0 stays off the allowlist until a crate needs it.

## Changes

- `deny.toml`: replace the SHA-273 header note with the policy above; add the
  `[bans] deny` entries.
- `CONTRIBUTING.md` "Dependencies": the TLS and AWS rules and why.
- No `Cargo.toml` change; SHA-251 adds the crates following these rules.
